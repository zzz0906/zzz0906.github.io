    RePrism 阅读笔记：把提示表示纳入请求调度

    笔记日期： 2026-11-26（UTC）
    笔记作者： Zhongzhu Zhou
    阅读论文： RePrism: Joint Request and Representation Scheduling for LLM Agent Serving
    论文作者： Xijiang Shen, Aoli Zhu, Yanbo Tan, Xiyuan Hu, Huailiang Tan
    arXiv： 2611.32545
    版本与日期： v1，2026-11-24

    1. 我怎样理解这篇论文

    读 RePrism 时，我先把注意力放在一个看似很小的变化上：调度器比较的基本对象，从“一个准备好的请求”变成了“一个请求加一种执行表示”。前者通常先决定谁运行，再为它选择缓存或 adapter；后者让表示本身的计算代价、已有资源和后续复用机会参与排序。这个变化之所以有意义，是因为选哪一种表示，会反过来改变其他请求能用多少显存、哪些上下文需要重算，以及整个 agent 会话什么时候结束。

    论文讨论四种表示：完整文本 Direct、保留前缀状态的 KV、把固定提示行为训练进 LoRA 的 Adapter，以及 Adapter 加残余上下文缓存的 Hybrid。它们有不同的计算与存储代价，也有不同的行为承诺。Direct 与 KV 被当作精确执行路径；Adapter 和 Hybrid 则允许在应用接受的范围内近似原提示行为，并不保证输出 token 完全一致。先明确这个前提，后面的性能数据才有可解释的含义。[1，正文第 1–4 节]

    图 1：根据正文第 4 节与附录 A 自绘的 Mermaid 说明图。离线行为资格决定哪些表示可以用，在线评分与资源准入决定这轮实际运行哪些组合。

    最醒目的结果是：动态到达率为每秒 1.8 个会话时，完整 RePrism 相对 S-LoRA 达到 1.37 倍请求吞吐，并把 P95 会话完成时间缩短到约四分之一。更窄的“联合评分对比请求优先评分”实验，则报告吞吐提高 2.7%、平均会话完成时间降低 12.3%。我不会把这两组结果混成一个结论：前一组同时包含表示集合、调度与缓存管理的差异，后一组才更接近联合决策本身的边际价值。

    这份笔记依据 19 页 v1 全文及附录 A–C，先完成英文技术阅读稿，再按中文的解释顺序重写。文中明确区分论文测量、自行复算与构造算例；我没有训练这些 adapter，也没有重跑论文的服务基准。对我来说，真正值得继续追问的是：行为资格有多可靠、预测误差怎样影响显存计划，以及调度器自身的 CPU 时间会不会吃掉收益。

    2. 前置知识：会话是图，提示有不同寿命

    一次用户任务可能需要多次 LLM 调用。仓库修复需要检索、诊断、生成补丁、验证和复查；其中有串行依赖，也有能并行的分支。论文用有向无环图表示调度器当前看得见的工作流，节点是调用或执行阶段，边表示数据或控制依赖。只有前驱完成、分支条件成立的节点，才进入 ready 集合。调度能改变 ready 节点的先后，不能越过真实依赖。

    用户感受到的是整个任务什么时候结束，因此论文重视会话完成时间 SCT。一个会话在 a 时刻按计划到达，目标节点在 f 时刻完成，SCT 就是 f 减 a。单请求的 TTFT 则从该请求被提交开始，到首个 token 返回结束。某条非关键分支先出 token，并不一定让会话更早结束；相反，一个不大的汇合前置请求若提前运行，可能让后续整条链更早启动。

    接着看输入。论文按复用范围将其分成固定行为提示 P、会话或路径上下文 R，以及本次调用特有的查询 Q：

    x=P∥R∥Q.(1)x=P\mathbin\Vert R\mathbin\Vert Q. \tag{1}x=P∥R∥Q.(1)

    P 可以是跨会话重复的角色规则、字段格式或系统指令；R 往往是同一会话中后继调用会用到的状态；Q 是新增问题。这个划分表达复用寿命，不意味着同样长度的字符串可以共享状态。精确 KV 复用仍要求有效模型、前缀内容、顺序和位置解释一致。

    普通自回归模型先通过 prefill 为输入建立 K、V，再逐 token 解码。缓存前缀可以省掉重复 prefill，但解码时仍需关注这些前缀 token。若把 P 的行为放进 adapter，在线输入中就可以省略 P；代价是模型变了，而且每层可能增加低秩运算。LoRA 对一个权重矩阵的更新可写为

    W′=W+BA,B∈Rdout×r,A∈Rr×din.(2)W'=W+BA,\qquad B\in\mathbb R^{d_{out}\times r},\quad A\in\mathbb R^{r\times d_{in}}. \tag{2}W′=W+BA,B∈Rdout​×r,A∈Rr×din​.(2)

    新增参数量随秩 r 与输入、输出维度之和增长，而非与提示 token 数直接成正比。这里要区分“存储形式不按提示长度增长”和“某个秩足够表达任意长提示”。后者没有保证。指令的信息复杂度、基座模型已有能力、适配层位置，都可能改变最低可用秩。

    我把这个设计看作应用与服务系统之间的接口：应用提供依赖、可复用身份和允许的行为替代；服务系统据此算成本。如果只有到达时间和输入输出长度，系统很难还原真实共享关系。论文选择人工设计工作负载，部分原因正是公开生产 trace 通常缺少提示文本和提示到 adapter 的映射。

    3. 四种表示改变了什么

    Direct 每次处理 P、R、Q，调用结束后不保留可复用状态。KV 对匹配前缀留下键值状态，命中时从后缀继续计算。Adapter 用训练好的权重表达 P 的行为，在线只处理 R、Q。Hybrid 除了这个 adapter，还保留在该 adapter 生效时为 R 计算的 KV；两种资源都命中后，只需为 Q 做新 prefill。[1，第 2 节]

    图 2：依据第 2 节自绘的对照表。表中写的是命中路径；缺失资源时仍要计入加载或构建成本。近似路径需先满足应用定义的行为资格。

    为什么不总选最快的 warm path？论文图 4 给了一个直接例子。在最长的测试配置下，KV 占 1000 MiB，Adapter 占 64 MiB，Hybrid 占 192 MiB；对应相对 Direct 的首 token 加速约为 6.70、3.26、6.62 倍。Hybrid 用更少的存储接近 KV 的首 token 速度，Adapter 最省内存但仍需重算 R。这些点说明资源形态的差异，却还没有纳入其他会话的机会成本。

    图 3：原论文 Figure 4，裁自 PDF 第 4 页，数据未修改。首 token 加速与端到端加速的分母不同，不能互相替代。

    这组实验的端到端加速最高仅约 1.18 倍，因为输出生成仍占据可观时间。KV 虽然省 prefill，后续每步仍需看完整前缀；Adapter 和 Hybrid 省掉 P 的在线 token 后，长提示下也可能减少解码开销。图中的 P 长度含聊天模板 token，不能直接拿前文配对的 378、733、1004、1723 这些固定提示长度去替换图上的横坐标。

    Hybrid 还要为首次残余缓存付费。R 为 64、128、256、512 token 时，首次构建与注册分别耗时 25.28、37.33、65.47、140.79 ms；随后每次命中相对 Adapter 节省 29.77、33.69、70.18、120.25 ms。若暂不考虑显存竞争与被逐出，用未来命中次数 n 还本需要

    n ΔThit≥Tbuild,nmin=⌈Tbuild/ΔThit⌉.(3)n\,\Delta T_{hit}\ge T_{build},\qquad n_{min}=\left\lceil T_{build}/\Delta T_{hit}\right\rceil. \tag{3}nΔThit​≥Tbuild​,nmin​=⌈Tbuild​/ΔThit​⌉.(3)

    四组比值约为 0.85、1.11、0.93、1.17，对应至少 1、2、1、2 次未来命中。这个复算解释了缓存为何能很快回本，却不能推导出“应该尽可能保留”。占用的显存若挤走另一个更有价值的对象，还要加上后者恢复、排队和批次受限的代价。离线 adapter 训练成本也不在这些在线构建毫秒数里面。

    因此，残余内容不重复时始终用 Adapter 可能合理；R 高度重复、显存充裕时始终用 Hybrid 也可能合理。联合选择主要处理两者之间的区域：不同请求的复用特征、资源驻留和内存压力并不相同，或者会随时间变化。

    4. 先判断能不能替代，再判断值不值得

    论文用 SGD 数据集的 Media_1 状态追踪任务演示提示内化。P 规定状态更新和输出字段规则；R 给前一状态，Q 是新话语。训练时基座权重冻结，仅更新注意力层的 LoRA 参数，并用数据集标注得到目标答案。虽然正文用 teacher/student 解释“带 P”和“不带 P”的两种配置，附录 B 实际描述的是目标答案上的预测误差训练。我不把它改写成未报告的逐 token teacher KL 蒸馏目标。

    这个示例有 48 条训练、12 条开发和独立 24 条资格测试样本。评估采用贪心生成，最多生成 64 个新 token。检查器先确认五个字段齐全，再比较 intent 和必要字段值；字段顺序可以不同。对 1004-token Media_1 提示，rank 4、8 未过门槛，rank 16 得分 0.917，超过预设的 0.85。论文按规则增加秩、重新训练并检查，选择最低的合格秩。[1，第 3.1 节、附录 B]

    资格得分本质上是有限样本上的通过率：

    B^=1n∑i=1n1{check⁡(yi)=1},B^≥0.85.(4)\widehat B=\frac1n\sum_{i=1}^{n}\mathbf 1\{\operatorname{check}(y_i)=1\},\qquad \widehat B\ge0.85. \tag{4}B=n1​i=1∑n​1{check(yi​)=1},B≥0.85.(4)

    附录 C 让这个“行为”变得具体：用户现在要求开启字幕，intent 保持 PlayMovie，标题 Body Double 从 R 搬过来，导演与类型字段因不适用于当前 intent 设为 NONE。输出格式漂亮，但错误地改了片名或保留无关 genre，仍然失败。反过来，字段顺序不同但规则全对，可以通过。因此这里的近似是任务约束下的行为近似，既不要求逐字匹配，也不是任意宽松的“意思差不多”。

    资格与驻留是两个独立维度。一个合格 Hybrid 即使当前没有残余 KV，只要能在正确 adapter 下重建，仍可能是候选，只是成本更高。一个不合格 adapter 即使就在显存中，也不能因为快而进入候选。尤其是同样的 R 文本，不能直接使用另一个 adapter 生成的 KV。实际接口至少应把模型、adapter、有效前缀和位置配置绑定到缓存身份；这是 KV 依赖模型的正确性要求，不是论文新增测量的功能。

    后续大规模调度实验使用张量结构一致、权重不同的 proxy adapter。作者拿一个语义合格的 rank-16 adapter 与其 proxy 对比，平均吞吐和平均 P95 SCT 的差异都低于 1.3%。这支持在该设置中用张量形状代理执行成本，但不能推广成“所有 proxy 都保留原任务行为”。这条证据边界会在批判性分析中再次用到。

    5. 节点价值：离结束有多近，关键路径有多长

    准备好的请求 v 只能和允许的表示集合 M(v) 配对。依赖条件与表示资格一起过滤候选：

    Ct={(v,m):v∈Rt, m∈M(v), Et(v,m)=1}.(5)\mathcal C_t=\{(v,m):v\in\mathcal R_t,\ m\in\mathcal M(v),\ E_t(v,m)=1\}. \tag{5}Ct​={(v,m):v∈Rt​, m∈M(v), Et​(v,m)=1}.(5)

    接下来要回答“运行这个节点，能怎样推进会话”。附录 A.1 从终点向前计算路径：尚未运行的节点采用 Direct 执行时长估计；正在运行的节点按剩余输出预算缩放；还没到服务器的节点加入已知工具等待。一个节点的剩余路径长度 L_v，等于它自身的剩余时间加直接后继中最大的路径长度；L_s 是会话可见图中最长的剩余路径。

    论文用两个比值相乘得到进度价值，再加入等待紧迫度，时间尺度 H 为 60 秒：

    Pt(s,v)=HH+LsLvLs,Wt(s)=min⁡(1,ws/H).(6)P_t(s,v)=\frac{H}{H+L_s}\frac{L_v}{L_s},\qquad W_t(s)=\min(1,w_s/H). \tag{6}Pt​(s,v)=H+Ls​H​Ls​Lv​​,Wt​(s)=min(1,ws​/H).(6)

    第一个比值随 L_s 变短而上升，偏向接近结束的会话；第二个比值在同一会话里优先更关键的长路径节点。比如 H=60、L_s=60、L_v=60 时，进度价值为 0.5；同一会话另一节点 L_v=30，只得到 0.25。若会话只剩 15 秒、当前节点覆盖完整剩余路径，进度价值为 0.8。这个设计兼顾“尽快收尾”和“先推进关键分支”，而不是简单按最长任务或最短任务排序。

    等待量 w_s 的累积条件更细：会话至少有一个 ready 请求，而且没有请求正在运行时，才继续增加。执行时间和等并行分支的时间不会自动变成额外等待优势。这能避免慢任务仅因执行久就持续抬高优先级，但也意味着它不是普通的会话墙钟年龄。节点值与表示值在本设置中都用单位权重：

    Vnode=P+W,Vrepr=Vnow+Greuse−Oresource.(7)V^{node}=P+W,\qquad V^{repr}=V^{now}+G^{reuse}-O^{resource}. \tag{7}Vnode=P+W,Vrepr=Vnow+Greuse−Oresource.(7)

    表示价值有三部分：这次省多少时间、以后可能复用省多少时间，以及占用资源导致其他缓存被逐出会多付多少恢复成本。三者最终都相对当前请求的 Direct 剩余时间表达，这样不同请求间至少有一个共同的参照口径。它仍是启发式评分，不是直接求解全局 SCT 最优值。

    6. 表示价值：即时收益、未来复用与机会成本

    设 T_D 与 T_m 分别是 Direct 和模式 m 的剩余执行时间，都包含 prefill 和解码；新增准备成本是加入该候选前后，资源计划增加的加载或构建时间。于是即时收益先减去模式计算和额外准备，再除以 Direct 基线：

    Vnow(v,m)=TD−Tm−ΔTloadTD.(8)V^{now}(v,m)=\frac{T_D-T_m-\Delta T_{load}}{T_D}. \tag{8}Vnow(v,m)=TD​TD​−Tm​−ΔTload​​.(8)

    举一个解释性算例：Direct 要 100 ms，另一模式计算 30 ms，新加载 20 ms，收益就是 0.5；若新加载变成 90 ms，收益为 -0.2。这里不能把同一 adapter 在本批次中需要加载一次的时间，向每个新请求重复收取，所以论文使用“新增”准备成本。已驻留与需冷启动可以让同一种表示的价值完全不同。

    未来收益来自当前可见的 pending 请求。当前请求和已经选进本轮批次的请求不再计入，以免重复奖励。未来请求 u 的节省时间用执行概率 p_u 加权，再按依赖满足前的预计延迟 d_u 折扣，T_0 为 1 秒：

    Greuse(v,m)=1TD∑upuΔTu1+du/T0.(9)G^{reuse}(v,m)=\frac1{T_D}\sum_u\frac{p_u\Delta T_u}{1+d_u/T_0}. \tag{9}Greuse(v,m)=TD​1​u∑​1+du​/T0​pu​ΔTu​​.(9)

    已提交请求取概率 1，尚未提交的条件分支用已知概率。一个未来请求若同时受益于几个共享资源，总节省时间要分配到这些资源，不能为同一次省掉的 prefill 多次记功。沿用 T_D=100 ms 的构造算例，未来节省 40 ms、执行概率 0.5、一秒后可运行，贡献为 0.1；九秒后才可运行，贡献降到 0.02。可见这不是简单数“还有几个后继会用到”，而是对近期、较确定的复用给更高权重。

    资源机会成本比较加入候选前后潜在逐出对象的恢复成本差，除以 T_D，再截到 [-1,1]。负值在模型中是可能的，因为新计划也可能降低预计恢复成本，不能想当然只保留非负部分。预测依据来自离线 profiling、当前驻留和可见工作流；论文没有声称准确知道未来。

    最后，分别把节点值和表示值归一到 [0.5,1]，相乘形成联合分数：

    St(s,v,m)=N[0.5,1](Vnode) N[0.5,1](Vrepr).(10)S_t(s,v,m)=N_{[0.5,1]}(V^{node})\,N_{[0.5,1]}(V^{repr}). \tag{10}St​(s,v,m)=N[0.5,1]​(Vnode)N[0.5,1]​(Vrepr).(10)

    每个因子最多在自己的区间里改变两倍，乘积位于 [0.25,1]。这能缓和单一项数值尺度压倒另一项的问题，却不证明策略最优或绝不饥饿。正文给了归一区间，没有完整列出所有退化情况，例如原始分数全相同或只有一个候选时怎样处理。笔记保留这个未说明项，不把自行猜测的细节写成作者方法。

    图 4：自绘算例，并非论文测量。A 的节点值为 1、表示值为 0.5；B 分别为 0.75 和 1，联合分数因此从偏好 A 变成偏好 B。

    请求优先会先锁定 A；联合排序得到 A=0.50、B=0.75，于是更愿意先用能即时复用的 B。但评分只能在合法、可容纳的候选中比较。它不能越过前驱、使用其他 adapter 的 KV，也不能取消动态显存预留。等待超过 60 秒的请求还有额外优先规则，同样受依赖和资源限制。这里的“60 秒优先”与进度公式中的“60 秒尺度”是两项规则，不能合成一个延迟保证。

    7. 两个算法：先做计划，再原子准入

    论文算法 1 的顺序很清楚：更新工作流与资源状态，构造可行的请求—表示组合，计算分数，然后在本轮开始时排一次序。某个请求的第一个可行组合进入计划后，这个请求的其他表示就被跳过。随着计划增长，会更新剩余显存投影；实际资源逐出留到批次最终准入阶段处理。本轮内部不因每次新增候选而重新排所有分数。[1，第 4.3 节]

    算法 1: 请求与表示的联合选择

    以下编号伪代码是对论文算法 1 的解释性重述。归一与成本预测仍作为论文抽象操作，不补写未说明的细节。

    1. 更新可见 DAG、运行批次和资源状态。
2. 收集依赖已满足、分支条件成立的请求。
3. 为每个请求枚举通过行为资格的表示。
4. 过滤硬性不可行组合，并计算联合分数。
5. 排序一次，同时应用超时等待请求的优先规则。
6. 建立空的暂定批次计划。
7. 按顺序检查每个组合：
   a. 同一请求已入计划则跳过。
   b. 不实际逐出资源，投影合并批次的显存。
   c. 若可行，加入并更新资源投影。
   d. 批次已满则停止。
8. 计划非空时调用算法 2，最终准入。
9. 否则仅在安全空闲点考虑预取。
10. 返回计划；最终准入失败则返回空计划。

    步骤 7 允许后面的可容纳请求绕过前面放不下的大请求，这能避免显存明明还有余量却让 GPU 闲置。但对公平性要谨慎：一个大的、资源冲突持续存在的请求，可能一轮轮被绕过。即使它超过 60 秒得到排序优先，也不能突破硬资源限制，因此不能声称系统保证在 60 秒内启动所有请求。

    算法 2: 批次资源准入与逐出

    第二个算法把“打算做什么”变成真正的共享资源修改。同一个对象被几个请求引用时，先取并集，只计一次字节数。

    1. 求暂定批次所需资源的去重并集。
2. 投影运行请求与新请求合并后的动态 KV 峰值。
3. 若合并需求硬性不可容纳，拒绝。
4. 计算还需腾出的字节数。
5. 保护运行中持有、正在加载及本计划需要的资源。
6. 按单位字节保留价值对其余资源排序。
7. 选足逐出对象，再剔除多余的被选对象。
8. 若仍腾不够空间，不改变资源状态并拒绝。
9. 原子提交显存预留与最终逐出集合。
10. 返回成功标志与逐出对象集合。

    先投影、后提交的意义在于失败不应留下半套资源状态。若检查到一半就逐出缓存，后来又发现批次放不下，会白白破坏原有复用，还可能让预留和真实驻留不一致。论文以 AtomicReserveWithEvict 表达这个边界，但没有给出并发正确性的形式化证明。我因此解释它要维护的关系，而不自行宣称某种锁或事务细节已被验证。

    关于 ProjectAdmit，正文说它在暂定阶段“不逐出驻留资源”，而 CommitAdmission 才确定实际逐出对象。我把前者理解为无破坏副作用的资源投影，并保留这两阶段；没有把文字中仍需澄清的条件替换成猜测实现。预取仅在没有运行批次且等待队列为空时发生，本次实验没有触发，所以它不是已测性能收益的来源。

    8. 显存峰值怎样计算

    Resource Manager 在运行时预算内同时容纳可复用资源和随解码增长的动态 KV。模型权重、固定工作区不属于这里的动态划分。运行批次与新批次共享的缓存对象只算一次，合并后需满足

    Mkeep+Mnew+bKVTpeak≤Bruntime.(11)M_{keep}+M_{new}+b_{KV}T_{peak}\le B_{runtime}. \tag{11}Mkeep​+Mnew​+bKV​Tpeak​≤Bruntime​.(11)

    其中 b_KV 是每 token 动态 KV 的字节数。对层数 L、KV head 数 h_KV、head 维度 d、每标量 b 字节的普通 attention 模型，同时存 K 与 V 得到

    bKV=2LhKVdb.(12)b_{KV}=2Lh_{KV}db. \tag{12}bKV​=2LhKV​db.(12)

    论文的 Llama-2 设置每 token 为 0.5 MiB。因此 16000 token-equivalent 的运行预算是 8000 MiB。Helium 分到 14000 等价 token，即 7000 MiB，因为不同框架的静态占用不同；作者试图把整张 GPU 的峰值对齐到 22000 MiB，允许 3% 的运行波动。这里对齐的是整卡上限，不是所有系统具有相同数量的可用动态 token。阅读 baseline 比较时应保留这个口径。

    附录 A.3 的峰值估计也比“当前用了多少”更细。把批次请求按剩余输出预算从大到小排列，记已有动态 token 为 u_i、剩余输出为 o_i。在第 k 长请求即将完成的事件处，前 k 个请求还活着，每个又生成了 o_k 个 token，而更短请求已经释放状态。此时的占用是前 k 个 u_i 之和，再加 k 乘 o_k。枚举所有完成事件得到

    Tdecode=max⁡1≤k≤n(∑i=1kui+kok).(13)T_{decode}=\max_{1\le k\le n}\left(\sum_{i=1}^{k}u_i+k o_k\right). \tag{13}Tdecode​=1≤k≤nmax​(i=1∑k​ui​+kok​).(13)

    这个推导采用估计器对应的同步解码进度与释放规则。请求并非都在各自峰值同时存在，所以直接把每个请求的独立最大值相加会过于保守。另一方面，只看当前占用又可能漏掉未来输出增长。论文还检查 prefill 阶段；上式只解决解码部分，不代表完整准入只需这一项。

    图 5：依据原文公式 A4 自绘算例。已有动态 token 为 (10,40,50)，剩余输出为 (30,10,5)；请求结束后释放状态，算例不是 GPU 实测。

    代入三次事件，分别得到 40、70、115 token，所以批次峰值是 115。当前占用是 100，会少预留 15；逐请求独立峰值相加则是 145，会多预留 30。按 0.5 MiB/token 换算，当前、真正峰值与独立峰值和分别为 50、57.5、72.5 MiB。这个小算例也提醒我：在显存紧张时，过度保守与不安全的低估，都可能改变批次选择，差别不仅是一个计数细节。

    但“输出预算”还需要明确。如果它是平均预测长度，就不是严格的上界；真实输出更长可能突破投影。生产化改进需要强制生成上限、误差预留，或者输出超出预测后的明确处理方式。把公式 A4 解释为其假设下的规划工具是合理的，把它说成任意执行环境下绝不 OOM 的证明则没有依据。

    9. 逐出策略：保留一字节值多少钱

    不同大小的 adapter 与 KV 不能只按“最近用没用”比较。论文定义资源 i 的保留密度：

    Di=CiBi(1+ri)(1+min⁡(4,hi)4).(14)D_i=\frac{C_i}{B_i}(1+r_i)\left(1+\frac{\min(4,h_i)}4\right). \tag{14}Di​=Bi​Ci​​(1+ri​)(1+4min(4,hi​)​).(14)

    C_i 是保留该对象能省掉的恢复时间，B_i 是字节数；r_i 在 [0,1] 内，利用当前候选排序估计未来需求。h_i 记录逐出后 10 秒内又发生重建的次数，相关历史保留 60 秒。未来需求因子最多放大两倍，近期重建因子也最多两倍，因此合起来最多把基础时间/字节比放大四倍。

    考虑一个自构造例子：adapter 重新加载需 20 ms，占 40 MiB，基础密度为 0.5 ms/MiB；若未来需求最高，而且已有至少四次近期重建，最终分数为 2。另一个 KV 占 100 MiB、重建 60 ms，没有需求和重建加成，分数是 0.6。这一轮更应保留前者，因为在假设的工作流预测下，它更可能马上又要回来。但若预测错误，这个策略也可能把过时对象留得太久。

    逐出时先按低保留值选到足够空间，再从已选对象中按较高价值优先回看：如果不逐出它，剩余对象仍足够，就将它移出逐出集合。这样可以减少变长资源导致的过量逐出。不过这是启发式，不能保证找到最好的子集。例如需要腾出 6 MiB，依次有两个密度较低的 4-MiB 对象，再有一个密度稍高的 6-MiB 对象，第一遍可能先选中 4+4；回看时单独撤掉任何一个都不够，因此仍逐出 8 MiB。后面的 6-MiB 替代没有被搜索。这个例子说明算法边界，不是论文测量中已观察到的错误。

    被逐出的 adapter 会转到 CPU 内存，下次重新加载；KV 则直接丢弃，下次重建。作者在测试条件下发现重算 KV 比从 CPU 搬回 GPU 更快，才采用这种不对称处理。换设备、总线、上下文长度或缓存层次后，结论可能变化，不能把它推广成所有系统都应该丢弃 KV。运行中、加载中和计划必需对象仍受保护，再低的保留密度也不能直接把它们驱逐。

    10. 怎样读完整系统的实验结果

    主实验使用单张 24-GB RTX 3090、Llama-2-7B-Chat、128 GB 主存，以及配置 52 个逻辑核的 Intel 8171M。RePrism 建立在 S-LoRA 上。S-LoRA 与 Chameleon 支持 Direct/Adapter，但不使用 DAG；SGLang 支持 Direct/KV，也不使用 DAG；Helium 支持 Direct/KV 且使用工作流；RePrism 同时用四种表示与 DAG。这些能力差异本来就是完整系统对比的一部分。[1，表 1]

    动态工作负载混合 CI 修复、事件响应和多文档分析。会话在 200 秒内按泊松过程到达，速率从每秒 0.7 到 1.9 个；随后停止新增并跑到全部完成。客户端最多保留 128 个 in-flight 请求，更多 ready 请求在客户端排队；adapter 按指数 1.1 的 Zipf 分布分配。这样的合成构造能控制复用与依赖，也意味着这些结果不是从完整生产 trace 原样重放得来。

    图 6：原论文 Figure 8，裁自 PDF 第 9 页，数据未修改。Helium 没有逐请求首 token 时间戳，因此图中没有它的 TTFT 曲线。

    吞吐以“所有完成请求数/发送开始至全部排空的总时长”计算，不仅看 200 秒发送窗口。SCT 从计划的会话到达时刻开始；TTFT 从请求实际提交开始，因此更早在客户端 ready 队列中的等待可能不进入 TTFT。若只看首 token 指标，把等待移到客户端也能显得更快；SCT 能更直接约束这种口径问题。论文把两者一起报告，是理解收益的重要条件。

    在每秒 1.8 会话处，RePrism 约为每秒 14 请求，是 S-LoRA 的 1.37 倍，P95 SCT 缩短 4.10 倍。后者表示新延迟约为旧值的 1/4.10，也就是降低约 75.6%，不是“降低 410%”。在每秒 1.7 会话处，相对 S-LoRA、SGLang 的 P50 TTFT 缩短倍数分别为 9.40、18.01。它们与另一个受控实验中的“平均 TTFT 缩短 5.26 倍”具有不同统计口径，不能拼接为同一项观察。

    受控工作负载包含 96 个会话、1056 个请求，使用 CI 修复图。策略比较采用 shape=0.5 的 gamma 到达间隔，目标速率每秒 0.2 会话；默认 P/R/Q/输出长度分别为 1152/256/256/128，提供 32 个 rank-16 adapter。资源压力实验则同时释放会话。图中结果平均五次运行，这有助于稳定测量，但若要评价每个小幅改善的置信程度，还需要更完整的原始波动与区间。

    11. 消融告诉我们收益来自哪里

    我更重视 RF 对照：它使用相同节点分数、后端、表示排序与资源管理，只是先把请求排好，再选表示；RF-FIFO 则按到达顺序。这样才较接近单独研究“联合”决策。不同 R、Q 长度下，吞吐提高最多约 5%。当 R=Q=256 时，相对 RF-FIFO 与 RF 的平均 SCT 缩短倍数分别为 1.35、1.14；资格覆盖率实验在 q=50% 处给出的精确百分比为吞吐增加 2.7%、平均 SCT 降低 12.3%。取整的倍数与百分比可以相容，但不是同一个精度的数。

    另一个消融逐步增加可用表示。仅 Direct 的 RP-D 比 S-LoRA 吞吐低 27%；加入 Adapter 或 KV 后接近它；再允许 Direct、Adapter、KV 后超过它，并把平均 SCT 缩短超过两倍。完整 RePrism 的 5.26 倍平均 TTFT 改善，说明表示菜单与复用能力很重要，不能全部记在联合乘积分数的账上。

    逐出实验中，RePrism、RP-LRU、用完即丢的 RP-SE 与 S-LoRA 的平均 SCT 分别为 82.5、85.6、129.9、196.5 秒；平均 TTFT 为 2.5、2.8、6.3、13.2 秒。相对 LRU 的进一步改善较小，而“根本不保留复用状态”损失更大。图上只保留一位小数，用这些标签算出的比值和作者用未舍入数据算出的比值略有不同，不宜把这种差异当作矛盾。

    12. 资格覆盖、可见范围与调度开销

    覆盖率 q 指不同提示中多少可以使用 Adapter/Hybrid，不是请求比例，更不是 token 比例。在 Zipf 访问下，若恰好是高频提示通过，半数提示也可能覆盖大部分请求；若只合格冷门提示，反过来可能覆盖很少。论文从 q=0% 到 100%，RePrism 吞吐从 1.56 提高到 2.16 请求/秒，平均 SCT 从 206.85 降到 51.87 秒，分别约是增加 38.5% 和下降 74.9%。

    联合评分相对 RF 的边际收益却在混合资格时最大。q=100% 时平均 SCT 改善最多 1%；q=0% 时还略差于 RF。这与设计动机一致：不是任何时候都需要很复杂的联合选择，当不同 ready 请求的执行选项差异最大时，才最可能重排出更好的结果。不能把“覆盖越高系统绝对表现越好”和“联合评分相对收益越高”混为一谈。

    图 8：据第 5.5.2、5.5.3 节明确给出的数值重绘。两面板来自不同控制实验，不将跨面板绝对值当作一个完整因子实验比较。

    Full 给调度器看完整的已提交工作流，Next-hop 只看 ready 节点及直接后继，Frontier 仅看 ready 节点。三种设置仍用完整图保证依赖与释放请求，因此 Frontier 测试的是调度信息减少，不是让系统自己发现未知依赖。Full 到 Frontier，吞吐从 1.97 降到 1.89，平均 SCT 从 82.48 增到 108.09 秒，约为吞吐减少 4.1%、SCT 增加 31.0%。相对请求优先策略的优势仍在，但能否看到未来确实影响结果。

    跨模型实验在 Llama-2、Llama-3-8B-Instruct、Qwen-2.5-7B-Instruct 上的吞吐倍数为 1.10、1.30、1.31，平均 SCT 缩短倍数均为 1.32。运行时预算分别是 8000、5875、5687.5 MiB，以对齐整卡上限。它说明收益不只出现在一个架构上，但仍然是不同 KV 几何和静态开销下的单卡测试，并没有变成多机系统的验证。

    13. 局限与可复算的范围

    论文把小规模语义验证和较大范围的性能评估组合在一起：前者展示提示可以在某个任务上内化，后者借助张量形状相同的代理 adapter 研究调度。这个安排有清楚的实验目的，也留下证据间隙。一个 rank-16 对照的运行时间接近，不能证明其他提示、模型、秩及会话中的生成输出都满足同样行为要求。

    设计工作负载能控制 prompt-to-adapter 映射、依赖、长度、复用和分支，因而便于消融；真实 agent 则可能有动态扩展的图、随机工具延迟、更新过的提示，以及随模型输出变化的路径。特别是近似表示可能改变 R 的文本，进而改变后续分支、输出长度和复用机会。使用 proxy 的性能负载没有同时证明这个闭环中的语义结果和资源轨迹保持不变。

    单卡也是范围边界。迁移到张量并行、流水线并行、prefill/decode 分离或集群，会引入副本位置、传输、通信和一致性代价。作者指出可以扩展，但没有报告这些设置的实验。同样，离线 adapter 训练、提示更新后的失效、重新资格测试，都需要在更长时间范围里摊销，不能只用在线 residual cache 的构建成本替代。

    评分依赖 profiling、输出预算与分支概率，候选集合归一还会引入上下文效应。动态峰值估计使用特定解码模型；等待优先也不能帮助一个硬性不可容纳的请求。这些启发式没有自动给出最优性、公平性或延迟上界。明确这些边界，才能知道哪些新实验会真正扩大结论。

    本次能独立核对的是算术与解释：缓存回本命中次数、MiB 换算、联合分数反转、动态 KV 完成事件峰值、表 2 相对成本、各倍数与百分比，以及后文的小样本区间。我没有据此声称复现吞吐。未来若进行系统实验复现，需要完整工作负载及到达序列、长度是否含模板、资格映射、整卡与运行预算、客户端释放规则、排空区间，以及 SCT/TTFT 各自的时间戳定义。

    一个可复算的准入场景

    为了把资源并集、峰值投影和最终准入连起来，我再构造一个缩小预算的例子。它不是论文实验配置。设运行时预算为 160 MiB，已经必须保留的共享 adapter 占 64 MiB，新计划需要的残余缓存并集占 32 MiB；动态 KV 使用前面算例的 115-token 峰值，每 token 为 0.5 MiB。那么合并需求是 64+32+57.5=153.5 MiB，还剩 6.5 MiB。先不考虑额外工作区时，这个资源计划可以放下。

    假设两个请求都使用那个 64-MiB adapter，正确做法仍是只计一次。若每个请求各加一遍，把同一对象重复收费，需求会被误算成 217.5 MiB，系统就可能拒绝本来可运行的批次。相反，若用当前动态占用的 100 token 代替峰值，需求会被算成 146 MiB，虚增 7.5 MiB 余量，随后加入别的请求就可能超预算。共享去重防止过度保守，峰值检查防止过度乐观，两者必须同时成立。

    再看保护规则。若另一个候选需要额外 16 MiB，原计划的 6.5 MiB 余量已不够。评分再高，也不能直接把正在运行请求所持有的 64-MiB adapter 逐出；管理器只能检查其余可逐出对象是否能补足 9.5 MiB，或者拒绝这次合并。若有两个未保护的 8-MiB 对象，选中两个能腾出 16 MiB，但只撤回其中一个就不够，这也解释了为何“回看删掉多余逐出对象”仍可能留下超过需求的释放量。

    最后，预算安全依赖预测的性质。如果实际动态峰值变成 129 token，同一计划会需要 160.5 MiB，超出上限 0.5 MiB。对这套构造数字，14 个 token 的误差就足以翻转准入判断。这个例子既不说明论文运行发生了越界，也不代替输出长度分布的测量；它只是把“预期长度不一定是上界”变成一个可手算的失败边界。后续实验应记录预测余量与真实峰值，而不只记录平均显存。

    14. 批判性分析：先约束优化目标的质量

    我最想加强的是行为准入的统计依据。rank 16 的 0.917 与 24 例中 22 例通过相符。若暂按独立伯努利试验处理，常见 Wilson 区间为

    代入 22/24，约得到 [0.742,0.977]。这是我自行计算的说明，不是作者报告的置信区间，也不是否定观察到的通过率。它说明：一个样本点估计高于 0.85，并不等于有充分证据说明未来总体通过率高于 0.85。如果用同一批资格样本反复挑选最低可过的 rank，还可能有自适应选择带来的乐观偏差；这个简单区间并没有修正它。

    具体改进可以从三件事开始。第一，把 rank 开发集与最终锁定的资格集分开；第二，按规则类型、状态组合与新残余上下文分层看失败，而不只看平均值；第三，只有应用选定的置信下界满足要求，才启用近似路径。对严格约束的任务，保持 Direct/KV 可能更合适；对接受一定近似的任务，应明确接受什么。只有在行为合同清楚之后，性能比较才有稳定分母。

    第二个改进是把评价推进到质量约束下的会话吞吐。设观察时间 T，完成 N 个会话，pass_s 表示最终行为通过，slo_s 表示在约定期限内完成。我建议报告

    Gvalid=1T∑s=1N1{passs}1{slos}.(16)G_{valid}=\frac1T\sum_{s=1}^{N}\mathbf 1\{pass_s\}\mathbf 1\{slo_s\}. \tag{16}Gvalid​=T1​s=1∑N​1{passs​}1{slos​}.(16)

    这个指标是我的建议，不是本文实验结果。它统计每秒完成多少有效且及时的完整会话，可以显露快速近似路径改变后继输出、触发重试或走错分支的情况。下一组有价值的对照应保留真实任务输入，记录模型实际生成的 R 和分支，并分别测试 exact-only 与带资格约束的表示菜单。只固定 proxy 性能轨迹，还回答不了这个问题。

    第三，要主动扰动预测，而不是只在校准良好的成本模型下测试。可以系统增加 T_m、输出长度、工具等待与分支概率的误差，观察 OOM 恢复、请求被绕过的年龄、缓存反复重建、尾部 SCT 和无效工作。显存预留应明确使用硬上界还是校准分位数，并规定实际输出超出预测后的回退。否则一个良好平均点可能掩盖很脆弱的边界。

    最后，调度计算本身值得设预算。附录的 62.45-ms 中位数提示我们，可以比较有界候选集合、删除每请求明显劣势的表示、复用未变化的评分分量，以及只在相关状态变化时重算。每种办法也可能损失策略质量或沿用过时预测，因此应以有效会话吞吐和尾延迟评估收益，不能只追求 CPU tick 更短。我愿意保留 RePrism 的联合接口，但希望把它依赖的语义、预测与控制成本一起放进目标里。

    15. 结论

    RePrism 的核心不是某一种表示在所有环境里都更好，而是请求顺序与表示选择彼此影响。一个调用现在该不该运行，取决于它能用什么表示；一种表示值不值得建立，又取决于哪些调用接下来会运行。论文用联合评分、动态显存峰值投影和原子准入，把这层关系落到了一个可以测量的单卡服务系统上。

    我认为它最有启发的场景，是表示资格混合、复用关系可见而且资源竞争真实存在的时候。实验也给出清楚边界：同质环境里最佳固定表示可能更快；联合评分本身的增量远小于完整系统的最大加速；候选过多时 CPU 调度代价不低。继续推进这条路线，我会优先补强行为资格的证据，并用真实生成驱动的、质量约束下的会话评估检验收益。
