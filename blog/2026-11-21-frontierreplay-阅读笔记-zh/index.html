    FrontierReplay 阅读笔记：不切开前向，也能保存精确的混合模型前缀状态

    笔记日期： 2026-11-21
    作者： Zhongzhu Zhou
    论文题名： FrontierReplay: Split-Free Exact Prefix Caching for Hybrid Language Models
    论文作者： Zekun Wang, Yizhuo Wang
    arXiv： 2611.26020
    版本与日期： v1，2026-11-19

    1. 先把问题分成三件事

    读完这篇论文，我认为最值得记住的并不是“增加一种检查点”，而是把三个问题拆开：未来的共享前缀会停在哪里，怎样得到那个位置的递归状态，以及这个状态是否值得继续占用显存。三个问题要一起解决。检查点放得更密，如果每保存一次都要增加调度迭代，端到端服务仍可能变慢；生成检查点再便宜，如果保留的是过时祖先，也帮不到下一轮会话。

    混合模型同时有注意力层与递归层。注意力 KV 像一串按 token 保存的历史，可以在页边界截断。递归状态更像不断覆盖的工作寄存器：处理完第 2,000 个 token 的矩阵，并不包含一个可直接切出来的“第 1,984 个 token 的矩阵”。如果下一次请求恰好复用到 1,984，就要有那个位置的状态副本，而且副本还应包括短卷积的历史缓冲。

    FrontierReplay 的思路是先让普通 prefill 向前跑，同时记录一小段递归层真正读到的输入；等整段前向结束，再从旧锚点只重放状态更新，补出中间位置的检查点。重放跳过注意力、MLP 和递归层的逐 token 输出，不为检查点额外切开 prefill。未来命中后直接复制这个精确状态即可。

    本笔记读完 v1 的 15 页，包括 12 图、4 表与参考文献；这一版没有单列附录。文中的模型性能全部来自作者报告，公式展开、显存估算和十进制舍入例子是我为理解方法做的独立复算，不是重新运行模型或服务实验。另需说明：我也是本文引用的相关工作 FlashState 的共同作者，论文中将它写作 FlashStates。下文会把作者适配的导出比较对象与原完整系统区分清楚。

    先给出一个带边界的判断：在主要的八个 9B/7B 模型与负载锚点，本文方法相对其 vLLM 设置获得 1.11–4.26 倍 goodput；但另一个 34B 文档问答点只有 0.76 倍，即使首 token 延迟已经下降。后一结果不是无关细节，而是理解整个方案的关键[1，§6]。

    2. 前置知识：KV 能命中，状态未必能恢复

    两套历史必须在同一位置接上

    设注意力 KV 仍连续驻留到位置 bbb，C\mathcal CC 是已经完成写入、且完整 KV 前缀仍可达的递归检查点集合。真正能恢复的位置是

    c⋆=max⁡{c∈C:c≤b},Δ=b−c⋆.(1)c^{\star}=\max\{c\in\mathcal C:c\le b\},\qquad \Delta=b-c^{\star}. \tag{1}c⋆=max{c∈C:c≤b},Δ=b−c⋆.(1)

    这里的 Δ\DeltaΔ 是“KV 虽然还在，但因缺少相应递归状态而无法直接复用”的 token 数。没有更深的状态时，可以回到位置零的初始状态。这是我对论文查找规则的简写，并非作者新增的定理。一个位于 bbb 之后的检查点不能补回丢失的注意力 KV；反过来，保留到 bbb 的 KV 也不能单独倒推出此前任意位置的递归状态。两套历史必须相交。

    图 1：论文 Fig. 2。Wang 与 Wang 的原图[1]。橙色区间虽然有 KV，却只能从较早的状态网格重新经过全模型计算。这里展示的是粒度不匹配，并非 FrontierReplay 引入了一种新的有损近似。

    论文采用 16-token 注意力页。其 vLLM align 网格在 Qwen3.5-9B 上是 528 token，在 Falcon-H1-7B 上是 1,568 token，理由是让一个状态的字节数与一组注意力页对应。举个整数例子：共享到第 2,000 个 token，528 网格只能停在 1,584，还要重算 416；1,568 网格则要重算 432。这只是帮助理解的例子，实际收益取决于真实前缀长度分布。即使把检查点细到 16-token 页，逻辑边界末尾不足一页的部分也仍需处理。

    token 工作量与调度步数不是同一个量

    Prefill 处理输入，decode 逐步产生输出。连续批处理在一次次调度迭代里混合两类请求；chunked prefill 又限制每轮给长输入多少 token，以免长 prompt 阻塞别人的 decode。为了在中间存状态而提前结束一个 chunk，即使没有多算 token，也可能多出一个需要重新排队的短尾块。

    作者用“检查点位置相同、prefill token 数相同”的比较隔离这个代价。聊天、工具和树搜索轨迹中，切块让 prefill 步数变为 1.44–1.86 倍；文档问答中的目标较稀疏，增加到 1.05–1.09 倍[1，§3.2]。因此不能把性能差异全部归到 FLOPs。额外调度步、短块执行和其他请求的共享时间线也在起作用。

    图 2：论文 Fig. 3。原图[1]。重放确实消耗 GPU 时间；split-free 的含义是不因保存检查点额外切开前向，普通的 chunked prefill 并没有消失。

    Qwen 是 Gated DeltaNet 与注意力交错，Falcon 则在混合块内并行放递归和注意力头。两种结构都要求记录每一层的真实输入。只保存第一层，再让后面各层重新生成输入，就会重新引入原本要省掉的大量网络计算。

    3. 状态为什么可以单独重放

    从两步、三步展开看 Mamba-2

    对一个 head，论文使用的简化 Mamba-2 递推是

    Sj=αjSj−1+Bj,Bj=vjkj⊤,oj=Sjqj.(2)S_j=\alpha_jS_{j-1}+B_j,\qquad B_j=v_jk_j^{\top},\qquad o_j=S_jq_j. \tag{2}Sj​=αj​Sj−1​+Bj​,Bj​=vj​kj⊤​,oj​=Sj​qj​.(2)

    SjS_jSj​ 的形状为 dv×dkd_v\times d_kdv​×dk​，vjv_jvj​ 有 dvd_vdv​ 维，kj,qjk_j,q_jkj​,qj​ 有 dkd_kdk​ 维，αj\alpha_jαj​ 是零到一之间的衰减系数。这一节把保存的起点记为 S0S_0S0​，所以 jjj 是相对锚点的索引，真实 token 位置还要加上起点。原始前向需要输出 ojo_joj​，但如果目标只是后面的状态，就不必重新生成每一个输出。

    不要一开始就背紧凑公式，先逐步代入：

    S1=α1S0+B1,S2=α2α1S0+α2B1+B2,S3=α3α2α1S0+α3α2B1+α3B2+B3.(3)\begin{aligned} S_1&=\alpha_1S_0+B_1,\\ S_2&=\alpha_2\alpha_1S_0+\alpha_2B_1+B_2,\\ S_3&=\alpha_3\alpha_2\alpha_1S_0 +\alpha_3\alpha_2B_1+\alpha_3B_2+B_3. \end{aligned} \tag{3}S1​S2​S3​​=α1​S0​+B1​,=α2​α1​S0​+α2​B1​+B2​,=α3​α2​α1​S0​+α3​α2​B1​+α3​B2​+B3​.​(3)

    每一次写入都会经过后续 token 的衰减，而起始状态经过所有衰减。令 γi:h=∏ℓ=ihαℓ\gamma_{i:h}=\prod_{\ell=i}^{h}\alpha_\ellγi:h​=∏ℓ=ih​αℓ​，空乘积取一，就得到

    Sh=γ1:hS0+∑j=1hγj+1:hvjkj⊤.(4)S_h=\gamma_{1:h}S_0+ \sum_{j=1}^{h}\gamma_{j+1:h}v_jk_j^{\top}. \tag{4}Sh​=γ1:h​S0​+j=1∑h​γj+1:h​vj​kj⊤​.(4)

    它对应论文 Eq. (2)，只是省略了绝对起点下标。公式告诉我们一层真正需要保存什么：正确的起始状态、对应窗口中的衰减、key 与 value。已经记录好这些量以后，重建最终矩阵不需要再跑注意力、MLP 或逐 token 输出投影。但短卷积缓冲也是状态的一部分，仅记录这个矩阵递推不等于完整保存了恢复所需信息。

    GDN 不能把矩阵乘积当标量衰减

    Gated DeltaNet 多了一次沿 key 方向的擦除，论文的式子可整理为

    Sj=Sj−1Aj+Bj,Aj=αj(I−βjkjkj⊤),Bj=βjvjkj⊤.(5)S_j=S_{j-1}A_j+B_j,\quad A_j=\alpha_j(I-\beta_jk_jk_j^{\top}),\quad B_j=\beta_jv_jk_j^{\top}. \tag{5}Sj​=Sj−1​Aj​+Bj​,Aj​=αj​(I−βj​kj​kj⊤​),Bj​=βj​vj​kj⊤​.(5)

    其中 βj\beta_jβj​ 控制写入强度，III 是单位矩阵。先调整旧状态中与 key 有关的分量，再写入新关联。仍然是仿射递推，但现在右侧作用的是矩阵。按时间顺序展开：

    Sh=S0A1A2⋯Ah+∑j=1hBjAj+1⋯Ah.(6)S_h=S_0A_1A_2\cdots A_h+ \sum_{j=1}^{h}B_jA_{j+1}\cdots A_h. \tag{6}Sh​=S0​A1​A2​⋯Ah​+j=1∑h​Bj​Aj+1​⋯Ah​.(6)

    例如三步以后，第一次写入对应 B1A2A3B_1A_2A_3B1​A2​A3​。不能把它改成 A3A2B1A_3A_2B_1A3​A2​B1​：有些调换连形状都不成立，即使形状碰巧允许，矩阵也通常不交换。论文用分块 WY 表示处理这些秩一更新的乘积，并不是把 GDN 直接替换成式（4）里的标量 γ\gammaγ。

    跨层并行重放看上去容易让人困惑：第二层不是依赖第一层的输出吗？在真实前向里确实如此，但日志已经把每一层实际收到的输入记录下来，那条依赖已经由真实前向求解过。事后的重放只用各层自己的日志推进状态，不再重新求整条层间计算。这也是为什么日志不能用另一段 prompt、另一模型或另一模板产生的隐藏量替代。

    我用独立小矩阵复算了式（4）与式（6），并验证把 GDN 乘积反过来会改变答案。它只检查本笔记的数学展开，没有验证作者程序，也没有运行模型。这个区分很重要：代数成立说明保存信息足够，实际精确性还要处理下一节的数值路径。

    4. 精确性还包括何时舍入

    前面的代数在实数域成立。实际 kernel 会在 chunk 或 decode 边界把状态写回存储精度，重新分组计算可能改变舍入轨迹。FrontierReplay 在日志页里用 bitmask 记录原始前向的这些边界，重放时在同样位置分段并舍入[1，§4.2]。

    设 FjF_jFj​ 是理想更新，RjR_jRj​ 在规定位置做舍入，其余位置取恒等映射。希望恢复的数值过程是

    S^h=(Rh∘Fh)∘⋯∘(R1∘F1)(S^0).(7)\widehat S_h=(R_h\circ F_h)\circ\cdots\circ (R_1\circ F_1)(\widehat S_0). \tag{7}Sh​=(Rh​∘Fh​)∘⋯∘(R1​∘F1​)(S0​).(7)

    这通常不等于先按实数闭式算到底，再只做一次最终舍入。知道状态使用 FP32 还是 BF16，也不足以描述它的全部数值历史；原来在哪里分块，同样可能影响最终保存的状态。

    图 3：Zhongzhu Zhou 自绘的数学说明。从 1 出发，每次做 S←0.9S+0.06S\leftarrow0.9S+0.06S←0.9S+0.06，每 token 四舍五入到 0.1 得到最终 1.0；两步后才舍入得到 0.9。这不是 BF16 误差测试，也不是模型测量。

    论文一处报告重放状态与对应的未中断前向状态逐比特相同，另一处又报告服务测试中只有 92% 的贪心输出逐 token 相同。这两句话并不矛盾。前者固定了所比较的前向与日志；后者允许动态并发批形状发生变化，作者将剩余差异归因于接近并列 logits 的浮点非结合性，并报告没有非近似并列位置的 argmax 翻转[1，§3.3、§6.3]。

    因此我把三个层次分开：固定输入和舍入历史后能否恢复状态；改变 batching 后 logits 是否会有浮点扰动；最终任务分数是否接近。相对任务分数 100.2–100.3% 不代表模型能力被提高了，作者给出的 p≥0.34p\ge0.34p≥0.34 更适合支持该测试下接近基线的判断，不能代替逐字符串一致性的证明。

    Falcon 还有 1,568-token 的恢复下限。作者不在更短位置放置或恢复状态，原因是 BF16 Mamba-2 的早期状态在衰减尚未充分消除初始历史影响之前，对舍入更敏感。于是“16-token 粒度”必须附带条件：有正确锚点、符合精度约束、有日志资源，才谈得上细粒度精确重建。它不是所有位置都无条件可用。

    近似 suffix replay 则主动舍弃远处历史，从短尾部重建。它可能适合容许误差的任务，但提供的是另一种语义契约。不能仅凭衰减系数小就认定遗忘总是无害，因为 key、门控和长上下文任务可能恰好依赖被尾部近似删除的那部分信息。

    5. 生成检查点的完整协议

    图 4：论文 Fig. 5。原架构图[1]。输入日志属于暂存资源，KV 与递归检查点属于可供未来命中的资源。虚线代表控制关系，不等于在所有 GPU 工作之间插入全局同步。

    调度器先找到最长的驻留 KV 前缀，再找这段前缀上最深的已完成检查点。恢复时把状态复制到请求的工作槽，保存的副本仍然要留着，因为接下来的真实前向会覆盖工作槽。等前向结束再拿这个被覆盖的工作槽当重放起点，就已经不是原来的锚点了。论文因此给保存状态加租约，在依赖它的重放结束前禁止物理回收。

    目标位置位于即将执行的 chunk 内。日志复制从 chunk 起点到最深目标的每层递归输入，按 16-token 页管理，兄弟分支各自拥有日志。它们可以共享不可变的历史状态，却不能共享会继续写入的暂存页。否则一条分支可能覆盖另一条的投影输入，得到一个形状看似正确、内容却属于错误路径的检查点。

    算法 1. 生成并公开精确目标状态

    下面按论文 §4.1–§4.2 与 §4.6 整理成编号伪代码，目的是解释依赖顺序。

    1. 找到 KV 驻留终点 b，以及不超过 b 的最深已完成检查点 c。
2. 租用 c，将它复制到请求工作状态，保护原副本。
3. 为下一个普通 prefill chunk 规划有序目标位置。
4. 准备 chunk 起点锚点、目标槽和请求私有日志页。
5. 目标距起点超过 1024 token 时，预先改用精确边界切块。
6. 若缺少活锚点或日志空间，准备阶段也退回精确切块。
7. 执行完整 chunk，记录每层真实输入、卷积信息和舍入边界。
8. 在同一 CUDA stream 上推进状态，只计算递推并保存各目标。
9. 记录完成事件；事件未完成之前，不把目标交给未来查找。
10. 事件完成后公开成功目标；失败或中断的半成品不公开。
11. 释放暂存日志与已结束的租约，进入下一轮保留决策。

    这里有两种不同的顺序。GPU 上，真实前向和重放进入同一 stream，保证日志先写后读；主机索引上，未来查找必须等 GPU 完成事件退休后，才看得见检查点。无需主机阻塞等待，不等于无需知道结果什么时候真正完成。论文把这两件事分开，是避免异步正确性漏洞的重要细节。

    资源释放也一样。一个状态在保留策略里优先级很低，不表示它所占的内存可以立即给别人。如果某个重放仍租用它，物理生命周期要比逻辑价值更长。发生抢占、失败或回退时都应保留这条约束。精确切块回退是语义正确的结果，只是没有获得预期性能收益；不能为了统计上更少回退而公开一个不完整状态。

    重放窗口上限是 1,024 token。更远目标主动切块，运行期缺锚点或日志页也可回退。主要配置的窗口中位数为 96、p90 为 768 token，窗口范围内完成率约 99.5%。这个比例有条件范围，不能把它改写成“所有请求 99.5% 都完全不切块”。普通 chunked prefill、超过窗口的主动切块与准备失败是不同来源。

    跨层设备指针表使一次重放只需少量 kernel launch，而非每一层都重走一次完整启动链。日志、复制和重放 kernel 在 warmup 时编译与捕获。这解释了额外 GPU 阶段如何保持较低开销，但并未消除它的状态读取、暂存字节和资源预留。

    6. 如何预测可复用边界

    作者的放置规则主要来自四类结构。第一类是聊天模板的稳定终点：启动时渲染两个探针会话，比较上一轮生成提示与下一轮重新渲染后的公共部分，找出尾部模板后缀之前的位置。这样下一轮到来时，往往能恰好接到共享历史的末端。

    第二类是已结束轮次的最后完整页边界。Decode 本身依次经过这些状态，所以结束后保存只需复制，不用额外重放。第三类是已知分叉：radix 节点已经有两个孩子，深度至少 256 token，而该处没有检查点时，可在后来的请求中把它设为目标，供再后来的兄弟使用。第四类是自然 chunk 结束位置，状态本来就存在，因此作为低优先级候选提供给池子。

    已知分叉规则具有因果性。服务器看到两个分支后才知道这里是 junction，不可能回过头让最早两个请求享受当时尚不存在的检查点。论文的优势不依赖未来轨迹 oracle，而是利用历史已经暴露的结构；相应代价则是分叉冷启动可能晚一拍。

    八个主要模型与工作负载组合中，79–100% 的可复用 token 终点对应先前轮次边界，落在此前未知分叉上的最多约 8%[1，§3.1]。这说明所选轨迹有很强的结构规律，但不能扩展成所有 agent 流量的定理。文档改写、检索顺序变化、客户端重新序列化工具信息、不同模板分支，都可能让下一次最长公共前缀停在另一处。

    模板探针的好处是解释清楚、不必学习复杂 overlap 分布；边界则是模板依赖。如果运行期间系统头、工具编码或模板版本变化，启动时识别的 stable end 可能不再合适。保守适配应重新识别结构并允许精确回退，不能仅凭两个启动探针就证明所有条件分支都永远稳定。

    文档问答还说明，位置“更深”不一定“更有用”。一条请求的 prompt 尾部可能已经包含私有问题，而后续问题只共享前面的文档。只保留最深尾部状态，可能根本接不到后来的公共前缀。论文为每个长前缀组保护一个已有自然检查点：在 stable end 之前一个 2,048-token 预算范围内，且距起点至少两个预算，也就是 4,096 token。当它的 KV 仍在、又没有更深的可达 junction 时，按 proven 层级保护。

    这些常数是作者的操作选择，不是从理论上证明的普适最优值。它们表达的是一个更一般的原则：保存能位于未来分歧之前、又尽可能接近分歧的位置，而不是机械地保存“当前最长”的那一份状态。放置位置、保留时间与 KV 可达性共同决定未来是否真能复用。

    7. 会话前沿保留与死状态回收

    为什么最近用过最多的，未必最值得留

    一次会话不断产生新锚点。最新锚点历史命中次数可能为零，因为下一轮还没到来；旧祖先却可能已被许多轮请求经过。纯频次规则于是会偏爱已经走过的历史，把恰好要供下一轮使用的新状态挤掉。FrontierReplay 在时间与频次之外，引入状态相对会话前沿的位置。

    图 5：根据论文 §4.4 自绘的 Mermaid 概括。箭头表示保留优先级递增，并非每个状态必须依次经过这些阶段。长前缀保护可提升一个已有自然状态；租约另外约束实际释放时间。

    最低是 Dead，层级 -1：前缀某一 KV 页已经丢失，恢复它也接不上注意力历史。其次 Superseded，层级 0：同一路径上已有更深状态，并满足没有有用中间分叉及论文规定的推进条件。接下来是自然 chunk 状态 1、未被验证有用的轮次锚点 2、Proven 3，以及运行请求的锚点 Running 4。

    Proven 包含分叉节点，或已被至少两个不同请求恢复的状态。为什么不是一次恢复就够？因为多轮链上，每一轮都会恢复前一轮锚点。若一次命中就永久提升，整个会话所有祖先都会变成“重要历史”，最终仍然没有空间留给新的前沿。池满时，新自然状态只能替换 dead 或 superseded 状态，也是在避免免费生成的候选吞掉昂贵的持久显存。

    Running 则保护仍在执行请求的锚点，因为该会话的下一轮很可能马上需要它。分叉服务多个未来兄弟，轮次锚点往往只服务一次后继，这两种价值都不能从过去 hit count 直接看出来。作者不是简单地给所有最近对象同一个高分，而是区分它们下一次被使用的结构原因。

    论文先用同层内 LRU 描述基础排序，后面的长前缀修正还引入“失去该状态后会多损失多少可复用 token”的估计，同层内优先淘汰损失较小的状态，并可提升反复命中且估计损失达到一个预算的状态。因此最终策略不能仅概括成六层 LRU。我用下式帮助理解一次相关命中的边际损失：

    ℓ(c)=max⁡{0, c−cfallback}.(8)\ell(c)=\max\{0,\ c-c_{\mathrm{fallback}}\}. \tag{8}ℓ(c)=max{0, c−cfallback​}.(8)

    cfallbackc_{\mathrm{fallback}}cfallback​ 是去掉它以后能回到的下一个可达锚点。这个式子是笔记的解释量，不冒充作者完整估计器。一个被很多兄弟依赖的分叉，与一个马上要继续的运行轮次，可能因不同原因都有高价值。

    把无用状态的空间借给 KV

    分池会产生偏斜：客户端在两次调用之间等待，期间其他请求挤掉该会话的 KV，旧递归状态便变 dead。继续占着它的几十 MiB 不能恢复任何完整前缀，而 KV 池可能正缺空间。作者每 16 个请求运行一次控制器，统计因 KV 丢失而死亡的状态。

    若过去四个周期没有淘汰过 tier 大于零的检查点，说明状态池当时不是主要瓶颈，就可以把最多 min⁡(16,2d)\min(16,2d)min(16,2d) 个槽借给 KV，ddd 为死状态数。只允许淘汰 tier 不大于零的对象，并保留覆盖运行请求工作状态的底线。控制器自身造成的淘汰不计入下轮死亡信号，以免缩池产生更多“死亡”，又驱动继续缩池，形成正反馈[1，§4.5]。

    CUDA 虚拟内存页让地址保持稳定而调整物理 backing，有利于已捕获的 CUDA graph 继续使用。但稳定虚拟地址不等于所有空间都可立即互换。活槽、租约、连续回收要求和 tensor-parallel 固定子池，都可能使一次借用失败。后面 34B 文档问答的反例正说明：有 VMM 机制，仍然可能被分池约束卡住。

    我认为这部分是论文里很有价值的设计选择。它同时承认两个事实：有些状态应该尽快丢，因为 KV 已不在；有些看似从未被用过的新状态却应保护，因为它刚好位于会话前沿。两个判断都依赖未来的可达关系，而不仅是某个对象本身的历史热度。

    8. 重放成本与显存账要一起算

    图 6：论文 Fig. 4。原始测量[1]。右侧比较每 token 斜率，不是完整请求端到端延迟；左侧在相同目标与 token 工作量下比较迭代增加。

    Lcross=ac−b,c>b.(10)L_{\mathrm{cross}}=\frac{a}{c-b},\qquad c>b. \tag{10}Lcross​=c−ba​,c>b.(10)

    若一个新检查点预计被有效恢复 rrr 次，每次少算 LLL 个全模型 token，可粗略写成

    benefit≈r(cL−Tcopy)−(a+bL)−Tlog−Cmemory.(11)\mathrm{benefit}\approx r(cL-T_{\mathrm{copy}}) -(a+bL)-T_{\mathrm{log}}-C_{\mathrm{memory}}. \tag{11}benefit≈r(cL−Tcopy​)−(a+bL)−Tlog​−Cmemory​.(11)

    CmemoryC_{\mathrm{memory}}Cmemory​ 是占用这些字节挤掉 KV 或其他状态造成的服务机会成本，使用时应先换算到共同代价单位。这是笔记整理的决策框架，并非作者测得的一个标量。没人再用的检查点，生成与持久占位都白付了，所以投机候选不能无限接纳。

    日志虽然短，也不能称为几乎不占空间。Qwen9B 每 token 是 363 KiB，1,024-token 窗口约 363 MiB；Falcon7B 为 312 KiB/token，同长度约 312 MiB。若简单为 32 个并发请求都预留最大窗口，仅日志就约需 11.34 或 9.75 GiB。实际方案采用有界共享暂存池和回退，而不是保证所有请求可同时拿到最大窗口。

    Mlog=∑i∈inflightLiui,Nstate≤⌊MpoolMcheckpoint⌋.(12)M_{\mathrm{log}}=\sum_{i\in\mathrm{inflight}}L_i u_i,\qquad N_{\mathrm{state}}\le \left\lfloor\frac{M_{\mathrm{pool}}}{M_{\mathrm{checkpoint}}}\right\rfloor. \tag{12}Mlog​=i∈inflight∑​Li​ui​,Nstate​≤⌊Mcheckpoint​Mpool​​⌋.(12)

    uiu_iui​ 是日志每 token 字节。按 10 GiB 检查点预算除以 49.1 MiB，Qwen9B 理论上最多放 208 个状态大小对象；换成 Falcon7B 的 66.9 MiB，则为 153 个。还要考虑工作状态预留与分配约束，所以这不是可随意用于持久复用的槽数。论文主要配置里可容纳状态的范围约为 105–208，而不是一个任意密集的全历史缓存。

    作者为 Qwen/Falcon 的 workspace 加日志 slab 分别静态预留 1.76/1.79 GiB，平均每步活跃写入却只有 68.4/23.9 MiB。这两个数字回答不同问题：一个是预留空间，另一个是某步实际写入量。不能拿平均写入少来否定预留字节的机会成本，也不能拿峰值预留直接当作每步流量。

    这一成本模型也解释了尺度收益：日志记录通常随宽度近似线性增长，而全模型计算有更强的宽度增长。作者测得的重放斜率优势从 4B 的 5.8 倍增至 27B 的 20.7 倍、Falcon34B 的 36.9 倍。但更大的模型也意味着更大的状态、更紧的 KV 容量，斜率优势并不自动转化成每种负载都更高的 goodput。

    9. 实验先看服务定义，再看倍数

    主要平台是一张 A800 80 GB，BF16 权重，2,048-token prefill 预算，piecewise CUDA graphs，32 GiB 缓存预算。Qwen3.5-9B 包含 24 个 GDN 与 8 个注意力层，递归状态为 FP32；Falcon-H1-7B 有 44 个并行混合块，Mamba-2 状态为 BF16。27B/34B 则使用双卡张量并行与固定的每卡分池[1，§6.1]。不带这些条件直接引用倍数，会丢掉决定结果的重要背景。

    四类负载分别是 ShareGPT 多轮窗口、SWE-agent 工具会话、LongBench 文档问答，以及八分支 GSM8K 树搜索。会话按 Poisson 过程到达，子调用等父调用完成后再发出。计时时，所有系统重放相同的记录响应，以控制响应长度与后续轨迹。这有助于可比性，但它并不等于一个实时 agent 环境：若模型输出改变，本来可能引起工具动作和后续调用分布变化，而固定响应轨迹不会测到这条反馈链。

    联合 SLO 是 TTFT 不超过 500 ms、每次调用的平均 TPOT 不超过 50 ms，并在 180 秒超时范围内完成。满足条件的调用数除以总墙钟时间才是 goodput。为了让式子可读，记 IiI_iIi​ 为调用 iii 的通过标记：

    10. 近似对照与消融分别支持什么

    准确率是另一组实验

    图 8：论文 Fig. 8。原 RULER variable tracking 扫描[1]。纵轴是相对 vLLM 的准确率，不是绝对正确率；略高于 100% 的点不应被解释为缓存让模型能力变强。

    准确性测试包括 303 个 LongBench、needle 与 RULER 项，再加 800 个 variable-tracking 问题。FrontierReplay 在作者测试中接近基线；SuffixReplay* 使用 512 行尾部时，在 24K/32K 的 VT 上相对准确率降低 13–17%，尾部缩到 128 行则降低 15–18%。它支持一个具体风险：用近处少量隐藏行近似递归状态，会丢掉某些长距离任务所需的信息。它不证明所有近似状态方法都必然损失同样比例。

    这个比较对象是作者按论文描述独立适配的版本，原方法当时没有发布代码。星号提醒读者不能把这里的参数和表现自动归给所有未来 SuffixReplay 版本。该设置在交错模型上，从零开始用最多 512 个稀疏隐藏行重建状态。它既改变状态语义，也带来每次命中都要支付的重建开销。

    在高竞争负载下，FrontierReplay 对近似方法并非处处胜。表 4 中，ShareGPT 的比值为 0.986 [0.90, 1.07]，应判作打平；工具会话也主要打平。LongBench 在负载六时为 1.538 [1.48, 1.59]，ToT 在负载十六时为 1.101 [1.04, 1.16]，才是更明确的胜出。一次生成检查点、之后只复制，可能比每次命中都做尾部重建更容易摊薄成本，但要以持久状态显存为代价。

    消融说明收益不只来自少切块

    图 9：论文 Fig. 9。原累计消融[1]。每个面板有自己的运行点与负载，绝对调用数不能不加说明地拿来替换表 3 的锚点结果。

    Falcon 工具会话的消融中，stable-anchor 切块版本为 0.37 调用/秒，去掉额外切块达到 0.67，最终达到 0.74，而该消融中的 vLLM 为 0.19。Qwen 文档问答里，frontier 与 junction 保护把 2.39 提到 2.58。这些结果说明少算 token、少调度一次与留对状态是不同贡献。

    消融是累计加组件，因此某项边际收益依赖于前面已经开启了什么。不能把它解释成任意组件顺序下都成立的独立因果份额。也不要把这一图里的 0.74 与表 3 的 4.26 倍强行相除：它们属于分别报告的设置和运行，分母不相同。更可靠的做法是始终保留所用图表、负载和配置标签。

    显存收紧以后，Falcon 工具会话在 16–24 GiB 点主要缺的是状态槽，并非日志。作者报告零 log drop，但约 7.2% 因检查点容量触发精确切块回退，各系统都在约 0.21 调用/秒以下饱和。这个场景只增加日志空间并不能解决问题。反过来，Qwen 的 16 GiB 工具会话维持 98.7% split-free 完成，goodput 为 1.37 对 0.76，体现绑定资源取决于模型状态尺寸与负载。

    作者还报告在八个主要锚点，重放与恢复占 GPU 墙钟时间不超过 1.2%，主机调度额外开销也不超过 1.2%。在避免了许多昂贵 prefill 的负载里，这个占比可以理解；但它是那些负载下的测量比例，不是低复用、小模型或极短请求的普适上界。

    11. 局限：论文已经给出的反例要认真读

    图 10：论文 Fig. 12。原规模比较[1]。34B LongBench 的 goodput 柱子低于一，但 TTFT 加速仍高于一；4B ToT 的 goodput 也基本打平。

    第一，延迟下降不保证合格调用变多。34B LongBench 在负载 0.5 时，中位 TTFT 从 225 降到 135 ms，约 1.67 倍加速，goodput 却只有 vLLM 的 0.76。命中率从 0.90 降到 0.83。固定 TP 子池每卡给 KV 22 GiB 加 82 个状态槽，而 vLLM 使用统一 32 GiB；活尾槽还阻挡了 22 次回收。命中路径更快，也可能抵不过其他请求失去 KV 的损失[1，§6.5]。

    第二，小模型可能没有足够可摊薄收益。4B ToT 在负载十二时消除 18 个 TPOT miss，但 TTFT 从 55 增到 62 ms，goodput 约 0.99 倍。445 对 444 个通过调用只差一个，而且是单次运行，不能据此认定稳定退化；但同样不能再说所有点都提高。

    第三，原生导出可以更便宜。细 tile 的 Qwen GDN 上，作者适配的 multi-target export 在聊天与工具追加比较中领先约 1.5–2.5%；粗 tile 的 Falcon Mamba-2 则因 off-tile 部分扫描而使重放更好。这里标 † 的追加比较只有一次配对运行，支持的是依赖 tile 与目标位置的交叉边界，并非所有导出方案必然落后。

    第四，任何状态资源都有机会成本。日志 slab、检查点、工作锚点都占字节，租约可能延迟回收。VMM 保持地址稳定，不会把活对象变成空闲空间。论文最本质的交换，是付出有限额外显存来减少全模型重算与调度切块，而不是让缓存变成没有代价的资源。

    第五，边界规律可能变化。新分叉、短 Falcon 前缀、模板更改与宽窗口都会降低不切块生成状态的覆盖率。精确回退可以保留语义，却可能逐步吃掉性能优势。论文依赖的结构统计来自选定轨迹，不能代表所有序列化方式、任意实时 agent 或突发多租户流量。

    最后，A800、固定 runtime 与精度、Poisson 到达和记录响应共同限定了证据范围。任务分数相近也不等于所有调度历史下字符串逐字节相同。最有力的精确性论断仍然是：在捕获的真实输入和舍入边界条件下恢复相应递归计算，并由作者的状态级与任务级测试支持。

    12. 批判性分析：接下来最应验证什么

    先修正分池决策，再继续追最大倍数

    我认为最有后果的弱点不在重放公式，而在“该把多少字节留给递归状态”。34B 文档反例直接否定了“重放很便宜，所以端到端一定更好”的直觉。下一版应比较多一个检查点省下的预期重算，与它挤掉 KV 造成的损失，同时计入活租约、不可连续回收空间及运行槽底线。

    具体做法是用统一总字节预算评估动态分配器，而不是只增大某个池，直到某条有利轨迹变好。应额外记录重分配失败、逻辑 dead 但物理不可回收的字节、租约时长、复用距离，以及“KV 还在却没有可恢复状态”的比例。控制器还应经历负载阶段变化，而不只在稳定流量里跑平均值。过于积极的借用可能改善当前均值，却在下一波会话到来时没有状态槽可用。

    这种验证能把两个问题分开：是策略不知道哪些字节更有价值，还是策略知道但物理碎片和活对象使它无法执行。前者需要更好的价值估计，后者需要调整布局或租约时长。只画一个最终 hit rate，无法区分这两类失败，也难以知道更复杂的控制器是否值得引入。

    让结构预测接受有意扰动

    模板探针和分叉规则透明、容易理解，但可能预测错或发现晚。我会保持语义会话相同，改变工具序列化、模板分支与头部元信息，再比较预测目标和真实后继最长公共前缀。应分别统计未知 junction、状态被淘汰、KV 丢失、精度下限和窗口上限造成的 miss。

    这比笼统说“命中率下降”更有操作性。若大部分是未知分叉，增大检查点池可能无用；若目标正确却因 KV 丢失，继续优化重放 kernel 也解决不了问题。可以尝试带置信度的目标预算：高置信轮次锚点优先，少量空间探索不确定分叉，若实际重用率很低就缩减探索。这是我提出的下一步，不是 v1 已证明的功能。

    学习或评估这种规则时必须保持因果性。只能用过去已经看到的请求，不能拿完整未来轨迹选出最佳位置，再把它包装成在线调度收益。论文当前结构规则的优点恰恰是这条因果链比较清楚，后续复杂化不应丢掉它。

    把精确性写成可迁移的数值契约

    舍入 bitmask 是很好的系统细节，却也引入移植义务。换后端 kernel 可能改变中间写回位置，短卷积缓冲语义也可能不同，即使模型形状相同。数值契约应明确状态 dtype、真实转换输入、卷积缓冲、舍入标记和公开事件；新后端需要重新建立固定前向的状态一致性，之后才有比较吞吐的意义。

    实验上，我会分开报告固定前向的状态差异、固定 batch shape 的 logits 差异，以及动态 batching 的输出变化。再按 top-2 logit 间隔分桶，能区分真实状态错误与近并列 argmax 扰动。这里提出的是论文级验证设计，不根据未知源码推断作者程序有什么隐藏问题。

    比较机制要给出决策区域

    共用 runtime 与移植基线有助于控制变量，但固定分池和统一池仍不同。我希望看到每种方法各自的分池扫描和相同总预算前沿，再观察 cuts、export、replay 在何处分别占优。按 tile 对齐目标用原生导出、off-tile 用重放，是一个合理组合设想；不过额外集成与 graph capture 复杂度，也可能抵消小幅孤立收益，需要整体验证。

    由于我参与 FlashState，比较归属尤其要准确。本文测试的是 FrontierReplay 作者实现的、受相关工作启发的多目标导出适配版本，有它自己的 kernel 修改和 graph signatures。结果必须绑定那个比较对象与目标分布，不能外推成原完整 FlashState 系统在同条件下一定有相同结果；反过来也不能因我参与相关工作而忽略本文真实报告的 export 优势和弱点。

    最终有用的交付应是一张决策图：模型宽度、tile、上下文、复用次数、活会话与 KV 压力如何决定生成哪种状态。一个最大加速倍数并不能代替它。论文已经给了两类很有价值的负面点，认真解释它们，比继续添加一个有利锚点更能推进下一版系统。

    13. 复现要点与操作性阅读框架

    这篇论文足以解释机制，但复现服务数字仍需要精确的 token 化与模板、记录响应、因果到达时间、分池布局、各比较对象的定义、精度，以及逐次运行结果。笔记没有重跑这些模型或服务实验。参考文献中的 runtime 资源入口也不能证明 FrontierReplay 已经发布了完整可复现工件。

    算法 2. 判断一个已有状态是否还值得保留

    下面把保留与生命周期条件整理成编号阅读框架；实际同层排序还包括损失估计和最近使用信息。

    1. 检查候选状态所需的全部前缀 KV 页是否仍然可达。
2. 缺任一必需 KV，则标为 Dead，不能当成可命中状态。
3. 否则判断是否存在更深状态，且中间没有需要保护的分叉。
4. 对其余对象区分自然点、未验证轮次、Proven 与 Running。
5. 为每个合格长前缀组应用一个自然状态保护规则。
6. 物理淘汰先排除仍被租用、GPU 依赖尚未结束的存储。
7. 池满时，新自然点只允许替换 tier 不大于零的候选。
8. 选最低可淘汰层级，同层结合损失估计与最近使用次序。
9. 每 16 个请求观察外部 KV 淘汰导致的死亡及状态池压力。
10. 满足静默周期和运行槽底线后，借出可回收槽给 KV。
11. 不把控制器自己制造的淘汰计入下一轮死亡信号。

    正式投入 GPU 做比较之前，最值得准备的是五层证据。第一层是轨迹完整性：完全相同的 prompt、模板、响应及父子调用时间。第二层是资源账：KV、状态、日志、workspace 与工作槽都算，每张 TP 卡的池子单独列。第三层是语义：递归矩阵、卷积缓冲、舍入历史、事件公开。第四层是服务口径：两个 SLO、超时、扫描负载与墙钟分母。第五层是不确定性：配对结果、独立种子，以及哪些图只有一次运行。

    一个简单复算就能说明为什么不该混指标。TTFT 从 1,100 到 125 ms 是 8.8 倍加速，延迟减少约 88.6%；容量从 0.69 到 1.11 是提高约 60.9%；锚点 goodput 的 4.26 倍又是第三种量。三者可以同时正确，因为回答的问题不同。把三个“倍数”写成同一个系统吞吐结论，会制造论文没有给出的结果。

    最先做的操作性测试可以很小：一条已知分叉轨迹，故意丢一页 KV、让起始锚点不可用、再让日志池耗尽。每个分支都应保留精确切块回退的契约。之后才扩大复用率和显存压力扫描，找出少生成检查点反而提高服务的区域。这里是一份未来验证计划，本笔记没有声称已经完成这些部署测试。

    14. 结论

    FrontierReplay 最清晰的想法，是把中间递归状态当作一段已记录状态计算的物化结果，而不是只能在整个网络前向停下时才拿得到的副产品。真实日志解决跨层输入依赖，舍入边界保留数值路径，GPU 事件保护异步公开，会话前沿策略让保存的状态更接近下一次实际使用。

    我的判断是按条件采用：重复结构前缀本来会触发大量全模型重算或额外调度迭代、且状态与日志显存没有挤掉更有价值 KV 时，这个设计很有吸引力。复用稀少、小模型已有 decode 余量、tile 对齐导出很便宜，或固定分池成为容量瓶颈时，收益就需要重新计算。

    这篇论文的价值还在于把检查点生产代价与复用收益分开测量，并给出一个真实的容量反例。下一步应让服务决策本身更自适应：哪个位置值得保存，用什么机制生成，以及为它付出多少其他缓存机会成本。
