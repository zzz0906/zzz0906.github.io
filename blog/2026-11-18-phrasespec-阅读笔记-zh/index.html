    Phrase-Level Speculative Decoding 阅读笔记：换掉草稿单位，保留目标模型

    笔记日期： 2026-11-18
    笔记作者： Zhongzhu Zhou
    阅读论文： Phrase-Level Speculative Decoding on a Frozen Target
    论文作者： Madhusudhana Naidu
    arXiv： 2611.12464
    版本与日期： v1，2026-11-09

    1. 我觉得值得记住的想法

    读这篇论文时，我首先想到的是一个经常被默认绑定的关系：草稿模型预测的单位，为什么必须等于目标模型使用的 token？目标模型当然要继续接收自己的 token ID，但草稿端完全可以先预测另一个符号，再把这个符号展开成一串目标 token。比如一句常用表达、一段数学格式，或者被目标 tokenizer 切得很碎的一个词，都可以成为草稿端的一次分类决策。

    论文就在这条缝隙里做文章。一个很小的 MLP 读取目标模型已经算出的隐藏状态，从独立词表预测一个一至三个单位的片段。候选展开以后，仍然由原来的目标模型验证。目标权重、tokenizer 和贪心解码规则都保留。草稿错了会浪费一次预测或验证机会；只要验证过程满足正确的因果关系，草稿本身不会决定最终输出。

    图 1. 根据论文摘要、第 1 节和第 4 节绘制的说明图。草稿头输出的是片段编号，展开后才进入目标模型。是否接受仍由目标 token 上的 argmax 决定，候选错误通常损失的是速度。

    我不把它概括成短语草稿已经全面超过 token 草稿。主实验是 Qwen3-4B、单张 A5000、batch 为 1、贪心生成，测试的 prompt 数量也很小。较大的短语头在两组数学任务上超过 EAGLE-3 的 tree-16 工作点，但在三个任务上都没有超过 tree-60。它更明确的价值是：增加很少的参数，也能获得可观的候选收益，并且不需要更改目标模型的接口。

    另一个值得记住的发现是，题名里的短语并不总是自然语言短语。作者的正则切分把单独的标点也视为一个单位，因此三个单位可能只是一小段 LaTeX。数学任务中，标点和 LaTeX 承担了大部分被接受的草稿工作。这意味着系统主要抓住了低熵的格式骨架。这个解释比泛泛地说模型学会预测长短语更具体，也更容易设计下一步实验。

    我读完了 v1 的 10 页全文、9 张表和参考文献；这个版本没有独立附录。下文的伪代码是根据论文机制整理的概念过程，补充推导与说明性算例会明确标注。表中 GPU 测量均来自论文，我没有另训草稿头，也没有运行推理基准。读这篇论文的重点，是弄清楚什么收益已经被测到，什么只是潜在空间，以及怎样把后者变成可检验的问题。

    2. 前置知识：先把三个单位分清

    2.1 目标模型只认识自己的 token

    设目标词表为 VTV_TVT​，当前已经提交的 token 前缀为 xxx，目标分布为 pTp_TpT​。贪心解码的下一步是

    y∗(x)=arg max⁡v∈VTpT(v∣x).(1)y^*(x)=\operatorname*{arg\,max}_{v\in V_T}p_T(v\mid x). \tag{1}y∗(x)=v∈VT​argmax​pT​(v∣x).(1)

    草稿词表只需要提供一个映射：某个草稿条目对应哪些目标 token ID。这个条目不需要在目标 embedding 或输出投影里增加一行。MLP 最后一层预测的是自己的类别编号；真正送入目标模型的仍然是目标 ID。这样就把草稿表达能力与目标词表解耦了。

    论文用 Qwen 的预切分边界解释为什么多词表达很难成为一个目标 token。我会把这个结论限定在所讨论的 tokenizer 上。BPE 的预切分正则、空格附着、规范化和特殊符号处理都可能不同，不能把具体 tokenizer 的限制写成所有 BPE 的共同定理。方法真正需要的条件更宽：有用的草稿单位，与目标模型的原子 token 不一致。

    常用的 fertility 指标是一个词平均占几个目标 token。它能提示潜在空间，却不能单独预测加速。一个长词被切成十几个 token，如果草稿头几乎猜不中它，仍然没有多少收益。服务中的前缀还混合了公式、代码、姓名和普通对话。语言级的平均切分长度，不能替代解码位置上实际可预测片段的分布。

    2.2 一次前向为什么能检查多步

    给定一条候选序列，因果模型可以通过 teacher forcing 并行算出每个位置的 logits。第几个候选 token 是否可接受，要用已提交前缀加上此前候选 token 得到的目标分布判断。一旦某处与目标 argmax 不同，后面的 logits 就建立在尚未接受的历史上，不能继续拿来证明后缀正确。

    多个候选共享前缀时，可以合并为前缀树。树节点只看已提交上下文和自己的祖先，不能看兄弟分支。位置 ID 也要表达自己在候选路径中的深度，而不能直接使用展平数组里的行号。这些关系决定了验证是否等价于普通贪心生成，和草稿头本身有多准确是两回事。

    一次验证还可以带出一个由目标模型自己选择的补偿 token。即使所有候选第一步都失败，也能前进一个 token。这解释了论文 token/pass 的算术下限是 1，但它不意味着速度一定至少是原来的 1 倍：失败的草稿和树验证仍然会花时间。

    2.3 候选数、验证行数、接受长度并不相同

    我用 NNN 表示草稿条目数，RRR 表示展开、合并之后的独立目标位置数，用 AAA 表示最后被接受的目标 token 数。一个条目可能展开成很多行，多条候选也可能共享一大段前缀。因此 NNN 不是验证成本，名义短语长度也不是收益。

    短条目不一定没有价值。长片段后半段不匹配时，短前缀仍可能有用；长片段第一步就很难猜时，它的巨大展开长度只是潜在奖励。为单单位条目预留候选槽位，可以保留这种退路，但也会占用本来可以放长候选的预算。在进入 GPU 之前，这已经是一个需要衡量边际收益和边际成本的选择问题。

    3. 草稿词表如何形成，分类头究竟学什么

    3.1 先明确展开接口

    把草稿词表记为 D={u1,…,uV}D=\{u_1,\ldots,u_V\}D={u1​,…,uV​}，条目 uuu 在前缀 xxx 下的目标展开记为 Ex(u)E_x(u)Ex​(u)。这里特意保留 xxx，是因为把一个字符串单独 tokenize，与把它放进完整续写后 tokenize，边界处可能不同。可以在已验证的 token 边界保存目标 ID 序列，也可以在展开时处理上下文，但不能默认两者天然相同。

    前导空格、Unicode 组合符号、数字分隔符、byte fallback 和特殊 token 都属于这个接口需要解释的内容。如果展开只是给出一段低质量候选，正确验证可以把它拒绝；但如果停止规则、位置或缓存一起处理错，就不能再用冻结目标模型来保证行为。论文给出了高层机制，没有把这些边界逐一列成完整协议，我在这里将它们作为独立实现必须说明的语义条件。

    作者从目标模型蒸馏出的数学续写中挖掘条目，允许一至三个正则单位，并给单单位条目保留约一半预算。8,000 词表实际有 4,003 个单单位条目、3,997 个多单位条目。不要为了方便把它写成正好 4,000 加 4,000；词表生成后实际数量才是报告事实。

    3.2 最长匹配是标注规则

    一个训练位置之后，可能同时匹配一个词、这个词加标点，以及更长的片段。最长匹配是从这些重叠标签中选择一个监督目标。它不等于运行时必须接受最长候选，也不意味着较短的匹配前缀失效。

    为了说明分类任务，可以写一个常见的交叉熵目标：

    LCE=−∑i∈Ilog⁡qθ(ui∗∣hi).(2)\mathcal{L}_{\mathrm{CE}}=-\sum_{i\in\mathcal{I}}\log q_\theta(u_i^*\mid h_i). \tag{2}LCE​=−i∈I∑​logqθ​(ui∗​∣hi​).(2)

    其中 hih_ihi​ 是目标隐藏状态，ui∗u_i^*ui∗​ 是选中的片段标签，I\mathcal{I}I 是真正进入特征预算的训练位置。这个公式是我的任务解释；v1 没有给出足以重建所有训练选择的完整损失与采样协议。尤其是，生成了多少 token，并不等于多少位置真正参与了训练，在线实验自己就承认了这个差别。

    分类准确率与推理收益也不是同一目标。交叉熵奖励选中正确标签，推理系统需要的是单位时间内多接受多少目标 token。当长而常见的条目容易预测时，两者一致；当长标签压低短前缀排名，或者极长条目经常第一步就失败时，两者就会分离。这个差别会影响词表构建、候选筛选以及后续在线更新的评价方式。

    算法 1. 词表构建和监督标注的概念过程

    下面整理的是论文的词表思路，边界验证为展开接口所需条件，不把未写明的训练细节补成作者的具体做法。

    01  从训练划分收集目标模型生成的续写。
02  用声明的词与标点规则切分每条续写。
03  统计长度为一、二、三个单位的合法片段。
04  在 V 个条目的预算内选择词表，保留单单位份额。
05  为每个条目关联边界正确的目标 token 展开。
06  遍历真正进入特征预算的隐藏状态位置：
07      找出与后续文本匹配的词表条目。
08      用最长合法匹配确定监督标签。
09  用这些位置与标签拟合小型分类头。
10  分别检查候选召回和实际接受的 token 收益。

    第 4 步和第 8 步之间有一个容易忽略的关系：虽然标签偏向最长匹配，候选集仍要留住短前缀。论文据此讨论短语相对单词的弱改进，但这需要比较器的候选确实被保留下来。即使候选集合包含关系成立，也只能帮助说明可接受前缀的空间，不直接证明总延迟更低，因为树行数、分类分数和验证成本还会改变。

    3.3 为什么一个 MLP 可能够用

    目标隐藏状态已经概括了完整上下文，小头不需要独立再做一遍语言理解。对数学格式这种重复结构，一个浅分类器就可能有效。作者报告，在所试预算里，更深的 MLP、注意力与卷积注意力没有胜出，增加宽度比增加深度更有用。我把它理解成当前数据和预算下的经验，不把它扩写成所有更复杂 drafter 都没有空间。

    替代方案仍有各自位置：检索适合命中资料库里的罕见字符串；自回归 drafter 能在后续猜测中利用自己的前序猜测；改目标 tokenizer 可能减少所有后续计算，但会改动目标接口及训练需求。这里的小词表头提供的是另一种取舍：只改变提议单位，用目标模型已有的隐藏表示来支付主要理解成本。

    4. 验证树的正确性，关键在因果上下文

    4.1 展平只是存储方式

    设当前已提交上下文为 xxx，某个节点所在路径为 z1:dz_{1:d}z1:d​。测试 zdz_dzd​ 时，目标 logits 必须对应 x,z1:d−1x,z_{1:d-1}x,z1:d−1​。这意味着兄弟分支不能相互看见，位置编号也要按路径深度安排。把所有节点放进同一个二维张量，并不意味着这些行组成了一段普通文本。

    图 2. 根据论文的前缀树描述绘制的概念图。两个候选共享第一个目标 token，其余节点属于不同路径。只有与目标贪心决策一致的分支可以进入已提交缓存，兄弟节点不是相邻的自然序列。

    接受以后还有一次状态边界。验证阶段可能为所有候选都计算 KV，但长期保留的只能是被接受路径对应的状态。最后由目标选择的补偿 token 虽然已经输出，其 KV 可能在下一轮才被真正算出。不能因为某一批计算过某个分支，就把该分支直接当作已经发生的历史。

    4.2 用归纳法理解为什么输出可以保持一致

    先假设目标计算是确定的，因果上下文、位置、数值精度和 argmax 平局规则都与基线一致。若当前提交前缀与普通贪心生成相同，则第一个候选位置所面对的目标条件分布也相同。只有候选等于目标 argmax 才接受，就会保持前缀相等。沿接受路径逐步使用同一逻辑，整个块都相等；再输出目标自己选出的下一 token，仍然相等。

    这个证明不要求草稿分布准确。一个很差的头会导致大量拒绝，但不会自动破坏证明。真正的前提是，验证 logits 确实对应正确的条件分布。树形批量计算和逐 token 计算可能使用不同 kernel 或归约形状，近似平局时浮点差异会改变 argmax。论文也保留了浮点平局的例外。我认为更好的实验报告应该同时给理论保证和实际 token 相等率，而不是把目标权重冻结直接等同于逐比特一致。

    算法 2. 一次贪心树验证的概念过程

    下面写出语义上需要完成的步骤，不规定目标后端的接口或缓存布局。

    01  从与贪心基线一致的已提交前缀开始。
02  用最近的目标隐藏状态为草稿条目打分。
03  选择 N 个条目，并保留声明的短条目份额。
04  展开为目标 ID，合并相同前缀。
05  按路径深度设置位置，只允许看祖先与已提交上下文。
06  用目标模型计算树上的条件 logits。
07  沿路径逐 token 检查是否等于目标 argmax。
08  选择最长的存活前缀，使用固定的平局规则。
09  若停止条件允许，输出存活前缀和目标补偿 token。
10  只保留接受路径的 KV，丢弃其他候选状态。
11  按目标顺序处理 EOS、长度上限和外部停止规则。
12  从新的已提交状态继续。

    若某个候选中间已经出现 EOS，或者请求只剩一个输出 token，不能因为草稿条目还没结束就整段输出。停止字符串也可能出现在片段内部，仍应按照正常目标 token 边界处理。这些细节既影响语义，也影响后面统计的输出长度和耗时。

    4.3 这还不是精确采样算法

    temperature 为 0 时，argmax 匹配就是要维护的行为。temperature 大于 0 时，要保持目标采样分布，需要额外的接受概率和残差采样规则；短语候选存在重叠路径，其概率质量也要正确处理。论文没有验证这一扩展，因此不能将贪心一致性改写为支持任意采样的无损加速。

    同样，表示层面与树深度正交，也不代表组合以后成本没有耦合。更深的神经草稿会引入串行工作，量化 KV 可能改变目标 logits，候选前缀重叠也会变化。可以组合是一个设计空间；组合后是否更快、匹配的是哪个数值目标，仍需要单独实验。

    5. 把接受收益和时间成本推导清楚

    5.1 展开长度不等于接受长度

    令 BBB 为一次验证真正接受的草稿目标 token 数，LLL 为至少接受一个草稿 token 的事件，pL=Pr⁡(L)p_L=\Pr(L)pL​=Pr(L)。先忽略最后一轮被 EOS 或长度上限截断，输出量为 K=1+BK=1+BK=1+B。按是否 landing 分解期望，有

    E[K]=1+E[B],E[B]=Pr⁡(L)E[B∣L]+Pr⁡(¬L) 0,E[K]=1+pL μB∣L.(3)\begin{aligned} \mathbb{E}[K]&=1+\mathbb{E}[B],\\ \mathbb{E}[B]&=\Pr(L)\mathbb{E}[B\mid L]+\Pr(\neg L)\,0,\\ \mathbb{E}[K]&=1+p_L\,\mu_{B\mid L}. \end{aligned} \tag{3}E[K]E[B]E[K]​=1+E[B],=Pr(L)E[B∣L]+Pr(¬L)0,=1+pL​μB∣L​.​(3)

    这是我对论文式 1 的严谨读法：第二个因子必须是在已经落地的条件下，实际存入输出的平均 token 数。若把它换成整个词表的平均展开长度，就把验证前后的两个分布混在了一起。被选中的条目不服从词表均匀分布，被接受的前缀更不服从。

    用主实验的 token/pass 和 landing 反推，大头在 GSM8K、MATH-500、MT-Bench 上每次 landing 的平均接受量分别约为 2.23、2.19、1.54。这只是我对报告数字的复算，不是新测量。它说明跨域损失不只是第一步更难猜；即使已经猜中第一步，后续能保住的长度也在下降。

    对一条长度为 mmm 的候选路径，设 aia_iai​ 为前面都匹配时第 iii 个 token 也匹配的条件概率，则

    E[B]=∑j=1mPr⁡(B≥j)=∑j=1m∏i=1jai.(4)\mathbb{E}[B]=\sum_{j=1}^{m}\Pr(B\ge j) =\sum_{j=1}^{m}\prod_{i=1}^{j}a_i. \tag{4}E[B]=j=1∑m​Pr(B≥j)=j=1∑m​i=1∏j​ai​.(4)

    第一步使用非负整数变量的尾和公式，第二步只是条件概率链式法则，不要求各位置独立。若为了说明取所有 ai=aa_i=aai​=a，就得到 a(1−am)/(1−a)a(1-a^m)/(1-a)a(1−am)/(1−a)。增加尾部长度的收益逐渐变小，尤其当前几个 token 很难预测时。前缀树则要把单一路径事件换成至少一条有效路径存活到相应深度，不能把各条目的收益简单相加。

    图 3. 根据式 4 绘制的数学说明图，并非模型实验。单路径、各位置条件匹配率相同的假设下，低匹配区间增加展开长度帮助有限。这张图不用于估计论文真实的树接受率。

    5.2 token/pass 为什么不能直接当加速比

    令普通目标解码每 token 时间为 t0t_0t0​，完整一次草稿与验证的时间为 tPt_PtP​，包括摊销的展开与缓存工作。在输出相近、解码足够长的条件下，有

    S≈t0 E[K]E[tP]=1+pLμB∣L1+δ,δ=E[tP]−t0t0.(5)S\approx\frac{t_0\,\mathbb{E}[K]}{\mathbb{E}[t_P]} =\frac{1+p_L\mu_{B\mid L}}{1+\delta},\qquad \delta=\frac{\mathbb{E}[t_P]-t_0}{t_0}. \tag{5}S≈E[tP​]t0​E[K]​=1+δ1+pL​μB∣L​​,δ=t0​E[tP​]−t0​​.(5)

    这里是总工作除以总时间，不是逐轮 speedup 的平均。困难位置可能既接受少、又产生更大的树，若平均比值，就会扭曲这种相关性。回本条件是 pLμB∣L>δp_L\mu_{B\mid L}>\deltapL​μB∣L​>δ：多接受的工作，必须超过额外耗时。

    GSM8K 的表 5 给出一次短语验证 41.16 ms，普通目标步为 36.06 ms，前者约为后者的 1.141 倍。用 2.730 token/pass 除以 1.141，得到约 2.392，与表 1 的 2.391 在舍入范围内一致。这验证的是表间算术关系，不是独立验证 GPU 测速，也不意味着提高 batch 后比例仍相同。

    这个表达式也解释了小头的价值：它可能比大 drafter 少接受一些 token，但如果额外时间更低，最终效率仍然有竞争力。反过来，接受量更高也可能不值，因为每多一个草稿步骤都要串行读取另一套权重。真正该比较的是两条曲线共同组成的工作点。

    5.3 长度不同，时间比值就不同

    设基线与加速版输出 token 总数为 T0,TAT_0,T_AT0​,TA​，平均每 token 时间为 m0,mAm_0,m_Am0​,mA​，并令 Δ=TA/T0−1\Delta=T_A/T_0-1Δ=TA​/T0​−1，则

    Stime=m0T0mATA=m0mA(1+Δ).(6)S_{\mathrm{time}}=\frac{m_0T_0}{m_AT_A} =\frac{m_0}{m_A(1+\Delta)}. \tag{6}Stime​=mA​TA​m0​T0​​=mA​(1+Δ)m0​​.(6)

    只有输出长度相同，直接相除 ms/token 才等于总时间加速。论文的共享基线比较采用了这样的长度校正。对于声称保持贪心行为的方法，这个量尤其应该与实际 token 相等率一起报告，让读者知道差异来自浮点、EOS 还是统计边界。

    表 1 的 MT-Bench 写出 35.528 与 22.27 ms/token，直接相除约为 1.595，但报告总时间加速为 1.544。若加速输出总量多约 3.3%，就能解释这组舍入数之间的差别；论文没有提供完整逐条长度，因此我只将它标作需要补充配对数据的地方，不据此判断结果有错。把两个指标区分清楚，比强行让表中每个数字满足一个简化比值更有意义。

    6. 参数预算：词表究竟花掉了什么

    6.1 固定头与每个条目的一行

    论文给出目标宽度 d=2560d=2560d=2560、隐藏宽度 H=256H=256H=256 时，固定头需要 2dH+H2+6H2dH+H^2+6H2dH+H2+6H 个参数，每个输出条目再增加 H+1H+1H+1 个，因此

    P(V)=2dH+H2+6H+(H+1)V,=1,377,792+257V.(7)\begin{aligned} P(V)&=2dH+H^2+6H+(H+1)V,\\ &=1{,}377{,}792+257V. \end{aligned} \tag{7}P(V)​=2dH+H2+6H+(H+1)V,=1,377,792+257V.​(7)

    代入 8,000 条目得到 3,433,792，代入 80,000 得到 21,937,792，与论文表 3 相符。输出层分别占约 59.9% 和 93.7%。词表缩小十倍，总头参数却只缩小约 6.39 倍，因为固定部分仍然存在。

    图 4. 根据论文表 3 的参数公式重绘，区分固定头与条目相关输出层。它表示权重参数，不包含目标 KV、验证临时行、激活或优化器状态。

    若只存一份半精度权重，两个头大约需要 6.87 和 43.88 十进制 MB。这是我的权重容量复算，不是进程显存实测。论文里的 0.0854% 和 0.5454% 是相对于目标参数量，而不是整个服务系统显存的比例。对这么小的头，缓存训练隐藏特征反而可能比权重更占空间，这一点在在线实验里已经变成实际限制。

    6.2 92.3% 保留的是哪个量

    小头在 GSM8K 的 token/pass 为 2.520，大头为 2.730，两者之比约为 92.3%。但小头每 token 时间是 16.67 ms，大头是 15.08 ms，小头仍慢约 10.5%。如果只关心草稿额外贡献，还要扣掉目标自身至少产生的一个 token：

    K8k−1K80k−1=2.520−12.730−1≈87.9%.(8)\frac{K_{8k}-1}{K_{80k}-1} =\frac{2.520-1}{2.730-1}\approx87.9\%. \tag{8}K80k​−1K8k​−1​=2.730−12.520−1​≈87.9%.(8)

    所以三个数字应该并排理解：总 token/pass 保留约 92.3%，草稿增量保留约 87.9%，每 token 时间增加约 10.5%。不能把其中一个数字写成保留了 92.3% 的加速效果。这个区别对小模型、小缓存和低秩压缩也常常有用：分母里固定不变的部分，会让保留比例看起来更高。

    论文表 8 的词表扫描还说明，词表大小不是单调规则。40k、16k、8k 头在 T4 上比较时，小头在 MT-Bench 可以优于 40k；但主实验的 80k 头又优于较小头。因此不能归纳成词表越小迁移越好。条目数量、每类监督频率、领域和拟合程度互相影响，需要控制变量来区分。

    6.3 我会怎样评价一个条目的价值

    高频容易统计，但不是完整的部署目标。一个条目是否值得保留，要看它多常被选中、额外接受多少 token、增加几行验证，以及占用多少参数。一个说明性的净时间价值可以写成

    U(u)=t0 ΔE[B∣u]−ΔE[tP∣u]−λ ΔP(u).(9)U(u)=t_0\,\Delta\mathbb{E}[B\mid u] -\Delta\mathbb{E}[t_P\mid u]-\lambda\,\Delta P(u). \tag{9}U(u)=t0​ΔE[B∣u]−ΔE[tP​∣u]−λΔP(u).(9)

    这是我提出的设计目标，不是作者的训练损失。这里一定要用边际量：候选共享前缀后，某个条目的成本取决于已有集合。一条独立看很长的候选，若前缀已经存在，可能只多一行；另一个高频条目若产生大量新分支，则可能很贵。

    下一步比较词表时，我会同时固定参数预算、训练位置预算和独立验证行数。只固定候选条目个数，无法区分究竟是单位选得好，还是实际给了更多验证计算。这个约束也能迫使系统明确：词表是为了压缩文本表示，还是为了减少目标模型的真实耗时。

    7. 主实验能支持怎样的比较

    7.1 先看实验边界

    主实验使用 Qwen3-4B、fp16、单张 NVIDIA A5000，batch 为 1，temperature 为 0，遇 EOS 停止并设置 2,048-token 上限。数学蒸馏训练意味着 GSM8K、MATH-500 属于域内，MT-Bench 是跨域迁移。测试分别只有 50、50、40 个 prompt，不是完整基准的全量结论。

    表 1 为每组任务选择最佳候选数：GSM8K 和 MT-Bench 为 32，MATH-500 为 16。较大头的报告加速为 2.391、2.444、1.544。它们使用该实验的 HuggingFace generate 基线。论文另一些表使用自己的 drafting-off 循环，另一些又换了目标模型和 MTP；这些分母不能混成一列比较。

    作者还指出，EAGLE-3 和自己的运行环境使用不同 Transformers 版本，普通生成基线就相差若干百分点，同一张卡多次运行也有漂移。表 2 把结果归到共同基线，改善了可比性，但共同数字分母不能消除两个环境分开运行的实验混杂。尤其是几个百分点的差异，不应该在缺少置信区间时被写成稳定胜负。

    表 6 换成 Gemma 4 E2B 和 T4，短语方案与模型自带 MTP 各自选择最佳 NNN。短语方案在列出的英文任务都落后，在 Hindi、Bengali、Tamil 获胜，Telugu 略低于 MTP。其中 AIME 明确是非配对结果，不能混进一个总体平均优势。

    论文用 token/pass 乘以转换效率分解速度：短语方案每次前向的额外成本更小，但接受量不及大 drafter。这个解释有道理，尤其串行草稿会反复增加读取权重的成本。不过进一步说剩下的差距只在语料、不在架构，就超过了实验隔离出的因果范围：容量、数据、词表与训练流程并没有交叉控制。

    7.4 小样本比较需要保留原始配对记录

    小样本足以证明机制能工作，也能发现大的差距，却不适合精确解释 2.704 与 2.757 的排序。最佳 NNN 若在报告样本上选择，还会出现选择偏乐观。更有用的是保存每个 prompt 的基线秒数、加速秒数、输出长度、pass 数、接受长度直方图和 token 是否一致。

    计算总体加速时，应对配对 prompt 的总时间比值做重采样，不能把每条 speedup 直接平均。短 prompt 与长 prompt 等权回答的是另一类问题。运行轮次的噪声也要与 prompt 差异分开，避免一个置信区间掩盖系统性的库版本差异。论文已经主动指出分母脆弱，我认为后续应该围绕这个问题把数据组织得更完整。

    8. 实验诊断：真正被利用的结构是什么

    8.1 数学格式承担了主要收益

    图 6. 根据论文表 4 的条目类别份额重绘。Other / not itemized 为 100 减去五个已列类别的余额。来自三单位条目的份额与这些类别重叠，不作为另一个互斥类别堆叠。

    GSM8K 中，标点与 LaTeX 合计占 banked token 的 57.4%，MATH-500 为 63.1%；普通单词只有 7.3% 和 5.5%。到 MT-Bench，LaTeX 降至 11.7%，普通单词升至 22.6%。这不是抽象的领域差异，而是分类头可利用的结构换了：数学续写里有稳定的格式骨架，对话里这种骨架弱得多。

    词表统计也要注意集合关系。小词表的多单位条目中，43.9% 含 LaTeX 字符、55.0% 含数字、24.7% 含换行，一个条目可以同时满足几个条件，不能直接相加。三单位条目的贡献又与标点、公式等类别交叉。若把这些比例画在同一个饼图或堆叠条形图，就会造出根本不存在的互斥划分。

    我会据此设计一个很直接的对照：相同参数与验证行数下，格式专用词表、语义短语词表和混合词表各能拿回多少收益？也许数学任务的大部分优势只需要更小的格式词表；也许对话迁移需要专门给常见词与领域术语分预算。这些是由现有证据引出的实验方向，不能写成已经得到的结果。

    8.2 验证行数便宜，是当前工作区间的现象

    图 7. 根据论文表 5 重绘。左边是平均独立树行数与完整 pass 时间，右边区分普通目标步与额外时间。三个点同时更换了任务和最佳候选数，属于描述性对照，不是严格控制的扩展曲线。

    平均树行数从 21.8 到 46.3，pass 时间却都在约 40 ms，符合低 batch 解码受权重带宽限制、增加行可以复用权重的直觉。但不能由此推出任意增宽都几乎免费：任务也同时变化了，而且这些行数可能恰好处在 kernel 的平坦容量区间。

    表中额外峰值显存为 0.73、0.72、0.26 GB，与树行数并不单调。上下文长度、临时 buffer 和 allocator 统计口径未知时，不应拟合一个普适的每行显存成本。小头权重只有几 MB，不意味着整个方法只增加几 MB。对 8 GB 设备，零点几 GB 的临时开销已经可能影响是否能运行。

    高并发时，原本闲置的计算资源可能已经被其他请求使用。验证树行会与普通 decode token 竞争算力和 KV 空间，单请求更快也可能使整体 goodput 下降。所以这篇的 batch-one 结果首先是低负载延迟证据，尚不是有 SLO 约束的服务容量证据。

    8.3 在线更新提高 landing，还没证明总耗时回本

    图 8. 重绘论文表 7 的前三个检查点。三个面板使用各自纵轴，不比较视觉斜率。词表同时增长，因此它不是固定容量下的纯适应实验。

    词表从 40,000 增至 43,261、45,719，landing 从 0.736 到 0.759、0.764；token/pass 先升后停，speedup 则从 2.180 到 2.214 再到 2.201。作者没有冻结头对照，也只跑一个 seed，自己把它称为尚未完成的工作。我赞同这种克制：landing 在改善，并不等于可重复的速度提升已经成立。

    用式 7 计算，增加 5,719 个条目就多了 1,469,783 个输出层参数，约为初始 11.658M 头的 12.6%。这是我的算术复算。容量和覆盖一起变化，不能把曲线改善全部归给在线训练。更干净的下一步，是保持词表大小固定，用替换策略对照冻结头。

    作者报告每块词表更新约 3–4 秒、MLP 更新约 5 分钟，相比约 2.4 小时流式运行看起来不贵。但若更新是额外串行时间，单看 300/8640300/8640300/8640 就约为 3.5%；表里最好一次 speedup 相对初始只提高约 1.6%。即使某段 decode 更快，整个流的墙钟也可能还没回本。若更新发生在闲时或可重叠，口径会不同，应另报实际关键路径和能耗。

    图 9. 根据论文表 9 重绘。左侧为报告的 token/pass，右侧为我用 speedup 除以 token/pass 得到的转换效率。实验固定 GSM8K prompt 文件与草稿头，比较三个候选数。

    9. 局限与失败边界

    最清楚的经验边界是分布。数学蒸馏头不能自动变成通用对话、代码或个人写作 drafter。现在的词表分析很好地解释了格式红利，却没有验证论文展望的个人助理场景。提示模板一变，格式片段的频率也可能变；混合任务中应保留便宜的 drafting-off 退路，而不是强制所有位置都走草稿。

    统计边界也很具体：一个 seed、50/50/40 个 prompt、缺少置信区间，再叠加几个百分点的基线漂移，不足以支持细小而稳定的名次判断。共享分母能帮助读表，却没有消除环境和时间漂移。未配对的 AIME、各任务自己选择最佳 NNN 的过程，都应该留在结论附近。

    算法边界是贪心验证的条件。冻结权重只是其中一项，正确的 mask、位置、KV 提交、停止行为和数值设置同样必要。论文没有穷尽这些接口细节。遇到非零温采样，也不能沿用 argmax 匹配的证明，必须另建分布保持规则。

    跨语言空间更多是待测预测问题。高 fertility 意味着单次猜中可能带回很多 token，但并不说明小分类器就能猜中。作者也指出，Indic 实验多在切分相对友好的 Gemma 目标上完成，更碎的 Qwen 场景尚未充分测量。文中更高的潜在加速目标属于展望，不是现有结果。

    资源边界则提醒我不要只盯头参数。目标权重、KV、树验证临时空间、训练特征和持续能耗都参与部署约束。在线更新目前只增长词表、没有淘汰，特征预算也覆盖不了全部生成位置。它能说明一种方向值得继续，却还不能证明设备端长期适应已经经济可用。

    10. 批判性分析：我会优先修改和验证什么

    10.1 用存活前缀分布替代平均展开长度

    我的第一个建议是，按条目类别公开接受前缀长度直方图，而不只给 landing 和词表平均展开。若最大表示深度为 MMM，一般形式是

    E[B]=∑j=1MPr⁡(some valid candidate reaches depth j).(10)\mathbb{E}[B]=\sum_{j=1}^{M}\Pr(\text{some valid candidate reaches depth }j). \tag{10}E[B]=j=1∑M​Pr(some valid candidate reaches depth j).(10)

    这能同时处理前缀重叠：十个条目共享前两个 token，系统也只能接受一次这两个 token，不能把十份期望收益相加。每个 pass 记录候选条目数、独立目标行、最长存活路径、名义展开长度和接受量，就能看清增加词表究竟改善了第一步预测，还是延长了尾部，或者只是制造更多冗余分支。

    举一个完全说明性的例子：长度六的候选，第一步匹配概率为 0.2，后续条件匹配均为 0.9，按式 4 其期望接受量约为 0.937；长度二的候选，两个条件概率都为 0.8，期望接受量为 1.44。前者名义长度是三倍，实际有用工作反而更少。这不是论文新实验，而是说明为什么词表压缩率不能直接作为候选价值。

    10.2 数据瓶颈需要与容量和结构分开

    论文有充分证据说明当前词表受数学语料影响，但没有充分隔离出剩余差距只由语料造成。分类容量、类别不平衡、表征能力和预测深度都可能限制结果。一个只读取当前隐藏状态的分类器，不能像串行 drafter 那样，在下一步猜测里显式利用自己上一步的猜测。

    我会做三个交叉对照：固定头结构增加独立训练位置；固定数据改变词表；固定词表改变头宽度。验证行预算相同，候选数在另外的验证集上选择。还可以把同样的格式条目给检索基线。如果检索已拿回主要收益，小头可能主要在做便宜的选择器；若神经头对新上下文持续改善，才更支持表示学习解释。

    架构搜索里的失败结果仍然有信息，只是它属于某一组预算与语料。更精确的说法应该是：当前简单头把已有接受工作转换得很高效，但接受工作不足究竟由什么造成，还需要独立实验。这样的表述不会削弱现有结果，反而把下一步问题说得更清楚。

    10.3 将数值一致性变成一个可报告结果

    我会让理论保证和实际 token 相等率出现在同一张结果表。固定目标后端、dtype、停止规则，在同一组 prompt 上比较 drafting off 与 on。每次首次分歧记录 token 位置和目标前两名 logits 的间隔，才能区分近似平局与路径、位置或停止语义错误。这里只提出行为实验，没有声称已经运行模型完成这种区分。

    还应包含前导空白、组合字符、数字标点和特殊 token 外观字符串，检验展开接口。正确行为是：候选不合适就拒绝，仍由目标 fallback 前进。这样的边界并不是要改目标 tokenizer，而是要证明草稿端的新符号确实能接回原接口。长度校正的存在，也使这些记录比一条泛泛的输出无损声明更有解释力。

    10.4 把在线更新写成回本条件

    设未来解码量折算成普通目标运行时间为 WWW，冻结头加速比为 SFS_FSF​，适应后为 SAS_ASA​，额外串行更新耗时为 CCC。更新值得做的条件为

    WSF>WSA+C,W>C1/SF−1/SA,SA>SF.(11)\frac{W}{S_F}>\frac{W}{S_A}+C, \qquad W>\frac{C}{1/S_F-1/S_A},\quad S_A>S_F. \tag{11}SF​W​>SA​W​+C,W>1/SF​−1/SA​C​,SA​>SF​.(11)

    用表里的 2.180 与 2.214，并说明性地取 C=300C=300C=300 秒，阈值约为 42,600 个基线等效秒，也就是约 11.8 小时。这是使用报告点估计的算术例子，不是生产预测。第二次更新的速度增益更小，对应回本时间还会更长。若更新可以利用闲时，关键路径上的 CCC 会降低，但总能耗、内存和训练工作不能因此消失。

    这能保留在线结果真正有价值的部分：landing 的上升是值得跟进的信号，却还没有证明当前流的端到端时间收益。下一次应同时报告纯 decode 与总墙钟，后者包括特征采集、词表维护和拟合；并且保持固定词表容量，区分更新与扩容。

    10.5 从无限增长改成固定容量替换

    增加条目会扩大输出矩阵，也会改变 logits 之间的竞争。长期运行的设备需要替换规则。一种可测方案是，用衰减的实际节省时间评价条目，扣除训练和额外验证成本，再与纯频率或 LRU 对照。目标是固定内存下节省多少时间，不是词表条目能否单调增长。

    替换还要考虑稳定性：新条目可能分走旧短前缀的概率，即使旧条目仍有用。单独预留槽位，未必解决分数校准。可以按条目年龄、领域记录接受工作，同时加入词表冻结、只更新头的实验臂。这样才分得开是覆盖变好，还是预测变好。

    真正进入个人设备时，还可能需要避免把敏感片段长期留在词表中，或设置条目过期规则。我将其视为从研究原型走向持久化个人使用时的设计约束，而不是论文已经测到的缺陷。它不影响当前小头机制成立，但会影响哪些条目可以被当作长期资产。

    10.6 用实际验证行预算控制候选数

    按任务选择最佳 NNN 是一个研究工作点，混合请求流需要在事前决定策略。一个便宜的控制器可以结合头置信度和近期接受率，选择关闭草稿或几个宽度。说明性的判断规则为

    pLμB∣L^(x,N)>δ^(x,N)+η.(12)\widehat{p_L\mu_{B\mid L}}(x,N)> \widehat{\delta}(x,N)+\eta. \tag{12}pL​μB∣L​​(x,N)>δ(x,N)+η.(12)

    其中 η\etaη 是估计误差留量。这是我的建议，不是论文已经评估的控制器。数学头在陌生文本上可能很自信却猜错，近期接受率也可能滞后于领域切换，所以仍要用真实请求分布校准。

    更公平的候选比较还应固定独立验证行，而不是只固定条目数。共享前缀可以让新条目几乎免费，长而不共享的条目则可能多出很多行。高并发时，进一步固定到达负载与延迟目标，测完成请求的 goodput 和 KV 占用，才能知道单请求收益是否仍然帮助整个服务。

    10.7 一个有顺序的后续评估方案

    我会先在当前 Qwen 工作负载补齐 token 相等率与完整时间边界，交错重复计时；再在相同参数、行数、训练位置预算下比较格式词表与语义词表；之后用冻结头、仅更新头、固定容量替换、只增不减四组实验区分在线机制；最后才去目标移动后端测持续性能、内存和能耗。

    总体统计采用

    S^=∑it0,i∑itA,i,(13)\widehat{S}=\frac{\sum_i t_{0,i}}{\sum_i t_{A,i}}, \tag{13}S=∑i​tA,i​∑i​t0,i​​,(13)

    对 prompt 做配对重采样，并另外报告计时轮次差异。每个采样单元保留长度、EOS 状态和 exact-match 标记。词表大小与 NNN 的选择放在独立验证集；系统性环境差异另做控制，不能靠一个置信区间自动抹去。

    这些实验围绕一个明确问题展开：在给定头、语料、内存与目标 kernel 预算下，改变草稿单位，究竟能多带回多少经过验证的目标工作，是否足够支付成本？论文已经提供了一个有说服力的正例。后续需要的是把适用边界测出来，而不是把潜在展开长度提前兑换成加速结论。

    11. 结论

    我会把这篇记成一个关于接口解耦的好例子：草稿端可以用更合适的符号表达未来，执行端仍严格遵循原目标模型。小头借用目标隐藏状态，在数学格式这种可预测结构上取得了明确的参数效率收益。

    阅读时最需要分清三个量：三个正则单位不一定是三个自然语言词，平均展开长度不等于实际接受长度，token/pass 的保留比例也不等于速度保留比例。较宽的 EAGLE-3 在主实验三个任务上仍更快；在线更新改善 landing，但总时间回本和移动部署还属于待完成部分。

    对我自己的研究，最值得借鉴的下一步是把词表与验证器一起设计：按边际接受工作和真实行成本选条目，明确贪心数值契约，在目标负载下测完整时间。这样才能从一个漂亮的表示想法，走到可重复、可部署的系统结论。
