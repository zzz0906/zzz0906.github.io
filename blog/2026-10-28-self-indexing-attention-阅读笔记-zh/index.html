    Self-Indexing Attention：一组符号位，怎样同时服务检索与压缩？

    笔记日期： 2026-10-28
    论文： Self-Indexing Attention for Compression-Compatible Sparse Long-Context LLM Inference
    作者： Xu Yang、Jiapeng Zhang、Yuxin Chen、Feiqiang Sun、Chengguang Xu、Feng Jin、Zhuo Tang
    版本与日期： arXiv:2609.13205v2，2026-10-07
    资料： 论文页面 · 本次精读 PDF · 全文

    1. 先问一个具体问题：检索索引能不能就是缓存的一部分？

    长上下文推理同时面对两笔账。第一笔是计算和读取：当前 query 到底要看哪些历史 token？第二笔是存储：为了让以后可能出现的 query 还能访问这些历史，key 和 value 要以什么形式留下来？稀疏注意力主要减少前一笔，KV cache 压缩主要减少后一笔。把两者放在一起，成本却未必自动相加地下降。

    例如，检索器可能另存一套索引；压缩器可能把检索所需的高精度 key 信息抹掉；选出 token 后，随机解码这些缓存条目又可能很慢。于是，看似便宜的选择器和看似紧凑的缓存，各自都成立，连接起来却增加了额外的内存、解码和数据搬运。

    Self-Indexing Attention 的想法很集中：先把 key 变换到一个适合低比特表示的坐标系，再把每个坐标的符号保留为一位。检索时，比较 query 和 key 的符号；真正计算注意力时，再用同一份符号和压缩后的幅值重建 key。索引没有额外复制一份相同的信息，而是直接成为 key 存储格式中的一个字段。[1，第 2–3 节]

    这个设计里有三层不同性质的结论。共享正交变换在精确算术下不改变原始注意力；符号打分与 query 池化只是近似选择重要 token；选中条目的幅值和 value 量化又会引入数值近似。只有第一层有代数上的严格等价，不能把这份严格性顺手延伸到后面两层。

    论文报告的结果也要分层读。在 Qwen3.6-35B-A3B 上，不压缩数值字段的稀疏版本 LongBench 平均分为 61.84，dense 为 61.44；存储预算匹配的组合版本为 60.88，对应压缩基线为 60.91。算子层面，64K prefill 达到 6.1 倍加速，64K、batch 8 的 decode 达到 10.3 倍。换成完整 Qwen3.5-9B，所报告负载下首 token 时间加速是 1.35 倍，稳定 decode 吞吐提升是 1.23 倍。[1，表 1–2、图 6]

    所以，这篇论文最值得读的不是“把 attention 变成一位运算就能快十倍”，而是如何让检索表示和缓存表示共享信息，以及这种共享在什么条件下划算。下文的实验数值都来自作者；小型反例、误差界、字节计算和后续实验建议属于我的分析，不是额外测得的结果。

    图 1：原论文第 3 页图 2。符号位既是检索索引，也是压缩 key 的组成部分；幅值和 value 仍交给数值压缩器处理。若 value 也旋转，输出端需要对应的逆变换。

    2. 前置知识：注意力、缓存读取与 GQA

    对于一个 query，记 q∈Rdq\in\mathbb R^dq∈Rd，历史 token 的 key、value 为 ki,vik_i,v_iki​,vi​，当前位置允许访问的因果集合为 Ct\mathcal C_tCt​。dense attention 计算的是

    ℓi=qki⊤d,pi=exp⁡(ℓi)∑j∈Ctexp⁡(ℓj),y=∑i∈Ctpivi.(1)\ell_i=\frac{qk_i^\top}{\sqrt d},\qquad p_i=\frac{\exp(\ell_i)}{\sum_{j\in\mathcal C_t}\exp(\ell_j)},\qquad y=\sum_{i\in\mathcal C_t}p_i v_i. \tag{1}ℓi​=d​qki⊤​​,pi​=∑j∈Ct​​exp(ℓj​)exp(ℓi​)​,y=i∈Ct​∑​pi​vi​.(1)

    这里不能忽略 softmax 的分母。删掉一个 token，改变的不仅是它原来贡献的那一项，剩下 token 的概率还会重新归一化。因此，“保留很多重要 token”和“输出完全相同”不是同一件事。即使保留了较大注意力质量，仍要看被删 value 与留下 value 的方向和幅度关系。

    prefill 一次处理大量 query，适合矩阵运算，但因果注意力的潜在 query–key 配对数随序列长度平方增长。decode 每步只增加少量新 token，却需要反复访问很长的历史缓存，内存带宽和可容纳的并发请求数就更加关键。同一个数学操作，在这两个阶段面对的瓶颈并不完全相同。

    GQA，即 grouped-query attention，让多个 query head 共享一个 KV head。设 G=Hq/HkvG=H_q/H_{kv}G=Hq​/Hkv​，每组有 GGG 个不同 query，它们看的是同一份历史 key/value，但各自的注意力分布仍然不同。本文利用这种已有的共享关系摊薄检索开销；它没有把多个 head 的最终注意力输出合并成一个输出。

    读这类论文时，最好始终区分三个预算。存储预算是全部驻留缓存的字节数；检索预算是为了提出候选，需要扫描多少历史表示；最终 attention 预算是有多少条目的数值 key/value 被解码并参与计算。第三项变小，不代表前两项消失。Self-Indexing Attention 保留完整的压缩历史，并扫描其中的符号位；它既不是永久驱逐旧 token，也不是一次哈希查表就能完成的常数时间检索。

    论文主要质量实验使用约 5% 的 attention density，同时设定最少 768 个 token 的预算，并在预算内保留前缀与近期窗口。最低预算会改变短上下文下的实际密度：768 占 16K 历史的约 4.69%，却占 8K 历史的 9.375%。这只是预算算术，不是新的实测配置。再加上 tile 对齐、前缀与窗口重叠、逐行因果过滤，实际访问数还会偏离一个简单的“固定 5%”。

    3. 共享旋转：什么是严格成立的，什么只是动机？

    3.1 先做 RoPE，再进入共同坐标系

    对每层 lll、每个 KV head hhh，论文固定一个随机化 Hadamard 变换：

    Rl,h=Dl,hHnorm,Hnorm=Hd,Dl,h=diag⁡(ϵ1,…,ϵd).(2)R_{l,h}=D_{l,h}H_{\rm norm},\qquad H_{\rm norm}=\frac{H}{\sqrt d},\qquad D_{l,h}=\operatorname{diag}(\epsilon_1,\ldots,\epsilon_d). \tag{2}Rl,h​=Dl,h​Hnorm​,Hnorm​=d​H​,Dl,h​=diag(ϵ1​,…,ϵd​).(2)

    变换施加在已经做完 RoPE 的 query 和 key 上。这个顺序很重要：真正定义 attention logits 的是带位置信息的向量。若先做任意旋转再做 RoPE，就要额外证明两种变换如何交换；本文的顺序直接避开了这个问题。

    采用行向量记号，令 Q′=QRQ'=QRQ′=QR、K′=KRK'=KRK′=KR，则

    Q′K′⊤=(QR)(KR)⊤=QRR⊤K⊤=QK⊤.(3)Q'K'^\top=(QR)(KR)^\top =QRR^\top K^\top=QK^\top. \tag{3}Q′K′⊤=(QR)(KR)⊤=QRR⊤K⊤=QK⊤.(3)

    每个 logit 都保持不变，softmax 权重自然也不变。如果 value 留在原始坐标系，直接使用原始 value 即可。若为了压缩而把 value 也变为 V′=VRV'=VRV′=VR，输出端需要乘回 R⊤R^\topR⊤：

    3.3 为什么符号位要原样留下？

    变换后的 key 被拆为 zi=si⊙miz_i=s_i\odot m_izi​=si​⊙mi​，其中 si=sign⁡(zi)s_i=\operatorname{sign}(z_i)si​=sign(zi​)，mi=∣zi∣m_i=|z_i|mi​=∣zi​∣。符号只做无损 bit packing，不再有损量化；幅值和 value 才交给外部数值压缩器。检索读这份符号，选中后重建 key 仍读这份符号。

    论文用变换随机性下近似平衡的符号位来解释这种选择。但“期望上近似平衡”不意味着部署后每一段符号流都达到最大熵，更不意味着不同 token 或不同坐标彼此独立。把这点分清，才能避免把表示设计的经验理由写成不成立的信息论保证。

    更直接的工程原因是：一个符号翻转会同时影响两条路径。它既改变重建后的 key，又可能改变离散的 top-k 选择。幅值误差同样重要，但保留精确符号后，幅值量化至少不会直接改变选择器所读的符号字段。这让检索与数值重建之间有了一条相对稳定的接口。[1，第 3.3 节]

    4. 符号检索：少读数值，不等于不扫描历史

    设变换后 query 的符号为 sQs^QsQ，缓存 key 的符号为 siKs_i^KsiK​。先统计同号坐标数，再减去阈值、截断负值，并乘回 key 范数：

    a(q,i)=∑j=1d1[sjQ=sijK],ϕ(q,i)=max⁡{a(q,i)−τ,0} ∥ki∥2,τ=d2.(6)a(q,i)=\sum_{j=1}^{d}\mathbf 1[s_j^Q=s_{ij}^K],\qquad \phi(q,i)=\max\{a(q,i)-\tau,0\}\,\|k_i\|_2, \qquad \tau=\frac d2. \tag{6}a(q,i)=j=1∑d​1[sjQ​=sijK​],ϕ(q,i)=max{a(q,i)−τ,0}∥ki​∥2​,τ=2d​.(6)

    Qwen 实验的 d=256d=256d=256，所以阈值为 128。只看符号，主要保留方向信息：两个方向相同但范数不同的 key 会拥有同一个码。乘上 key 范数，是把原始点积中的尺度因素补回来。对于单个 query，它自己的范数在所有候选之间一样，不影响排序；但这不意味着整个代理分数等于原始点积，尤其不能直接延伸到多个 query 池化的情况。

    bit packing 之后，一致数可以写成 d−popcount⁡(SQ⊕SK)d-\operatorname{popcount}(S_Q\oplus S_K)d−popcount(SQ​⊕SK​)。也可以分别统计“两位都为一”和“两位都为零”的位置。若最后一个机器字没有填满，需要屏蔽无效位，不能把补齐位置算进分数。换成正负一表示，二值内积为 2a−d2a-d2a−d，因此减去 d/2d/2d/2 再截断，相当于取二值内积的正部分，差一个固定比例。

    好处是选择阶段不必计算高精度 QK，可以利用紧凑的符号缓存和二值矩阵运算。代价则是坐标内的幅值被抹掉。范数加权之前，一致数只有 d+1d+1d+1 种取值；阈值之下又全部变成零，很容易出现并列分数。附录中的确定性遍历规则能让并列处理可重复，却不能让一个本来没信息的并列更有语义。

    由此能直接看出一种失败边界：如果重要远端 token 与池化码的一致数都不高，系统可能主要依赖强制保留的前缀与局部窗口，剩余远端名额则被大量并列候选占据。增大预算或许有帮助，但只是让更多候选有机会被读到，并没有让原先的排序更准确。

    范数项也存在取舍。不乘范数会忽略尺度，乘上后又可能让大范数、角度稍差的 key 超过小范数、角度更好的 key。真实点积本来就依赖范数，所以不能把这种现象一概说成错误。真正需要实验证明的是：粗糙且经过截断的角度估计，与范数结合后，在不同层、head 和上下文上是否仍是好用的选择依据。

    “索引”这个词还容易让人误以为已经实现次线性查找。实际上，每个 query group 仍然要扫描相关历史的符号字段。若机器字宽为 www，直观的打包比较需要约 O(Ld/w)O(Ld/w)O(Ld/w) 个字级操作，还要读取范数并做 top-k；二值矩阵指令主要改变常数与批处理效率。选中的数值 attention 从每行约 O(Ld)O(Ld)O(Ld) 降为 O(kd)O(kd)O(kd)，但历史扫描这一项仍在。

    因此，它减少的是“为了 attention 读取和计算完整数值 key/value”的成本，而不是消灭上下文长度带来的所有成本。只有把符号扫描、选择、随机取数、解码和最终 attention 一起算进去，才能判断实际收益。

    5. 压缩预算：所谓免费索引，免费在哪里？

    选出 token 后，系统只需解码这些条目的数值字段。重建的变换域 key 可以写成

    z^iK=siK⊙DK(ciK),ciK=QK(miK),ciV=QV(vi).(7)\widehat z_i^K=s_i^K\odot D_K(c_i^K),\qquad c_i^K=Q_K(m_i^K),\qquad c_i^V=Q_V(v_i). \tag{7}ziK​=siK​⊙DK​(ciK​),ciK​=QK​(miK​),ciV​=QV​(vi​).(7)

    其中 QK,DKQ_K,D_KQK​,DK​ 是幅值编码与解码，QVQ_VQV​ 处理 value。如果数值量化先做归一化，重建时还要使用对应范数。这里真正要求的是一个接口：符号必须直接可读，选择器所需的范数要可用，任意选中的条目要能高效解码。只是“都用了低比特”远远不够。

    论文里的命名尤其值得仔细看。独立 TQ1 是 key 一位、value 四位；“Ours + TQ1”则是 key 的一位符号，加一位幅值，再配四位 value。完整 key 实际占两位。因此，后者在存储预算上更应该和 key 两位、value 四位的 TQ2 对比，而不能说它和独立 TQ1 的总位数相同。[1，附录 F、表 11]

    以 d=256d=256d=256 计算，每个 token、每个 KV head：TQ2 的 key 为 256×2/8=64256\times2/8=64256×2/8=64 字节，value 为 256×4/8=128256\times4/8=128256×4/8=128 字节，总 payload 192 字节。自索引加一位幅值则是符号 32 字节、幅值 32 字节、value 128 字节，仍然是 192 字节。两种匹配格式都再保存同样的四字节范数，得到 196 字节，尚未计共享的量化器元数据。

    图 3：按附录 F、表 11 的格式做字节计算。两种匹配格式都是 192 字节 payload，并各自加上四字节范数。独立 TQ1 只用于说明名称差异，不能当成存储完全匹配的对照。

    这就是“没有额外索引元数据”的准确含义：相对于这种完整 key 格式，索引复用了本来就要保存的符号字段。它不等于缓存没有元数据，也不等于任何压缩器都能无成本接入。如果一个 codec 把各坐标联合编码、隐藏符号，或者使用不兼容的旋转，甚至只能顺序高效解码，那么它可能需要重排格式、改变数值量化方法，或者承担额外随机访问成本。

    另一条路线是给任意压缩缓存再配一份独立二值索引。这样选择器有更大设计自由，却会多占字节，也可能重复存储信息。还可以先解码高精度 key 再检索，换取更好的排序，但这等于在知道哪些 token 有用之前先读更多数值。本文选择共享的符号接口，就是在这两种开销之间做取舍。

    还要强调，它保存的是完整压缩历史，不是只保存这一步选中的 k 个 token。当前 query 不需要某个旧 token，并不说明未来 query 也不需要。对持续增长的 agent 轨迹来说，这个区别直接决定方法是在减少每次访问量，还是在不可逆地丢失历史。

    6. 共用候选集，不共用最终注意力

    6.1 为什么用 absmax-sign？

    如果 prefill 中每个 query 都独立扫描全部符号，选择阶段本身仍然昂贵。论文在同一 KV head 内把 64 个 query 向量分组，先跨 GQA heads，再跨邻近位置做池化。若每个 KV head 对应 GGG 个 query heads，一组大致覆盖 64/G64/G64/G 个位置。不同 KV head 可能使用不同变换，不能把它们当成同一坐标系随意混池化。

    平均值会抵消符号。例如同一坐标上四个 query 值为 +9,−8,+1,−2+9,-8,+1,-2+9,−8,+1,−2，均值为零，却不能据此说没有强烈的正向需求。absmax-sign 在每个坐标选择绝对值最大的那个值，再保留其符号：

    u∗(j)=arg⁡max⁡u∈B∣q~u,j∣,sjB=sign⁡(q~u∗(j),j),q~u=quR.(8)u^*(j)=\arg\max_{u\in\mathcal B}|\widetilde q_{u,j}|, \qquad s^{\mathcal B}_j=\operatorname{sign}(\widetilde q_{u^*(j),j}), \qquad \widetilde q_u=q_uR. \tag{8}u∗(j)=argu∈Bmax​∣q​u,j​∣,sjB​=sign(q​u∗(j),j​),q​u​=qu​R.(8)

    理想目标是找出“至少对组内一个 query 很重要”的 key，也就是依据 max⁡u∈Bquki⊤\max_{u\in\mathcal B}q_uk_i^\topmaxu∈B​qu​ki⊤​ 之类的分数排序。absmax-sign 是一个便宜的替代办法，不是在精确计算这个最大值。[1，第 3.4 节]

    图 4：原论文第 5 页图 3。absmax-sign 避免把最大幅值方向直接平均掉，但不同坐标最终保留的符号可能来自不同 query。

    6.2 一个两维反例：保住强坐标，不一定保住重要 key

    考虑已经处于变换域的两个 query：q1=(10,−9)q_1=(10,-9)q1​=(10,−9)、q2=(−9,10)q_2=(-9,10)q2​=(−9,10)。池化后符号为 (+,+)(+,+)(+,+)，第一个正号来自 q1q_1q1​，第二个来自 q2q_2q2​。再比较两个等范数 key：kA=(1,1)/2k_A=(1,1)/\sqrt2kA​=(1,1)/2​，kB=(1,−1)/2k_B=(1,-1)/\sqrt2kB​=(1,−1)/2​。

    与池化码比较，kAk_AkA​ 有两个一致位，kBk_BkB​ 只有一个。维度为二时阈值为一，所以代理分数偏向 kAk_AkA​，而给 kBk_BkB​ 零分。但真实的组内最大点积，kAk_AkA​ 只有 1/21/\sqrt21/2​，kBk_BkB​ 却达到 19/219/\sqrt219/2​。对某个 query 很有用的 key，完全可能输给一个更符合“拼接出来的符号码”的 key。

    这不是说 Qwen 里经常出现这个精确例子。它说明的是保证缺在哪里：逐坐标挑出的赢家不一定属于任何真实 query，也不保持组内最大相关性的排序。方法能否有效，依赖真实 query group 是否有足够一致的结构。缩小分组、保留多个池化码、让某些 head 独立检索，都是可能的替代方案，但会增加选择成本或占用更多候选预算。

    6.3 因果过滤必须回到每一行

    组内共享候选集可能包含对前面几行而言尚未出现的 token。最终 attention 前必须逐行过滤。记组候选为 IB\mathcal I_{\mathcal B}IB​，位置 ttt 的合法近期窗口为 Lt\mathcal L_tLt​，论文给出的结构可写为

    IB,t=Lt  ∪  {i∈IB:i<t−∣Lt∣+1}.(9)\mathcal I_{\mathcal B,t} =\mathcal L_t\;\cup\; \{i\in\mathcal I_{\mathcal B}:i<t-|\mathcal L_t|+1\}. \tag{9}IB,t​=Lt​∪{i∈IB​:i<t−∣Lt​∣+1}.(9)

    前缀已经包含在组候选里；当前位置自己的近期窗口补上合法的近邻。集合并集去掉重叠，历史边界则排除未来位置，并避免远端部分重复占用局部窗口。之后，每个 query head 使用自己的 query 算 QK 和 softmax，而不是使用池化 query 直接产生最终输出。

    这会带来一个容易漏掉的实验细节：过滤之后，前面某些 query 的实际 token 数可能少于名义预算；tile 对齐又可能让访问数向另一个方向变化。因此，“同样 k”不一定意味着同样的实际计算量。严格对比应该看因果过滤、去重和对齐之后，实际读了多少独立历史条目。论文的诊断实验专门对齐了这个有效数量，这比只报告一个抽象预算更可靠。

    7. 把两阶段流程写清楚

    下面的伪代码按数学数据流重新整理原文，重点区分“提出候选”和“最终合法 attention”。它不是某个具体内核的逐行描述。前缀和局部窗口都包含在名义预算里，不能在比较成本时把它们当作免费的额外 token。

    算法 1：分组 prefill 与自索引缓存

    输入：已做 RoPE 的 Q、K，V；每个 KV head 的固定变换 R；
      总预算 k、前缀集合 P、近期窗口长度 w。
01. 对每个 KV head，计算变换后的 key：ZK = K R。
02. 保存精确打包符号 sign(ZK) 和所需的 key 范数。
03. 用选定压缩器编码 key 幅值和 value。
04. 若 value 也旋转，则编码 V R，而非原始 V。
05. 对共享一个 KV head 的每组 64 个 query 向量：
06.   用该 head 的 R 变换 query。
07.   跨 heads 和位置做逐坐标 absmax-sign 池化。
08.   扫描 key 符号，计算阈值化、范数加权后的分数。
09.   保留前缀 P，并为逐行局部窗口预留预算，形成远端候选。
10.   对组内每一行 t：
11.     只保留位于该行合法历史、且不重复局部窗口的候选。
12.     与该行近期窗口取并集，去掉重复下标。
13.     只解码这些条目的数值 K/V。
14.     使用该行自己的 query 计算 QK、softmax 和 value 和。
15.     仅当 value 曾旋转时，对输出乘 R 的转置。
输出：各 query 的 attention 输出，以及完整压缩缓存。

    缓存构建覆盖所有 token，数值解码却只针对选中的条目。第 11–12 步不是可有可无的整理工作，而是保证因果性、去掉重复访问的必要步骤。第 14 步同样关键：共享的是候选提案，最终分布仍属于每个真实 query。若把池化后的符号码误当作实际 query，就变成了另一种方法。

    算法 2：单步 decode 与当前 GQA 组

    输入：当前新 query heads、新 key、新 value；完整压缩缓存；
      总预算 k、前缀 P、近期窗口长度 w。
01. 用固定 KV-head 变换 R 处理新 key。
02. 将其符号、范数、压缩幅值和 value 追加到缓存一次。
03. 用同一个 R 变换共享此 KV head 的当前 query heads。
04. 只跨当前 heads 做 absmax-sign，不跨解码时间池化。
05. 构造合法强制集合 F = 前缀与当前近期窗口的并集。
06. 对 F 之外的合法历史符号计算范数加权代理分数。
07. 在剩余 k - |F| 预算内选择额外下标，并处理对齐。
08. 解码选中数值 K/V，复用共享缓存读取。
09. 每个 query head 独立计算自己的 logits 和 softmax。
10. 累加 value；若使用旋转 value，则撤销该旋转。
输出：当前 attention 输出，以及增加一个 token 的缓存。

    decode 只池化同一步的多个 query heads，不池化未来时间，也不是把过去 query 一起平均。未来 query 尚未出现，过去 query 又未必在问当前的问题。缓存追加只做一次，因为同一 KV head 下多个 query heads 共享该缓存，不能按 query head 重复追加。

    短历史还需要处理有效集合不足的问题：预算不能超过合法独立 token 的总数。如果强制前缀与窗口已经覆盖大部分历史，额外 top-k 就不应机械地补出重复下标。论文的最低预算、局部窗口与 tile 对齐规则，都是具体运行配置的一部分，不能替换成一个不带边界条件的固定比例。

    从系统角度看，作者描述了二值矩阵运算、融合选择，以及支持 GQA 的 selected-KV attention 路径。它们的重要性在于，廉价打分如果仍然生成巨大的中间分数表，或者额外扫描几遍内存，最终也可能很贵。伪代码暴露的是这些成本环节，而不是宣称一次 popcount 就决定了整条路径的耗时。[1，第 4 节、附录 F]

    8. 选错 token，怎样传递成输出误差？

    “保留注意力质量”这个指标可以通过一个简单推导变得更直观。设选中集合为 S\mathcal SS，其在原 dense softmax 中的总概率为 m=∑i∈Spim=\sum_{i\in\mathcal S}p_im=∑i∈S​pi​。当 0<m<10<m<10<m<1 时，分别把选中和遗漏部分归一化，得到输出 ySy_SyS​ 和 yRy_RyR​。如果选中部分的 logits、value 都还精确，则

    y=myS+(1−m)yR,yS−y=(1−m)(yS−yR),∥yS−y∥2≤2Vmax⁡(1−m)若 ∥vi∥2≤Vmax⁡.(10)\begin{aligned} y&=m y_S+(1-m)y_R,\\ y_S-y&=(1-m)(y_S-y_R),\\ \|y_S-y\|_2&\le 2V_{\max}(1-m) \quad\text{若 }\|v_i\|_2\le V_{\max}. \end{aligned} \tag{10}yyS​−y∥yS​−y∥2​​=myS​+(1−m)yR​,=(1−m)(yS​−yR​),≤2Vmax​(1−m)若 ∥vi​∥2​≤Vmax​.​(10)

    第一步只是把 dense 加权和分成两部分。第二步从稀疏输出中减去 dense 输出。第三步使用三角不等式：两边都是范数不超过 Vmax⁡V_{\max}Vmax​ 的向量的凸组合，所以二者之差最多为 2Vmax⁡2V_{\max}2Vmax​。若 m=1m=1m=1，选择本身没有误差。这是解释性的上界，往往较松，不能直接代入论文数值去预测 NRMSE。

    它说明了为什么只看召回多少 token 不够。遗漏的概率越小通常越好，但如果遗漏 value 与留下 value 的平均方向接近，即使遗漏质量较大，输出也可能变化很小。反过来，少量低频但方向特殊的 value，可能对输出很关键。token 命中率、保留概率质量、输出误差和最终答题分数，应当作为相关但不同的指标来观察。

    如果选中条目还经过量化，记精确选中输出为 ySy_SyS​，实际输出为 y^S\widehat y_Sy​S​，则

    ∥y^S−y∥2≤∥y^S−yS∥2+∥yS−y∥2.(11)\|\widehat y_S-y\|_2 \le \|\widehat y_S-y_S\|_2+\|y_S-y\|_2. \tag{11}∥y​S​−y∥2​≤∥y​S​−yS​∥2​+∥yS​−y∥2​.(11)

    前一项包含选中 key 的 logit 扰动与 value 重建误差，后一项是选集改变带来的误差。好的变换可以让量化更稳定，却不能补回完全没被选中的证据；好的符号选择能找到证据，也不能保证压缩 value 精确无误。所以，组合系统在下游分数上改善，并不能单凭一个总分就判断究竟是哪一部分改善了。

    还有一个接口层面的交互：当前方法的选择器读取精确符号与范数，最终内核读取解码后的数值。如果换一个压缩器时顺便改变了符号提取基底或范数定义，选择器本身就不再是同一个选择器。这也是“兼容”必须包含表示约定、不能只看位宽的原因。

    9.2 RULER：接近 dense，但并非所有任务都一样

    论文在 16K、32K、64K 上测了 NS3、NM3、CWE、FWE、QA2 五类任务。Qwen3.6 的 64K dense 分别是 100、100、99.90、99.33、68；Self-Indexing 是 100、99、100、98.67、70；压缩组合版本是 100、99、99.60、98.67、69。这支持在这些任务和长度下接近 dense 的判断。[1，表 2]

    其中一些任务也能区分不同选择器。相同设置下，Quest 的 NM3 为 75，SI-KV 为 96，本文为 99；CWE 上 SI-KV 为 92，本文为 100。相比“平均都差不多”，这些具体任务的差异更有诊断意义。但满分附近的检索任务本身又缺少空间揭示细微损失，不能仅凭接近 100 分就断言所有长上下文能力都被保留。

    在较小的 Qwen3.5 上，64K dense 的 CWE 为 79.50，本文为 79.90；dense QA2 为 66，压缩版本为 64；dense FWE 为 100，压缩版本为 96.67。对一个只关心宏观平均的读者，这些看起来不大；对依赖某一类远端证据的实际应用，它们可能就是需要进一步测量的部分。

    还要区分长度与内容分布。合成 needle、词频统计和包含多轮修订指令、相似实体、过期信息的 agent 轨迹，未必会给选择器相同压力。论文的任务组合提供了有价值的证据，但还没有证明它一定能在任何长对话里找到最新且权威的那条指令。

    10. 消融实验：机制线索很强，统计覆盖仍有限

    10.1 池化与每 head 随机化

    表 3 报告四种配置的输出 NRMSE：不带 per-head flips 的平均池化为 8.1590%，加 flips 后为 7.7751%；absmax 不加 flips 为 7.4469%，二者结合为 7.1283%。在这个诊断里，两种改变都帮助降低误差，组合最好。

    方向上，它符合设计动机：平均值容易把符号抵消；不同 head 使用独立随机化，可以避免所有 head 被同一坐标模式限制。但四个数并不自动构成跨分布、跨任务的统计证明。附录说明它们来自同一个长 prompt 中抽取的 query rows；同一文档里很多 head、位置的测量，不能当成很多独立文档样本。

    距离精确 top-k 仍有可见差距，这说明改进候选提案还有空间。与此同时，输出误差下降与保留质量上升并不成简单比例；根据前面的推导，value 几何和重新归一化都会影响输出。这正是需要同时看选中了谁、保留多少 dense 概率、输出如何改变，以及最终答案是否正确的原因。

    相对原始 key，随机化 Hadamard 的 key 误差下降约 24.5%，QK 误差下降约 44.1%；相对普通 Hadamard，下降幅度只有约 2.9% 和 2.5%。两种比较都值得看，但它们回答的问题不同。大部分收益来自更适合量化的基底，随机符号在这个诊断里带来较小的额外收益。

    对应的 QK 余弦相似度从原始的 0.9545，提高到几种旋转下约 0.9817–0.9818。数值很接近，仍不能保证 top-k 边界附近的排序一致：两个本来几乎一样的 logit，小扰动就能交换先后。连续重建指标和离散选择结果，必须分开解释。

    11. 速度：选择器、attention 算子、整模型是三层账

    11.1 算子计时包含了哪些工作？

    论文的效率图并不是让一个免费 oracle 先把下标选好，再只计时很小的 attention 矩阵。所报告稀疏路径包括变换、token 选择、稀疏 attention，以及可选的逆变换。主设置为 BF16、head dimension 256；dense prefill 使用 FlashAttention-3，dense decode 使用 FlashInfer。算子计时做三次预热、十次测量，采用同步后的中位延迟。[1，图 6、附录 C.1、F]

    图 7：原论文第 9 页图 6。上面两个面板是算子比较；下面是 Qwen3.5-9B 完整模型，在 64K、batch 4、输出 256 token 下的结果。TTFT 看延迟，steady decode 看吞吐，不能当成同一种指标。

    batch 1 的 prefill，在 8K、16K、32K、64K 上分别加速 3.7、5.3、5.9、6.1 倍。相同长度下 batch 1 decode 分别是 2.1、2.2、2.5、3.0 倍。固定 64K 后，batch 2 为 4.6 倍、batch 4 为 6.8 倍、batch 8 为 10.3 倍；batch 8 的长度扫描则是 4.5、5.6、6.9、10.3 倍。

    这种变化本身就是结果，不能只留下最大的 10.3。更大的 decode batch 让完整缓存流量更贵，也改变了选择和稀疏执行的摊销空间；prefill 则有不同的矩阵计算与访存比例。短上下文里，固定开销和最小 token 预算占比可能更大，收益自然不一定与长上下文相同。

    作者还描述了评测平台上二值矩阵吞吐约八倍的优势，以及每组 64 个 query 带来的选择摊销。这些可以帮助解释选择器为什么便宜，但不能直接相乘后宣称是整系统加速。范数读取、top-k、数据布局、同步、gather、解码和最终 attention 都还要耗时。硬件是否支持相同二值运算、维度是否合适，也会改变可达到的常数。

    这里有一个重要的复杂度边界。每组扫描历史，确实比每个 query 都做高精度 QK 便宜得多；但当 prompt 变长，组数也增加，每组要看的历史也增加。固定分组大小下，prefill 选择仍保留平方级的历史评分结构，只是常数显著下降。因此，论文的收益主要是表示、批处理和硬件路径共同带来的实用加速，而不是把所有长序列工作都改成了线性复杂度。

    11.2 为什么整模型只快 1.35 倍和 1.23 倍？

    Qwen3.5-9B 的 32 层中只有八层使用 full attention。其余层以及非 attention 运算保持原样。在 64K、batch 4、输出 256 token 的配置下，十次运行均值给出 TTFT 加速 1.35 倍、稳定 decode 吞吐提升 1.23 倍。八层占 25% 是层数比例，不是“attention 恰好占运行时间 25%”的测量。

    如果被优化部分原来占总耗时比例 fff，它自身加速 sss 倍，一个理想化串行模型给出

    Stotal=1(1−f)+f/s.(12)S_{\rm total}=\frac{1}{(1-f)+f/s}. \tag{12}Stotal​=(1−f)+f/s1​.(12)

    推导很直接：把原总成本归一化为一，没变的部分仍是 1−f1-f1−f，变快的部分成为 f/sf/sf/s。仅作解释，若 f=0.4f=0.4f=0.4、s=6.1s=6.1s=6.1，总加速约为 1.50 倍。但论文没有报告这里假设的 0.4，不能把它写成实测，也不能从 full-attention 层比例直接推出来。

    同理，5% density 意味着最终 attention 读的 token 大幅减少，并不意味着整模型就快二十倍。符号扫描还在，选择有成本，稀疏访问可能不如连续访问规整，未改变的模型计算又设置了上限。实际部署要问的是：在自己的 batch、上下文长度与输出长度下，省下的数值缓存读取，能不能覆盖新增的整条选择路径。

    还要分清低延迟与饱和吞吐。服务满负载时每秒输出更多 token，可能同时改变排队行为；孤立算子中位延迟和后文的洪峰负载测试回答的是相关但不同的问题。把各处最大收益拼成一个统一“加速倍数”，反而让结果难以用于决策。

    12. DeepSeekV4-Flash：这是另一种索引缓存替换实验

    12.1 换了什么，没有把哪种结果混进来？

    在 DeepSeekV4-Flash 中，实验把原生 FP8 indexer key cache 换成 128 维变换后 key 的一位符号缓存。原生权重、query 构造、主 KV cache 和后续 sparse attention 保留，top-512 也保持相同。这条集成路径对 query 独立打分，不采用 Qwen 的跨 query 分组；对应阈值为 64。[1，附录 A、F]

    只看索引 key payload，128 个 FP8 坐标是 128 字节，128 个符号位是 16 字节，理想上减少八倍。但这不是整个模型缓存或总显存减少八倍。主 KV 字段、元数据、权重、运行缓冲都仍然存在。这组实验展示了符号索引的另一种用途，不是 Qwen 上“符号加幅值加 value”的完整压缩格式实验。

    64K LongBench Pro 上，DeepSeekV4-Flash 原生平均分为 64.1，一位符号版本为 64.2。同图里的 Qwen3.6 从 57.5 变为 60.5，Qwen3.5 从 33.8 变为 33.5。平均数可以帮助定位整体水平，但要判断“能力有没有保留”，附录的 128K 细分更加重要。

    12.2 总分几乎不变，任务表现却发生了交换

    图 8：原论文附录 A、第 14 页图 8。128K LongBench Pro 的一次运行，括号中是该任务类别样本数。总分几乎一样，却同时存在明显上升和下降的类别。

    整体从 0.5677 到 0.5679，差距极小。但 evidence QA 从 0.400 升到 0.700，aggregation 从 0.529 到 0.635；consistency checking 从 0.280 降到 0.171，dialogue memory 从 0.500 降到 0.300。retrieval/ranking 从 0.812 到 0.765，sequence reconstruction 从 0.915 到 0.876，rule induction 从 0.680 到 0.627；structured numerical reasoning 在这次运行中保持 0.550。

    所以，可以说“这次运行的整体平均相近”，不能说“各项能力都被无损保留”。这些类别里有的只有十个样本，有的二十个，差异可能同时含有较大抽样波动与真实的任务敏感性。需要配对的逐例结果、重复运行与适当置信区间，才能更好地区分二者。

    AIME 2025 使用三十道题、十六次运行，共 480 个采样答案。原生答对 234 个，为 48.75%；一位符号版本答对 228 个，为 47.50%。差六个答案，即 1.25 个百分点。不能把 480 个答案当成 480 道互相独立的题，因为同三十个问题被重复采样。做统计推断时，应保留问题层面的聚类与方法间配对结构。

    这组结果的价值恰恰在于，它提醒我们检索近似会改变错误分布。对重视证据问答的应用和对重视长期对话记忆的应用，相同总分未必意味着相同风险。论文没有提供足够证据把这种任务级交换概括成统一的提升或统一的退化。

    12.3 2P1D 部署：显存收益怎样变成服务收益？

    部署测试使用 DeepSeekV4-Flash（0731），两台机器上运行两个 TP4 prefill worker 和一个 TP4 decode worker。洪峰测试有 144 个请求，每个约 128K 输入、32K 输出。关键对比是在两边都启用 HiSparse 的条件下进行，而不是把 HiSparse 自身的收益也归给符号索引。[1，附录 A、表 5]

    图 9：据原表 5 重绘。每组两柱都使用 HiSparse，比较原生 indexer cache 与一位符号缓存。这里是服务部署结果，不是单个 attention 内核计时。

    decode pool 容量从 1500 万 token 增至 2010 万，约增加 34%；饱和并发从 71 增至 96，约增加 35%；吞吐从 1821 增至 2116 token/s，约增加 16.2%；端到端 goodput 从 1362 增至 1666 token/s，约增加 22.3%；测试时间从 56.4 分钟降至 46.1 分钟，约减少 18.3%。

    原生但不使用 HiSparse 的配置只有 533 万 token 的 decode pool 容量，未能完成这次洪峰测试。它说明了容量背景，不能拿来作为一个已成功完成运行的分母，计算漂亮的端到端加速比。相同 HiSparse 下的两个成功配置才是更合适的主要对照。

    这也展示了内存与吞吐之间并非线性关系：单个索引字段减少八倍，变成总池容量增加 34%，再变成较小的吞吐提升。更多请求能够驻留，不代表计算、通信、调度和生成过程都能同比例加快。作者也指出，dense 方案若采用压缩 KV cache，同样可以为并发腾出空间；因此还应在相同服务约束下，与其他节省内存的方案比较。

    若要把这个结果用于自己的服务，需要进一步知道请求到达分布、排队延迟、goodput 的具体约束和服务目标。否则，“在洪峰下总完成更快”和“单个用户更快拿到回答”仍然不能画等号。本文已有端到端证据，但部署契约还可以描述得更完整。

    13. 局限与失败边界

    首先，候选提案本身有损。符号丢掉坐标幅值，阈值丢掉负向信息，池化又把多个 query 拼成一个合成码。两维反例说明这是数学上真实存在的边界，只是不能据此估计实际发生频率。邻近 query 关注不同实体，或同组 heads 承担不同远端检索职责时，值得特别检查。

    其次，压缩兼容性是有条件的。选择器要求直接访问符号、使用一致的变换基底、拿到正确范数，还要求任意选中条目能够高效解码。一个非常擅长顺序读取、却不擅长随机解码的 codec，可能吞掉节省的 attention 成本。论文的匹配格式支持这一格式上的结论，尚不能证明对所有联合向量量化表示都同样成立。

    第三，完整历史工作并没有消失。符号缓存扫描、范数流量和 top-k 随历史增长，完整压缩 KV 也仍然驻留。分组让 prefill 的选择常数小很多，却没有消除组数与每组历史长度共同增长的结构。若未来上下文再扩展一个数量级，新的瓶颈可能从数值 attention 转移到选择路径。

    第四，证据覆盖仍有限。主要机制消融集中在少量 prompt，固定变换 seed 和有限模型家族不能代表所有分布。论文文字讨论了其他随机 seed 下较小的变化，但主表缺少足以判定细小平均分差距的完整不确定性信息。128K 任务细分已经展示：整体平均接近，不足以消除尾部能力变化的疑问。

    第五，系统收益依赖具体条件。二值矩阵吞吐、top-k 融合、tile 大小、full-attention 占比、batch 和内存组织都会影响结果。维度 256 与长上下文负载是明确而有利的评测条件；别的维度、缺少对应内核的平台、低延迟服务目标，可能移动盈亏平衡点。“无需训练”只是说不必重新训练模型，不代表没有集成、调参和运行点选择成本。

    最后，数值等价只属于未选择、未量化时的旋转代数。实际系统有意近似 attention。接近参考的 benchmark 分数是有用的工程证据，却不提供敏感检索、版本追踪或长期会话记忆上的逐输出保证。

    14. 批判性分析：怎样把这项工作进一步做扎实？

    14.1 最强的贡献是表示接口，而不是最大加速倍数

    我认为这篇论文最有延展性的贡献，是让“检索元数据”和“压缩 key 数据”不再必须是两个分离对象。符号变成一个清晰字段，选择器与数值 codec 就可以通过它对接。相比一个特定硬件上的峰值加速，这个接口设计更容易启发后续工作。

    但接口也限制了双方。最优的压缩器可能偏好隐藏符号的联合编码，更好的选择器也可能想用可学习投影或更细的 head 统计。本文选了一个实用的共同表示，而不是证明这个共同表示对两边都最优。后续工作应测量：省下的索引字节与读取，是否足以补偿这种约束损失的精度或自由度。

    这样看，也更容易区分三种改进。保持接口而降低幅值量化误差，是数值表示改进；在相同扫描成本下提高保留质量，是检索改进；让额外显存真正转化成更好服务，是部署改进。把它们分别报告，比只给一个组合总分更能说明方法为什么有效。

    14.2 我希望看到怎样的对照矩阵？

    一个更干净的实验可以交叉四个因素：独立 query 与池化 query；普通与随机化 Hadamard；dense 与符号提案选集；未压缩与完整位数匹配的数值字段。所有格子保持相同前缀和局部窗口规则，并记录实际独立、合法的历史 token 数。

    这样能把变换的量化收益、符号选择的排序质量和分组的速度收益拆开。压缩对照尤其要固定完整 K/V 位数：独立一位 key 和“一位符号加一位幅值”之间的比较，可以说明系统效果，却不能单独解释选择器贡献。选择器对照也不能只固定名义 k，因为对齐后若读取数量不同，成本就没有对齐。

    每个格子至少同时报告保留的 dense 注意力质量、选中输出误差、逐例配对的下游分数、选择器延迟和完整算子延迟。精确 top-k 仍可以当质量上界，但不把它包装成同成本的快速基线。这是一套建议的验证设计，不是论文已经完成的额外实验。

    还有一个更细的接口实验值得做：保持符号字段、query 分组和 token 下标完全相同，只替换幅值/value codec，观察数值误差与随机解码成本。若结果很好，才能更有力说明“选择器和数值压缩器可以独立改进”；若换 codec 后需要同时改范数或坐标定义，就应明确承认接口没有完全解耦。

    14.3 平均之外，要测试哪些尾部情况？

    128K 任务细分给出了明确方向：某些应用更在意 consistency checking 或 dialogue memory，而不是平均 QA。一个系统可以保持 benchmark 平均分，同时改变自己常犯哪类错误。因此，我更希望看到按任务设定损失容忍阈值、按文档或问题做配对 bootstrap、以及多次生成运行。重采样单位应是问题或文档，不应把同一问题的重复答案、同一文档的多个 head 都当成独立样本。

    对检索而言，特别值得增加相似实体混杂、同一文档多个版本、很晚才出现的纠正、远离局部窗口且只出现一次的关键证据。这些样例直接施压于“组候选能否满足每个独立 query”，比单纯增加长度、同时让任务仍然很容易，更能暴露失败机制。

    一种可能的自适应办法，是在组内分歧较大时保留两个或更多池化码，同时固定最终数值 attention 的总预算。另一种是只给部分 heads 或层缩小分组。前者增加符号扫描与候选合并，后者减少摊销，二者都要画在质量与延迟的权衡曲线上，而不是当成没有代价的修复。

    还可以观察零分候选比例和 top-k 边界并列程度，作为选择器失去区分力的诊断信号。但从诊断信号走到安全回退策略仍需要实验：更多随机候选、扩大局部窗口、临时使用更精确打分，会消耗不同资源，也可能偏向不同任务。这些都应标为后续设计，而不是本文已经验证的功能。

    14.4 部署要给出清楚的成本分解

    如果要决定是否上线，我希望 profile 能分出变换、符号扫描、范数访问、top-k、gather/dequantization、selected attention，以及没有改变的模型计算。测试应覆盖不同上下文与 batch、混合 prompt 长度、冷热缓存，并明确硬件。服务侧还应记录排队延迟和在具体目标下计算 goodput 的方法。

    现有整模型与 2P1D 实验已经比孤立内核曲线前进了一步。下一步最有价值的，不一定是把峰值再抬高，而是画出一个可使用的区域：哪些输入输出规模、哪些质量约束、哪些服务目标能同时满足。这样，读者才能比较共享符号、换一个压缩器、扩大选集或减少池化，哪一种更值得投入内存和计算。

    15. 结论

    Self-Indexing Attention 提供了一条相当连贯的组合路线：共享正交基底保持原始 attention 的代数关系，精确打包的 key 符号同时承担检索和压缩 key 重建，分组提案与二值打分摊薄两阶段选择开销，最终只解码并读取选中的数值 K/V。

    它的边界也应该与优点一起保留。结构化变换的矩不能证明符号排序精确；absmax 避免平均抵消，却可能漏掉对单个 query 重要的 key；免费索引是相对特定 sign/magnitude 格式而言；很大的算子收益到整模型会缩小，而接近的平均分也可能掩盖任务级损失。

    对我而言，最重要的启发是：检索表示与缓存表示应该一起设计。论文在具体模型和运行条件下给出了支持这条路线的证据。接下来需要更扎实回答的，是有效 token 预算、完整位数匹配、任务失败尾部，以及从符号扫描到可用服务之间的全部成本。
