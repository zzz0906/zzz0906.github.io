    CAAS 阅读笔记｜怎样让 LLM 智能体的一整批任务更早完成？

    笔记日期 2026-11-15 UTC · 作者 Zhongzhu Zhou
    所读论文 Reducing Batch Makespan for LLM Agent Workloads through Inference–Environment Coordination
    论文作者 Wei Feng、Meiling Chen、Boxiao Chen、Lu Liu、Bin Zi、Libin Ye、Xingyu Lu、Lei Xu、Jun Zhou
    arXiv 2611.16661v1 · 版本日期 2026-11-12 UTC

    1. 一批任务为什么会等在最后几条轨迹上

    设想晚上跑一批代码智能体评测。每题先读代码，再调用搜索或执行测试，拿到结果后决定下一步。报表要等最后一题结束。当大多数题已经做完，GPU 可能空着，最慢的那题还有后续工具调用。此时再提高单轮解码吞吐，对下一轮什么时候能发起帮助有限。另一种情形出现在批次前段。运行器为了保护外部服务，只让三个样本入场。三个样本都在等工具时，即使推理引擎能接下更多工作，也得等这三个样本中的一个恢复或退出。

    这篇论文把推理服务和工具环境看成两个相互喂给对方工作的阶段。先用历史轨迹估算混合模型两个缓存池的配比，再用轨迹标签把后续轮次尽量发到保有缓存的副本，并在工作节点内提前处理有望复用的请求。运行器可以独立限制在场样本和正在运行的工具作业，最后由 CAAS（Chain-Advancing Action Scheduling）决定空出来的工具槽先交给谁。[1, §1、§3–4]

    图 1. 原图裁自 [1, Fig. 1]。样本在等待推理或工具时一直占一个样本槽。环境作业开始执行后才占环境槽。

    作者的实跑对照给出 10.4%–65.0% 的平均批次完工时间降幅。这个区间汇总的是组合方案。MCP-Atlas 上，换成优化后的 FCFS 版本已经拿到了大部分绝对时间收益，再更换工具调度规则带来 3.1% 或 8.5% 的进一步降幅。读这个结果时，我想追的是每一段收益对应哪个比较，以及一次调度动作何时能真正影响批次末尾。

    2. 前置知识

    完工时间怎样由单个请求组成

    用 aia_iai​ 和 fif_ifi​ 表示任务 iii 的入场与终止时刻。在一条串行轨迹的第 kkk 步，xi,kx_{i,k}xi,k​ 是实际推理时间，yi,ky_{i,k}yi,k​ 是实际环境服务时间，ui,ku_{i,k}ui,k​ 与 vi,kv_{i,k}vi,k​ 是两边的排队时间。没有环境操作的步骤可令对应的两项为零。从第一条任务入场的 t0t_0t0​ 起计时，有

    从整批视角看，某任务还有一段入场前等待 ai−t0a_i-t_0ai​−t0​。入场更早可以抵消它在引擎里变长的排队。TTFT 看单个请求多快收到首 token，TPOT 看后续输出的平均步速。两个指标与 TTT 同时测量才知道代价落在哪里。比如把样本并发从 100 提到 250，可能让早期 GPU 工作更密集，却让每个短请求首 token 等得更久。只要最后完成的任务提前了，批次指标仍会改善。

    多轮轨迹还带来释放约束。一次工具调用的结果回来以后，模型才知道下一步的输入。手里即使还有一张空闲 GPU，也无法用它提前跑那个未来请求。调度提前了一个工具作业，改变的是下一轮工作变为可执行的时钟。工具服务本身可以一秒也没省。后面会用一条四秒的算例把这一点画出来。

    混合模型的两份缓存

    含注意力层的模型把前缀的键值或潜在表示保存在 KV 池。带递归层的模型还要保存对应前缀的状态快照。把更新写成 st=F(st−1,zt)s_t=F(s_{t-1},z_t)st​=F(st−1​,zt​)。已知位置 ppp 的正确快照 sps_psp​，就能用后缀 zp+1,…,zTz_{p+1},\ldots,z_Tzp+1​,…,zT​ 接着算，前提是模型权重、输入前缀和位置语义都匹配。若可用快照落在更早的位置，缺的那段必须重算。保住一份 KV 缓存，并不能弥补同一前缀所需的递归状态已经被淘汰。

    论文用 Ling-3.0-Flash 做受控回放。模型包含 KDA 与 MLA，回放的配置比例是 5:1，注意力侧缓存随着前缀增长，递归侧按槽分配。作者对一条不断追加内容的轨迹只保留最近一个可复用状态。这个做法遇到分支、回滚、上下文压缩或工具结果被回写时需要重新判断命中范围。轨迹标签可以指路，真正的复用仍要由前缀和缓存状态判定。

    三种并发量

    • CSC_SCS​ 是在场的样本数上限。从入场到退出，一条样本一直占槽。
    • CEC_ECE​ 是同时执行的环境作业数上限。等待槽位的作业只占着所属样本的槽。
    • CI⋆C_I^\starCI⋆​ 从推理节点的缓存容量推算，描述可同时让多少轨迹的两份状态留在缓存。它的量纲是样本。当前 API 请求数、GPU 的 decode 序列数和它各有各的计法。

    另一个容易漏掉的条件是工具作业内的扇出。一个调度槽拿到手以后，作业若会自己并发调用多个 API，加上超时重试，单看 CEC_ECE​ 可能保护不了某个端点的配额。论文先把环境抽象成一组任意作业都能使用的非抢占槽，方便分析政策变化。

    4. 网关决定去哪里，节点决定哪条先跑

    算法 1. 有负载约束的一致性哈希

    运行器为同一轨迹的各轮请求附上同一个标签。网关把标签哈希到环上，顺时针第一个节点是主副本。它维护各节点已有的推理请求数 L(w)L(w)L(w)，既算排队也算运行。若所有后续请求都回主副本，最新的两份状态更可能在手边。但若一簇长轨迹落在同一节点，旁边还有空余 GPU 也帮不上忙。作者用原文式 (9) 的门槛判断何时外溢：

    L(w)≤θ,θ=α(∑vL(v)+1)W,α≥1.(6)L(w)\le\theta,\qquad \theta=\frac{\alpha(\sum_vL(v)+1)}{W},\quad \alpha\ge1 . \tag{6}L(w)≤θ,θ=Wα(∑v​L(v)+1)​,α≥1.(6) 
    1. Map the trajectory label to the worker ring.
2. Find the clockwise home worker.
3. Read current loads and compute the eligibility threshold.
4. Visit home, then clockwise successors at most once each.
5. Send the request to the first eligible worker.
6. If the scan fails, use the home worker.

    式 (6) 分子中的 1 是本次正要路由的请求。左侧仍用候选节点的旧计数，所以通过检查后，节点计数可超过门槛。比如三个节点有 (8,1,2)(8,1,2)(8,1,2) 个请求，α=1.25\alpha=1.25α=1.25，门槛是 5。主副本已有 8 个，后面的 1 或 2 谁先在环上出现就交给谁。假定观察值是同一时刻的精确计数，至少一个节点不高于均值，因此原文保留的最后退路只在额外限制或读数不一致等实际条件下可能派上用场。

    我对这个选择的理解是用便宜的排队信号换取大部分可达的亲和性。真实工作量与请求数之间有距离，一个 200k token 的冷前缀和一个只需补几百 token 的热请求在计数里各是 1。外溢还有时序代价。一次外溢后，最新快照可能在临时副本，下一轮却仍优先回旧家。用最近落点可以保住这次复用，但一串轨迹也可能被锁在热节点。用预填充欠账估算负载需要额外测量。比较这几种策略时，我会同时记录外溢次数、最新可用快照在哪里，以及因此重算了多少 token。

    算法 2. 先按标签筛一轮，再按前缀排序

    标签集合 AAA 存的是最近被节点接纳进 batch 的轨迹，由 LRU 维护。每个等待请求第一次进入这一层时查 radix cache，记下命中的 token 数 ℓ(q)\ell(q)ℓ(q)。以后在排队期间重复打分可用同一份记录。tqt_qtq​ 是排队时刻，键值按字典序从小到大：

    6. 受控回放能回答什么

    图 8. 原图裁自 [1, Fig. 2]。回放使用相同的目标生成长度、工具服务时长和记录结果。模型仍然在测量环境中实际生成 token。

    7. 局限

    受控回放的优点在于可把需求按住。真实工具可能在一波请求后给出 429，几个相关任务一起重试。调度本身改变了这些事件发生的机会，固定时长的回放没有这一反馈。SWE 与 MCP-Atlas 只挑历史成功轨迹，丢掉了一部分可能极慢的失败样本。实跑保留所有任务，补上了最后阶段的外部效度，但各次工具返回和生成的内容不完全一样。读因果时，固定迹线和真实语义要互相补充。

    实验覆盖两种 Ling 混合模型和一套 GPU 系列。模型层类型比例、状态精度、缓存池层级、每条轨迹的上下文长度或环境资源的共享方式一变，几组调参点都可能移动。论文没有报告各对照的配对置信区间，也没有给出保质的非劣判定边界。例如 Ling-3.0 的 Opt-FCFS 与 Opt-CAAS 评分为 66.6 和 65.6。均分相近是有益观察，还需看这 1 分来自哪些题、重复运行的波动多大。真实并行工具或多代理的任务图还可能在同一轨迹中有多个后续分支，当前的串行释放假设会改变。

    CAAS 把已完成轮数作为未来长短的线索。我更想知道这条统计关系在哪个区间成立。给离散总轮数 NNN，当任务已经走到 nnn 轮，余下轮数的条件期望可以展开：

    E[N−n∣N≥n]=∑k=1∞Pr⁡(N−n≥k∣N≥n)=∑k=1∞Pr⁡(N≥n+k)Pr⁡(N≥n).(14)\begin{aligned} \mathbb E[N-n\mid N\ge n] &=\sum_{k=1}^{\infty}\Pr(N-n\ge k\mid N\ge n)\\ &=\sum_{k=1}^{\infty}\frac{\Pr(N\ge n+k)}{\Pr(N\ge n)}. \end{aligned} \tag{14}E[N−n∣N≥n]​=k=1∑∞​Pr(N−n≥k∣N≥n)=k=1∑∞​Pr(N≥n)Pr(N≥n+k)​.​(14)

    第一步把整数余量拆成各门槛的指示变量，第二步用「至少 n+kn+kn+k 轮自然也至少 nnn 轮」。若停止是几何分布，条件尾部与 nnn 无关，深度没有预测力。考虑一个混合例子，80% 的题两轮，20% 十二轮。第 1 轮余量平均为 0.8(1)+0.2(11)=30.8(1)+0.2(11)=30.8(1)+0.2(11)=3。能到第 3 轮的全是长题，余量变成 9；已经到第 11 轮，余量又降成 1。CAAS 可以在前段识别出幸存下来的长类，快到终点时按深度递增给优先级却会高估它。

    可以按工具类型、重试标记、任务源和当前深度分层，对剩余轮数、再释放一个推理请求的概率以及剩余服务时间画条件分布。拿同一批任务比较 FCFS、窄时间带和宽时间带、深度优先和带等待时间上限的剩余工作估计。若深度只能预测轮数，不能预测繁忙工具的耗时，就要用端到端剩余服务量定义对照。一个长链可能全是短检索，一个浅链也可能要等几分钟的独占构建。

    让优先规则在同一小图上失败一次

    沿用图 7 的所有到达时刻和环境时长，只改浅轨迹 S。让它拿到工具结果后还需 20 秒推理，并假设推理槽足够，不和 D 相互等待。FCFS 仍让 S 在第 8 秒拿结果，最后到第 28 秒；D 在第 22 秒完成。CAAS 则让 S 到第 12 秒才开始最后推理，于第 32 秒完成；D 还是第 18 秒结束。批次从 28 秒变成 32 秒，预测失误造成了相反结局。这个反例允许改变后继计算，不需要增加环境服务预算或改变两条作业深度。它说明用已完成的轮数切换优先级，真正赌的是谁手里还握着关键路径。

    对于单工种非抢占工具，时间带的宽度控制允许多少旧队列内部被重排。如果同一带有 KKK 条已知作业等待，单条工具服务时间都有已知上界 bbb，在单槽、无其它优先规则打断的简化条件下，同带重排引入的额外等待至多约为其余 K−1K-1K−1 条的服务上界和。可超越的时间戳跨度为 BBB，等待的量纲仍由服务时间和队列长度共同决定。真实数据中慢调用时间无稳定上界，工具重试也会形成同带或跨带的多次排队。若对用户暴露每题进度，除了监控完成尾部，我会量同带内等待增长最大的那一类样本，查看规则是否天然偏向有较多短轮的任务。

    用工作量下界定位真正的瓶颈

    给 CEC_ECE​ 个等价工具槽、整个批次工具总服务秒数 HEH_EHE​，它们即使无缝填满也要 HE/CEH_E/C_EHE​/CE​ 秒。设 PiP_iPi​ 为轨迹 iii 的串行服务时间和，忽略排队、同时也忽略该任务迟迟入不了场所花的时间，那么

    T≥max⁡{HECE, max⁡iPi}.(15)T\ge\max\left\{\frac{H_E}{C_E},\,\max_i P_i\right\}. \tag{15}T≥max{CE​HE​​,imax​Pi​}.(15)

    第一项来自把工具服务量平均摊到所有槽，第二项来自串行依赖不能并行执行。用图 7 的算例，时钟从 0 秒起，一开始在执行的占位作业也占 4 秒，因此工具总量 16 秒。D 从其工具可排队开始，自身串行服务至少 4+6+4=144+6+4=144+6+4=14 秒。两项分别约束资源总量和单轨迹。CAAS 的 18 秒更靠近 16 秒，FCFS 的 22 秒距下界更远。实际还有依赖释放和入场等约束，因为并不是每一秒都有可派发的下一单。若工具分为有独立配额的端点，则对每类各算一次工作量界再取最大。统一工具池的容量低估了热点端点排队的影响。

    我会在回放增加相关的网络波动和重试突发，而不是给每条调用分别加独立噪声。共享上游会让一组轨迹同时卡住。针对同一组任务，要比较开始、半数完成、95% 完成和全部结束的绝对时间，还可以跟踪相同 ID 的个体完工量。分析工具等待和任务失败时，使用配对批次重复或按共享事件阻塞抽样，避免把同一轮限流里几十条调用当作独立证据。调度收益如果来自更快地把题跑失败，应在按状态分解中可见。

    如果推理底座已经用了 FlashStates，哪些机制可以省掉？

    我会先省掉第 3 节的预设配比和配比扫描。FlashStates [6] 让 attention KV 和递归检查点从同一张 GPU 的缓存预算分配。式 (3) 的两类足迹之和仍可用来粗估驻留量。实际能放进多少样本，还要看在飞请求占用、共享 KV，以及加并发后要淘汰多少有用的混合状态。样本入场上限仍需实测。

    节点内的 RP 值得先试着拿掉。如果 FlashStates 的淘汰策略已经能让完整混合状态留到下一轮返回，靠插队赶在状态被淘汰前复用的收益可能会缩小。不过先跑热请求也会改变组 batch 与首 token 延迟，余下价值需要实测。多 worker 的路由是另一层问题。一个节点的缓存预算可以共享，轨迹换到另一个节点时仍可能丢掉亲和性。若副本之间的负载失衡明显，LBCH 仍有用武之地。

    工具侧我会先保留独立的样本入场上限与工具并发上限，派发用 FCFS。缓存做得更好，前缀重算会少，工具作业到达的时序也会变。外部配额和长链的串行依赖仍在。只有当工具队列仍然拥堵、长链继续拖住最后完工时间时，才值得加 CAAS 的深度优先。原文表 3 量的是原有推理栈上的增量，FlashStates 上能省多少，现有两篇论文没有直接测量。

    要知道剩多少复杂度值得留，我会固定模型、硬件、总缓存预算、任务和到达顺序，以及工具并发。先跑 FlashStates 加独立闸门，再分别测试单加 RP、单加 CAAS、两者一起加。多副本场景单测路由。第一轮固定样本并发以隔离机制，第二轮分别找各方案的入场上限。一起看未缓存预填充、工具排队、95% 完成时刻和整批完工时间，就能判断共享预算解决之后，剩下的时间花在哪里。

    固定画像之外，还要观察在场压力

    SWE 并发扫到缓存边缘，状态压力改变下轮工作量，工作量又改变在场时间。静态比值能告诉我们不可长期维持什么，到了陡坡附近可以观察单位时间新预填充 token、最近轨迹命中、等工具的样本比例和在场上下文分位数。降低 CSC_SCS​ 虽会让一部分任务晚入场，却可能减少驱逐带来的反复重算。若控制器刚看到排队缩短就立刻加样本，容易在两端振荡，设置迟滞或最短观察间隔才有可测的动态行为。

    路由、节点和工具可以首先分开诊断。对网关记外溢时的可用快照时间差，估计「为了负载均衡额外做了多少预填充」。对 RP 记前缀命中在排队期间失效的比例，分别试启动前有界重查、基于缓存代际失效，或者低优先层按等待年龄提升。对工具层记录每个端点的排队时钟和重试传播。这样即便最终还是用固定阈值，也能知道下一次异常来自热点工具、缓存压力还是工作量偏置。

    9. 复现时保留哪些量

    用原文附录 A 对应配置做配对。推理回放用思考模式的 Ling-3.0，单副本 TP4。网关对照是双副本，SWE、BFCL、WideSearch 的 (r,CS)(r,C_S)(r,CS​) 分别为 (0.09,196)(0.09,196)(0.09,196)、(2.26,2000)(2.26,2000)(2.26,2000)、(0.10,200)(0.10,200)(0.10,200)。受限工具回放用 r=0.14r=0.14r=0.14、双 TP4、CS=50C_S=50CS​=50 对照 FCFS 和 CAAS，工具槽各在 3、5 做一组。实跑两种模型的 MCP-Atlas 都是环境槽 3，优化配置样本槽 50，缓存比分别 0.14 与 0.34。时间带 30 秒，推理耗时桶 1 秒。保持任务集、生成设置、硬件和服务上游条件尽可能配对。SWE 图 3 的超时线为 6 小时，图 6 的特定对照超时时限是 13 小时，不应混用。

    最小日志需要样本入场和终止、每轮推理请求起止、每次工具入队与服务起止、最终状态和重试类别。若要区分工具执行与排队，不应只记录完整 API 调用从发起到回来的总耗时。让回放在同一状态下释放相同后继，验证一条串行轨迹同时仅有一个待办环境阶段。对推理还应保存输入总量、实际预填充量和抽样的命中数据。公开汇报时把超时当成删失，保留失败题和失败时间。在本笔记中，算过容量交点、顺序样例、表 3 隐含分位数、表 A3 部分比值，训练和服务测量均引用原文。

    10. 结论

    这篇工作把智能体批量运行的两类延迟连在了一起。先用缓存容量和轨迹视角保护本来可复用的工作，再靠独立样本上限让推理与外部调用有机会重叠。到了工具侧，CAAS 用已出现的依赖线索提前推进可能决定完工的轨迹。最有说服力的证据来自等并发的 SWE 与固定其他条件的工具侧对照。历史画像能给出一个可解释的起点，最终还要读时钟、看状态驻留，并同时核查批次和单请求体验。
