不匹配从哪来，又到哪去？

在 RL 中，我们先用推理引擎采样 rollout，再将采样序列送入训练引擎执行 prefill，根据得到的 logprob 计算梯度并更新模型。 两个引擎的前向可能在许多位置算出不同的 logprob，由此使 rollout 带有 off-policy 偏差；校正这种偏差的方法也不止一种。

训练端评分、推理 prefill 与 decode

推理在 prefill 阶段并行处理 prompt，写入模型的 cache，再通过每次生成一个 token 的 decode 继续生成。训练端则并行为整条完成序列评分。 这些路径上的 kernel 可能采用不同的舍入规则或加法顺序。对于循环层和压缩 attention，prefill 还会写入后续每一步 decode 都需要读取并更新的 state。

舍入取决于加法顺序

BF16 中比 1 大的最小可表示数是 1 + 2−7。若计算 (1 + 2−8)，结果会舍入为 1；但若先计算 (2−8 + 2−8)，得到的是 2−7。只要涉及 reduction，我们就必须让两个引擎使用相同的加法顺序。

精度

kernel 执行一系列运算时，每个中间值的精度都是计算定义的一部分。若一个引擎把中间结果舍入到 BF16，另一个保持 FP32， 后续运算就会读到不同的值，最终产生不同的输出比特。

缓存状态必须在 prefill 与 decode 之间对齐

Decode 会为每个新 token 读取并更新 cache。对于 Gated DeltaNet 这类带状态的层，prefill 写入的 cache 以及 decode 的每次更新，都必须与训练端的计算结果一致。因此，我们必须确保 prefill 与 decode 之间没有 mismatch。

如何让训练端与采样端达成一致

我们希望各次前向的 logprob 对齐，因此从最终的 logprob 出发， 沿训练端与采样端的计算路径反向追踪。对每个 算子，我们记录其输入、舍入点 与 加法顺序。对缓存状态，我们比较 prefill 写出的内容 以及 decode 的每一次更新。对分布式算子，我们记录到达了哪些值，以及它们 被加在一起的顺序。

对每个算子，我们向两个引擎提供相同的输入并比较输出字节。一旦出现差异，就把问题 缩小到仍能复现 mismatch 的一行、一次 reduction 或一次状态更新，再对齐这个算子。

对齐一个算子的四种方法

  1. 在训练端前向中调用推理 kernel。我们从 XoRL 调用 SGLang 的 前向 kernel，并为其编写训练用的自定义反向。
  2. 让两个引擎使用同一个 kernel。我们编写一个新 kernel，或扩展已有 kernel，并在 XoRL 与 SGLang 中都调用它。
  3. 让 reduction 对 batch 不变。我们固定决定 reduction 形状的参数， 这样更大的 batch 只是多启动同样的工作，而不会把加法 重新分组。
  4. 编写两个执行相同算术的 kernel。当两个引擎需要不同的 形状或布局时，我们分别编写 kernel，让它们在相同的位置舍入，并按相同顺序相加。
ρₜ = qₜ / μₜ = [qₜ / sᴾₜ] trainer scoring vs. serving prefill × [sᴾₜ / sᴰₜ] serving prefill vs. serving decode × [sᴰₜ / μₜ] stale state

我们希望每一项都等于 1。对于同步 rollout 且 cache 即时重建的情况，最后一项（过期 state）就是 1。我们的工作是让训练 prefill 与推理 prefill 对齐，再让 推理 prefill 与推理 decode 对齐。

所有涉及 cache 的组件都需要额外检查。训练、prefill、eager decode 与 CUDA-graph decode 都会 写状态，四者必须在每个 token 边界写出相同的字节。

训练模型时，我们用 K3,t = ρt − 1 − log ρt 报告 train-infer mismatchSchulman，「Approximating KL Divergence」（2020）。引入 K3 估计量。。它处处 非负，且仅当 ρt = 1 时为零。

我们达到的保证比 K3 = 0 更强：在 1 附近它的行为像 (ρt − 1)2/2，因此在 FP32 里已经变成 0，而 logprob 仍可能有微小差异：差 1e-8 就已经精确为零。 训练端评分、推理 prefill 与推理 decode 的 FP32 选中 token logprob 是 bitwise-identical 的。尽管 SGLang 提供了 batch-invariant kernel 开关，但仅凭 SGLang 仍无法实现 0 train-infer mismatch。我们必须在其基础上继续扩展。

验证阶梯

最终，我们训练完整模型，并在同一权重版本上比较每一个选中 token 的 logprob。测试按难度递增：

  1. 将同一段程序执行两遍，比较输出字节。
  2. 改变 batch 形状与启动配置，比较同一批行。
  3. 向 XoRL 与 SGLang 提供相同的输入。
  4. 在同一权重版本的在线采样中比较它们。
  5. 训练完整模型，并要求 K3 保持为零。

接下来，我们会在一系列模型上测量 train-infer mismatch，以展示这套方法， 从稠密的 Qwen3-8B 开始。

Qwen3-8B：对齐一个稠密 Transformer

在 Qwen3-8B 上，两个引擎可能在常数构造、舍入位置和 reduction 顺序上无法对齐。这里消除 mismatch 相对直接，也为后续处理更复杂的模型提供了可复用的基础组件。 我们会逐个检查模型中的算子，说明 mismatch 从何而来、如何修复，先从 LoRA 开始。

LoRA：前向对齐的两种方式

LoRA 将线性层从 W(x) 改为 W(x) + s B(A(x))。我们支持 两种 serving 模式。合并模式在推理前将 sBA 融入基座权重。分离 模式则保持 A 与 B 分开，并将 adapter 激活加到 W(x) 上。这两条 路径的舍入点不同：合并路径在乘 x 之前先舍入更新后的权值， 分离路径则分别舍入基座投影与 adapter 投影，再相加。

固定 adapter 合并后更快，因为推理无需执行额外的 adapter 投影。在 multi-LoRA 训练中，XoRL 为每个实验保留独立参数与 optimizer state，而 SGLang 则在一次部署中将多个 adapter 的请求合并到同一个 batch。

在合并模式中，我们在 XoRL 与 SGLang 中构造 W′ = W + sBA，并使用相同的权值字节运行模型。 我们在 XoRL 中缓存 W′，直到 A 或 B 改变，并用自定义 autograd 算子将梯度映回 A 与 B。在分离模式中，我们从 XoRL 调用 SGLang 的 LoRA 前向，并实现训练 A 与 B 所需的反向。当量化 expert 需要新的 LoRA 前向时，我们先将 LoRA 运算加入 SGLang，再从 XoRL 调用该前向。

方法 1：在训练端前向中调用推理 kernel

RoPE：对齐表与旋转

CPU 表与 GPU 表会分叉

RoPE 根据与位置相关的正弦和余弦，旋转隐状态中成对的分量。两个引擎可能在 何处构造正余弦表、以及旋转过程中 何时舍入上无法对齐。

对 Qwen， SGLang 在 CPU 上构造逆频率，并在 GPU 上完成位置表， 以便并行计算大外积与正余弦。它只传输较小的 逆频率向量。XoRL 在 CPU 上构造完整表， 因为它在 FSDP 给每个 rank 分配执行 GPU 之前，就在 CPU 或 meta tensor 上构造模块与派生常数。

CPU 与 CUDA 的正弦、余弦实现不同，因此两个引擎可能产出不同的值。当我们用 Qwen3-30B-A3B decode 一条序列时，表的 BF16 值在位置 592 之前都一致。 它们在位置 593 首次不同，下一个 token 上就出现第一次 logprob 不匹配。 这是一条重要经验：必须在足够长的序列上测试 mismatch。

图 CPU 构造的表与 GPU 构造的表在位置 593 首次无法对齐。从此处起，同一旋转会给出不同输出。

在 CPU 上只构造一次表

我们让两个引擎以相同方式构造 RoPE 表：在 CPU 上构造完整的 FP32 表， 缓存后再传到 GPU。在任一引擎施加旋转之前，表的字节就已对齐。

表字节对齐之后，两个引擎都可以选用两种旋转之一。Class A 将正弦、余弦 cast 为 BF16，并在整个旋转过程中舍入。Class B 将旋转保持在 FP32，仅在输出处 cast。我们用 Class B，因为它 更快快 1.23×。 也更准确相对 FP64 的 MAE 大约低 40%。。

RMSNorm：固定 reduction 顺序

RMSNorm 暴露出一个新问题：编译器可以改变 reduction 的执行方式。

为什么会有不匹配？

RMSNorm 将一行中的每个值平方，求和后取均值的倒数平方根，再用其缩放该行。RMSNorm 在计算平方和时需要 reduction，因此两个引擎必须采用相同的 reduction 顺序。

XoRL 在上一层返回前就将 residual 加入，因此下一层 RMSNorm 得到的是一行 BF16。 SGLang 将隐状态与 residual 分开传入，并在 RMSNorm 内部相加。这两种 输入签名会派发到不同的 Triton kernel。

单输入 kernel 载入一行 BF16 并在寄存器中平方。residual kernel 在 FP32 中将两个输入相加， 将结果舍入到 BF16 并存为 residual 输出；然后再存储并重载 FP32 平方。单输入 kernel 计算 1 / sqrt，residual kernel 则用 rsqrt。二者在数学上等价，但可能舍入成不同的 FP32 值。

residual kernel 还会为下一层存储 BF16 residual 行。这次存储 并不进入 reduction，但它的存在会把 Triton 赋给 reduction 操作数的 layout 从 sizePerThread = [4] 改成 [8]。sizePerThread 是每个线程拥有的连续段，不是总数。32 线程一个 warp、四个 warp，128 个线程覆盖 1,024 个值，因此两种 layout 下每个线程都拥有 8 个值。 无论哪种，每个线程仍然拥有 8 个值。变的是哪 8 个：[4] 下线程取两段长度为 4、相距 512 的段，[8] 下则取一段连续的 8 个。 下图单独展示这一效应：同一行 tl.sum 源码，仅添加必需的 BF16 store，就会改变加法顺序，8,192 个输出中有 2,854 个发生变化。

Triton 发出了什么

两个 kernel 都用 triton.compile 对着固定的 sm90 目标、Triton 3.7.1、四个 warp、关闭 autotuning 来编译。两份 TTIR 模块都包含同一个覆盖 1,024 个 FP32 值的 tt.reduce 运算。layout 分配之后，reduction 操作数在单输入 kernel 里是 sizePerThread = [4]，在带 store 的 kernel 里是 [8]。 PTX 每个线程发出的 add.f32 条数相同，两种 layout 都是 7 条，只是操作数不同。

GEMM：沿 K 执行同一次 reduction

GEMM 沿 K 维累加乘积，得到每个输出。训练会处理数千行 packed token， 而 decode 常常只乘一行。像 cuBLAS 这样的库会为每种形状选不同的 kernel，这些 kernel 可能按 不同顺序加同一组 K 乘积。Split-K matmul 是清楚的例子：若干 thread block 分别累加 K 的片段，再合并部分和。当 M 变化时，库可能选出不同的 split 数，从而改变 reduction 顺序并造成不匹配。

方法 3：让 reduction 对 batch 不变

我们编写一个 Triton kernel：每个 program 计算一块输出 tile，并从左到右累加完整的 K 维。BF16 输入使用 64 个值的 slab。kernel 使用一个 FP32 累加器从第一块遍历到最后一块，只 cast 一次输出。现在 M 变大时，我们只是多启动同样的工作。这就是一个简单的 batch-invariant kernel。

Dense attention：一次流式 reduction

Dense attention 是一种 token 混合算子：它对 value 的低维投影进行加权线性组合，权重来自 key 与 query 的低维投影点积的 softmax。 输入中存在较大值时，直接计算 softmax 可能数值不稳定；由于 softmax 对平移不变，可以先从输入中减去最大值。朴素实现需要扫描整个向量来求最大值。FlashAttention 则采用 流式 softmax：它从每块输入 tile 中提取最大值 m、指数和 l，以及加权 value 和 u。在归约两块 tile 级摘要之前，先将它们缩放到同一个最大值。归约所有 tile 级摘要后，即可得到 attention 输出 u / l。

m = max(m₁, m₂); l = exp(m₁ − m)l₁ + exp(m₂ − m)l₂; u = exp(m₁ − m)u₁ + exp(m₂ − m)u₂; Attention = u / l

推理引擎可以通过 多种 attention backend 完成这项计算，例如使用 FlashAttention 或 FlashInfer；训练端则可能使用 FlashAttention、FlexAttention，甚至 SDPA。每个 backend 分块与合并摘要的方式都不同。

训练会处理许多 packed query，而 decode 通常用一条 query 访问很长的 key/value cache。推理 backend 可能将 cache 切分，让多个 block 同时处理这条 query，再通过第二次 reduction 合并各自的 (m, l, u) 摘要。改变 split 数 就会改变加法的先后顺序。不同版本的 FlashAttention 也可能对第一次 reduction 分块得不一样。

对 dense attention，我们在两个引擎中都使用带 num_splits=1 的 FlashAttention 4，因此两边都不再做第二次合并。

LM head：对词表执行一次 reduction

LM head 接收最终隐状态，为词表中的每个 token 计算一个 logit。 对选中的 token y，其 logprob 等于选中 logit 减去整个词表上的 log-sum-exp：

log p(y | h) = zᵧ − log Σⱼ exp(zⱼ)

LM head 将固定 K 的矩阵乘与流式 log-sum-exp 融合在一起。输出取决于 矩阵乘的累加顺序、词表分组边界，以及用来 合并各组摘要的树。

两个引擎都用上固定 K 的矩阵乘之后，它们的 logits 就对齐了，包括选中 token 的 logit zy。剩下的不匹配可能来自词表上的 log-sum-exp。 每个词表组产出一个最大值与一个指数和 (m, l)，头再合并这些摘要。训练端可以一次分 256 个 logit，而 decode 分 128 个。分组不同意味着局部最大值不同，缩放后的和就会按不同顺序相加。

我们让两个引擎都以 256 个 logit 为一组，并在组内及合并各组摘要时使用同一棵显式 reduction 树。

方法 4：编写两个执行相同算术的 kernel

SGLang 需要整行 FP32 logits 来采样 token，而 XoRL 只需要被采样 token 的 logprob。因此，XoRL 直接从 GEMM tile 的 FP32 累加器计算选中 logit 和每一份流式 softmax 摘要，无需物化完整的 [M, V] logits tensor，从而节省大量显存与计算。这说明，为了提高效率，两个引擎可以使用不同的 kernel，只要它们执行相同的算术并产生 bitwise-identical 的输出。

要让两个引擎一致，无需冻结每个启动参数。两边必须固定的是决定 reduction 形状（进而决定顺序）的参数；只影响调度的参数可以自由调整。例如在 LM head 中，我们固定词表维的 tile 宽度和 K slab 宽度，因为它们决定哪些 tile 会被归入同一份摘要，以及沿 K 归约的方式。但每个引擎仍可根据工作负载自行选择行块大小、group size、pipeline stage 与 warp 数。

Qwen3.5/3.6 系列带来了新的挑战：Gated DeltaNet 这样的循环层会将一份 FP32 state 从一个 token 传到下一个，state 中的任何差异都会沿序列传播。对 Qwen3-8B，我们只需对齐 XoRL 与 SGLang；现在还要对齐 SGLang prefill 与 SGLang decode。这也是我们遇到的第一个 MoE，因此还会讨论 MoE 对齐的特殊难点。

Gated DeltaNet：对齐循环状态

Gated DeltaNetYang, Kautz, and Hatamizadeh, “Gated Delta Networks” (2024)。引入本架构使用的循环线性注意力层。 维护一个持续更新的 FP32 矩阵 H，汇总当前 token 之前的全部信息，并在每个 token 上更新一次。对于单个 head 和单个 token，其循环形式为：

H̄ₜ = exp(gₜ)Hₜ₋₁, δₜ = βₜ(vₜ − H̄ₜᵀk̂ₜ), Hₜ = H̄ₜ + k̂ₜδₜᵀ, oₜ = Hₜᵀq̂ₜ/√dₖ

这里 g 是衰减门，β 是更新强度，v 是当前 token 的 value，q̂ 与 k̂ 是 L2 归一化后的 query 与 key。更新 Ht = (I − βtk̂tk̂tᵀ)H̄t + βtk̂tvtᵀ 就是 delta rule。

训练与 decode 对循环的分组不同

训练、prefill 与 decode 对循环采用不同的分组方式。XoRL 每次计算 64 个 token。 SGLang 在 prefill 时也用 64-token 的 chunk，但 decode 一次更新一个 token 的 H。 64-token 计算与逐 token 计算 对 FP32 乘法与加法的分组不同，因此可能在 chunk 边界产生不同的 state。下一个 token 读取该 state 后，差异会沿序列继续传播。

64-token block 内部的计算也不同。SGLang 的 kernel 将 state 存为 [V, K]，采用对应的转置乘法顺序，再通过单独的小块 pass 和一次 merge 求逆 64 行三角因子。XoRL 将 state 存为 [K, V]，并使用一次融合 merge。两边计算的是同一组和，但 FP32 分组不同，因此在长上下文中会有少量元素无法对齐。

在 decode 时回放 64 行计算

两个引擎使用相同的 reduction 顺序进行 q/k 的 L2 normalization，将 g 与 β 保持在 FP32，并在对衰减取指数之前 mask 掉未来位置。Serving 也使用 XoRL 的 [K, V] state kernel 及其融合三角 merge，因此两边 在构造 chunk 边界的那些阶段执行同一套 kernel 体。对 XoRL 的前向， 我们调用 SGLang 的因果卷积 kernel 并实现其反向。

XoRL 训练与 SGLang prefill 使用一次 64 行状态更新，prefill 在每个完整 chunk 之后存储 FP32 状态。要 decode token p，我们从该边界出发，按训练顺序重算第 0 到 p 行。到达下一个 chunk 边界之前，最多重算 64 行。

不匹配 XoRL 训练每次计算 64 行，而 SGLang decode 每次更新一个 token 的 H。SGLang prefill 采用相同的 64 行分组，但按 serving 方向传递 state。

已对齐 要 decode token p，SGLang 从与训练、prefill 相同的 FP32 chunk 边界出发，按相同顺序计算第 0 到 p 行。

GLM-5.2 又引入两项复杂因素：稀疏注意力，以及使用 FP8 原生权值的 expert。要正确训练 GLM-5.2，我们需要组合多种并行方式：Context Parallel、Expert Parallel、Tensor Parallel、Fully Sharded Data Parallel 与 Pipeline Parallel。XoRL 支持对 GLM-5.2 进行全参数、LoRA 与 QLoRA 训练。

稀疏注意力

一些 GLM block 会选择较早的 token 位置参与 attention，后续 block 会复用这些位置。若 selector 的选择不同，mismatch 会沿序列级联。我们先对齐 selector，再对齐 attention。

选出稀疏注意力位置

Selector 返回后续稀疏 attention block 将读取的位置。XoRL 与 SGLang 构造输入的方式不同：XoRL 分别投影 key 和 head gate，再为 BF16 query、key 评分；SGLang 联合投影 key 和 head gate，并在 RoPE 之后将 query、key cast 为 FP8，各自使用独立的 scale。这些差异可能改变最终选中的位置。

我们让 XoRL 采用推理端的 selector 计算：在 BF16 中联合投影 key 和 head gate，并在 RoPE 之后进行 BF16 舍入；然后分别按各自的 scale 将 query 和 key cast 为 FP8。两个引擎都对完整历史评分，分数相同时选择较小的位置，并按升序将位置返回给后续稀疏 attention block。

Prefill kernel 写入 prompt 的 key，decode 则追加每个生成 token 的 key。Prefill 与 decode 可能在不同位置执行 normalization、RoPE 和 BF16 舍入。为了在 XoRL 中复现 serving cache，我们标记 prefill 边界，并使用对应的 SGLang prefill 或 decode 计算重建每一行。

两个引擎可以采用不同的历史存储方式，只要每个逻辑位置上的值相同。XoRL 将历史存储在连续 tensor 中，SGLang 则存储在 64-token page 中。

每一层都使用 128-token 的滑动窗口注意力。C0 层只看这个窗口。 C4 层还会看重叠的摘要。这些摘要覆盖八个 token，每四个 token 建一次。C128 层对每个不重叠的 128-token tile 有一份摘要。每个 query 在一次 softmax 里同时看自己的摘要与滑动窗口。

压缩前缀

要构造一行压缩结果，模型先在 BF16 中投影隐状态，再使用 FP32 权重执行 pooling 和 normalization， 然后施加 RoPE 并存为 FP8。投影采用与稠密层相同的 batch-invariant matmul 和同一份 RoPE kernel。 训练端看到完整序列，而推理在 prefill 时构造这份状态、在 decode 时更新它。因此两边可能在不同的 token 边界上创建压缩行。我们只在对应的 token 组完成时才创建 C4 与 C128 行，以便对齐 serving 边界，确保后续 query 读到正确的压缩行。

Importance sampling、PPO 截断与 CISPO

不截断的 importance sampling 把 token 梯度乘以 ρt。我们把构成该比值的 选中 token logprobs detach 掉，只对 log qt 求导。

XoRL 上的 IS 比 Tinker 上的 IS 表现更好，但仍落后于 bitwise-aligned 运行。 我们使用与 Tinker 相同的形式。 训练后期，IS 每个回合比 bitwise-aligned 运行多生成 44% 的 token。 这些 token 大多不是真正的推理，而是模型在下一次猜测前反复检查格式、词数和准备状态。 如前所述，大比值引发的大梯度会积累在 optimizer state 中，并影响后续许多步。 我们发现绝大部分质量来自 IS 比值大于 1 的 token（也就是训练端给出的似然高于采样端）。

PPO 运行的表现要差得多。我们使用与 Tinker 相同的 clipping threshold。 它丢弃了太多重要 token 的梯度，几乎无法学到有效策略。 测得的 mismatch 虽然远低于 IS，但主要原因是策略只会产生退化的 rollout。

CISPO 正是为了解决这些问题：它不允许 IS ratio 无限增大，也不丢弃梯度，而是限制其贡献。我们使用默认值。实验表明，CISPO 能有效缓解 mismatch。XoRL 上的 CISPO 运行达到 72.5% held-out solve rate，明显高于不截断 IS 的 63.9%，但仍低于 bitwise-aligned 运行的 77.4%。CISPO 在 Tinker 上的效果也很显著，将表现提升了 25%，几乎达到 0-mismatch 运行的水平。按报告的 K3 比较，Tinker 上的 CISPO 也远低于 IS baseline。

在我们尝试的目标函数中，没有一个能完全达到 0-mismatch 运行的水平，尽管 CISPO 已经相当接近。不过，经过仔细调参的目标函数仍有可能近乎完全校正 mismatch。

我们的大多数实验都在 MoE 上进行，因为 train-infer mismatch 对 MoE 的影响可能比对稠密模型更严重。 在网络的大部分位置，mismatch 往往平滑累积：这里相差几个比特，那里再相差几个比特。 但 MoE 层包含离散选择。一旦 router 的 top-k 在训练端与采样端选出不同的 expert，mismatch 就会显著放大。 我们推测，这可能正是导致部分 Tinker 运行失败的模式。

先前工作提出了一种方法：Router Replay。 它在推理时记录被选 expert 的下标，再将其传给训练引擎。Group Sequence Policy Optimization 描述了 Qwen 更早的 Routing Replay 策略，Stabilizing MoE Reinforcement Learning by Aligning Training and Inference Routers 提出 Rollout Routing Replay。 这一做法见于 GSPO 与 R3。但在上面的两次 River 运行中，我们没有观察到只回放 router 下标带来的收益。 Router Replay 的确能略微降低 mismatch，但如果用它挽救 mismatch 很高的 rollout，问题就会显现。假设推理引擎给 expert 0 较高的分数，而训练端给出的分数较低；即使回放相同的 expert 0，仍会出现严重 mismatch：expert 下标一致，routing 权重却不同，因为训练端会根据自己的 logits 重新计算权重。因此，只回放下标在 mismatch 很小时几乎不起作用，在极端 mismatch 时甚至可能有害，只有在中等区间才可能有帮助；总体效果预计会相互抵消。

Cursor 在训练 Composer 2 时改进了 Router Replay：过滤掉训练端 router 给出异常低 gating score 的回放 expert，并用训练端 top-k 中的候选替换。根据其报告，这能降低基础回放残留的 p99 数值 mismatch。这是一种合理的策略；下面再看第三种方案。

我们将 Router Replay 扩展为同时记录并传输 routing 权重。R3 作者特意只传输下标，以保持 router 可训练；这是一个值得肯定的目标。 SGLang 为每个请求返回两份 payload：被选 expert id（整数），以及经过 normalization 的 FP32 routing 权重；每个 token、每个 MoE 层、每个被选 expert 各有一份。XoRL 直接使用传来的权重，不再重新计算。这份 payload 随 token × MoE 层 × 被选 expert 增长，因此我们通过 handle，经 Mooncake 或文件系统传输，而不将其内嵌到 rollout 记录中。

我们将扩展后的 Router Replay 称为 Total Router Recall。它的效果很好：held-out accuracy 几乎与 bitwise-aligned 运行相同，且 K3 全程维持在 3e-4，而没有像 baseline 那样持续上升。

但 Total Router Recall 也有代价：我们无法再按常规方式训练 router。 技术上仍可用 stop-gradient 技巧保留梯度。 若前向传入 w − sg[w] + w*，前向值仍是采样端权重 w*，反向则是 ∂w/∂θ。但后续层使用的是 w*，因此 ∂L/∂w 在回放的 router expert 上求值，而 ∂w/∂θ 在训练端 logits 上求值。两个因子来自不同的 router 选择，因此实际优化的是采样端权重附近 loss 的线性化，梯度误差项相对于两个 router 的差距是一阶的。 训练端现在也与采样端的内部实现耦合：它需要获取采样端的 expert id 和经过 normalization 的权重，并按照采样端的 layout 覆盖每个 token、每个 MoE 层的数据。 每个请求从采样端传到训练端的数据量都很大。Mooncake 能缓解一部分传输压力，但捕获并跨设备发送这些 metadata 仍会带来不可忽视的开销。

我们通过一套与 Tinker 兼容的接口在 XoRL 中运行实验：先启动训练与 采样服务器，再由 轻量客户端 向它们发送采样和训练请求。 我们不希望每个请求都将大量 router metadata 从采样端经客户端再送回训练端。 但这也意味着，如果客户端修改了 token / logprobs，例如删除第一个答案之后的 token，就必须对 routing payload 做出相应修改。

到这里可以看出，这仍是一种权宜方案。Tinker 甚至不支持基础的 Router Replay。 尽管如此，Total Router Recall 仍是我们目前找到的、最接近 bitwise-aligned 系统的替代方案。 如果需要一种容易接入、能够缓解 mismatch，且不要求训练 router 的方法，它是一个不错的选择。 任何能够替代 0-K3 的方案都有吸引力，因为它可能避免 0-mismatch 方案的额外开销。

即使在 0-mismatch 栈上使用 CISPO——这是我们找到的缓解 mismatch 效果最好的目标函数——异步仍会严重降低表现。过期权值与过期 cache 会使 mismatch 迅速升高，模型很早就进入平台期。加入 Total Router Recall 后，可以恢复大部分表现，同时保留 Async RL 的加速收益。在 TRR + CISPO + Async 运行中，报告的 K3 仍会在早期升高，但随后持续下降。

Streaming / Async RL 的目标是让所有训练 GPU 与推理 GPU 始终保持满负载。Streaming RL 可以在不引入任何 mismatch的情况下，让训练与推理部分重叠。

SGLang 每完成一条轨迹就立即返回，客户端组装出完整 group 后再交给 XoRL。XoRL 对每个完整 group 执行一次前向和反向——因为只需在 group 内对 advantage 进行 normalization——并在最后统一执行一次 optimizer step。因此，得到的梯度更新与将全部数据组成一个大 batch 一次处理完全相同。由于等待时间服从几何分布，训练端与采样端可以实现较好的重叠，而无需采用异步更新。

Async RL 用过期策略的新请求填补异构序列长度造成的空隙，但代价是引入 mismatch。另一种做法是通过 multi-LoRA 训练，用不同策略的请求填补这些空隙。当一个任务只剩少量耗时较长的轨迹时，另一个任务可以用新的 batch 填充采样队列。每个请求相对于自己的 adapter 仍是 on-policy，因此这种重叠不会引入 mismatch；前提是这些任务共享同一个基座模型。这不会缩短单个任务的训练时间，但如果一套 XoRL 训练服务和一套 SGLang 采样服务需要同时运行多个实验，multi-LoRA 可以有效提高 GPU 利用率。

结语

我们相信，在开源权重 MoE 上实现 0 mismatch，是任何 RL 栈都能够达到的目标，而且收益明确。这些技术目前都已用于 XoRL，也可以移植到其他栈。虽然 XoRL 目前使用 SGLang 进行推理，但同样的方法也适用于其他推理引擎。
