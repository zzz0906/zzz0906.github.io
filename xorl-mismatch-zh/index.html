开源 RL 栈普遍受 train-infer mismatch 困扰：训练 引擎Megatron-LM、TorchTitan 与 XoRL。 和推理引擎SGLang、vLLM 与 TensorRT-LLM。 算出的 logprobs 对不上。

我们训练 Qwen3.6-35B-A3B 来玩 Wordle，并表明消除训练-推理不匹配后，我们开源 RL 栈的解题率从 63.9% 提升到 77.4%。本文将说明我们如何对齐训练引擎 （XoRL）和推理引擎（我们 fork 的 SGLang），从而以 0 mismatch 训练 DeepSeek、 GLM 与 Qwen 这类开源权重 MoE——也就是让 XoRL 与 SGLang 产出逐字节相同的 logprobs。随后我们会讨论以 0 mismatch 训练的代价与收益，并探讨缓解不匹配的其他方案。

不匹配从哪来，又到哪去？

在 RL 里，我们用推理引擎采样 rollout，再把这些采样序列送进训练引擎做 prefill，用得到的对数概率反传梯度来更新模型。 两个引擎可以在前向的许多位置算出不同的 logprobs，而这些 rollout 因此带上的 off-policy 性，也有多种校正办法。

训练端打分、推理 prefill 与 decode

推理在 prefill 阶段并行处理 prompt，写入模型的缓存状态，再用一次一个 token 的 decode 生成后续 token。训练端则并行给整条完成序列打分。 这些路径上的 kernel 可能对同一组值采用不同的舍入或加法。对循环与压缩注意力而言，prefill 还会写出后续每一步 decode 都要读并更新的状态。

舍入取决于加法顺序

BF16 里比 1 大的最小可表示数是 1 + 2−7。若我们计算 (1 + 2−8)，会舍入成 1。但若先加 (2−8 + 2−8)，得到的是 2−7。只要做 reduction，我们就得让两个引擎使用相同的加法顺序。

精度

kernel 计算一串运算时，每个中间值的精度都是计算的一部分。若一个引擎把中间结果舍入到 BF16，另一个保持 FP32， 后续运算就会吃到不同的值，从而写出不同的输出比特。

缓存状态必须在 prefill 与 decode 之间对齐

Decode 在每个新 token 上读取并更新 cache。要对 Gated DeltaNet 这类带状态的层达成一致，prefill 写出的 cache 以及 decode 的每一次更新，都必须与训练端算出的结果一致。也就是说，我们必须消除 prefill-decode 不匹配。

如何让训练端与采样端达成一致

我们希望各次前向的 logprobs 对齐，所以从这里出发，再 沿训练端与采样端往回走。对每个 算子，我们记录它的输入、舍入点 与 加法顺序。对缓存状态，我们比较 prefill 写出的内容 以及 decode 的每一次更新。对分布式算子，我们记录到达了哪些值，以及它们 被加在一起的顺序。

对每个算子，我们让两个引擎吃同一份输入并比较输出字节。一旦不同，就把问题 收缩到仍能复现不匹配的一行、一次 reduction，或一次状态更新，然后再对齐这个算子。

对齐一个算子的四种做法

  1. 在训练端前向里调用推理 kernel。我们从 XoRL 调用 SGLang 的 前向 kernel，并为其写一份训练用的自定义反向。
  2. 给两个引擎各加同一个 kernel。我们写一个新 kernel，或扩展已有 kernel，并在 XoRL 与 SGLang 中都调用它。
  3. 让 reduction 对 batch 不变。我们钉死决定 reduction 形状的那些量， 这样更大的 batch 只是多启动同样的工作，而不会把加法 重新分组。
  4. 写两个做同一套算术的 kernel。当两个引擎需要不同的 形状或布局时，我们各写一个 kernel，让它们在相同的点舍入，并按相同顺序相加。
ρₜ = qₜ / μₜ = [qₜ / sᴾₜ] trainer scoring vs. serving prefill × [sᴾₜ / sᴰₜ] serving prefill vs. serving decode × [sᴰₜ / μₜ] stale state

我们希望每一项都是 1。最后一项，过期状态，对同步 rollout、并且 cache 是现算的情形就是 1。我们的工作是让训练 prefill 与推理 prefill 对齐，再让 推理 prefill 与推理 decode 对齐。

凡是带 cache 的东西都还要多做一次检查。训练、prefill、eager decode 与 CUDA-graph decode 都会 写状态，四者必须在每个 token 边界写出相同的字节。

训练模型时，我们把训练-推理不匹配报告为 K3,t = ρt − 1 − log ρtSchulman，「Approximating KL Divergence」（2020）。引入 K3 估计量。它处处 非负，且仅当 ρt = 1 时为零。

我们达到的保证比 K3 = 0 更强：在 1 附近它的行为像 (ρt − 1)2/2，因此在 FP32 里已经变成 0，而 logprob 仍可能有微小差异：差 1e-8 就已经精确为零。 训练端打分、推理 prefill 与推理 decode 的 FP32 选中 token logprob 字节是逐比特相同的。尽管 SGLang 有开关去触发 batch-invariant kernel，单靠 SGLang 仍拿不到 0 train-infer mismatch。我们必须在 SGLang 之上继续构建。

验证阶梯

最终，我们训练完整模型，并在同一权重版本上比较每一个选中 token 的 logprob。测试按难度递增：

  1. 把同一段程序跑两遍，比较输出字节。
  2. 改变 batch 形状与启动配置，比较同一批行。
  3. 让 XoRL 与 SGLang 吃同一份输入。
  4. 在同一权重版本的在线采样中比较它们。
  5. 训练完整模型，并要求 K3 保持为零。

接下来我们用一系列模型上的训练-推理不匹配来展示这套方法， 从稠密的 Qwen3-8B 开始。

Qwen3-8B：对齐一个稠密 Transformer

在 Qwen3-8B 上，两个引擎可能在常数如何构造、值在何处舍入、以及 reduction 如何排序上对不上。这里消除不匹配相对直接，但会给我们后续更复杂模型留下积木。 我们会按模型里的每个算子走一遍，说明不匹配从何而来、如何修，从 LoRA 开始。

LoRA：对齐前向的两种做法

LoRA 把线性层从 W(x) 改成 W(x) + s B(A(x))。我们支持 两种 serving 模式。合并模式在推理前把 sBA 加进基座权重。分离 模式则保持 A 与 B 分开，并把 adapter 激活加到 W(x) 上。这两条 计算在不同的点舍入：合并路径在乘 x 之前先把更新后的权值舍入， 分离路径则先分别舍入基座投影与 adapter 投影，再相加。

固定 adapter 合并后更快，因为推理不必再做额外的 adapter 投影。在 multi-LoRA 训练里，XoRL 为每个实验保留独立参数与优化器状态，而 SGLang 则在一次部署里把多个 adapter 的请求打进同一个 batch。

在合并模式里，我们在 XoRL 与 SGLang 中构造 W′ = W + sBA，并对相同的权值字节跑模型。 我们在 XoRL 里缓存 W′ 直到 A 或 B 改变，并用自定义 autograd 算子把梯度映回 A 与 B。在分离模式里，我们从 XoRL 调用 SGLang 的 LoRA 前向，并实现训练 A 与 B 所需的反向。当量化 expert 需要新的 LoRA 前向时，我们先把 LoRA 运算加进 SGLang，再从 XoRL 调用该前向。

方法 1：在训练端前向里调用推理 kernel

在 XoRL 的前向里调用推理 kernel、只补一份反向，是消除训练-推理不匹配的有力手段，但训练时可能不如写一个自定义 kernel 高效。

RoPE：对齐表与旋转

CPU 表与 GPU 表会分叉

RoPE 用与位置相关的正弦、余弦旋转隐状态中的成对分量。两个引擎可能在 何处构造正余弦表、以及旋转过程中 何时舍入上对不上。

对 Qwen， SGLang 在 CPU 上构造逆频率，并在 GPU 上完成位置表， 以便并行计算大外积与正余弦。它只传输较小的 逆频率向量。XoRL 在 CPU 上构造完整表， 因为它在 FSDP 给每个 rank 分配执行 GPU 之前，就在 CPU 或 meta tensor 上构造模块与派生常数。

CPU 与 CUDA 的正弦、余弦实现不同，因此两个引擎可能产出不同的值。当我们用 Qwen3-30B-A3B decode 一条序列时，表的 BF16 值在位置 592 之前都一致。 它们在位置 593 首次不同，下一个 token 上就出现第一次 logprob 不匹配。 这是一条重要教训：我们必须在足够长的序列上测不匹配。

图 CPU 构造的表与 GPU 构造的表在位置 593 首次对不上。从此处起，同一旋转会给出不同输出。

在 CPU 上只构造一次表

我们让两个引擎用同一方式构造 RoPE 表：在 CPU 上构造完整 FP32 表， 缓存它，再把成品表传到 GPU。在任一引擎施加旋转之前，表的字节就已经对齐。

表字节对齐之后，两个引擎都可以选用两种旋转之一。Class A 把正弦、余弦 cast 成 BF16，并在整个旋转过程中舍入。Class B 把旋转保持在 FP32，只在输出处 cast。我们用 Class B，因为它 更快快 1.23×。 也更准相对 FP64 的 MAE 大约低 40%。。

RMSNorm：钉死 reduction 顺序

RMSNorm 暴露出一个新问题：编译器可以改变我们做 reduction 的方式。

为什么会有不匹配？

RMSNorm 把一行里的每个值平方，把平方相加，取均值的倒数平方根，再用它缩放这一行。RMSNorm 在算平方和时做 reduction，因此我们必须在两个引擎之间对齐这次 reduction 的顺序。

XoRL 在上一层返回前就把 residual 加上，因此下一层 RMSNorm 收到的是一行 BF16。 SGLang 把隐状态与 residual 分开传入，并在 RMSNorm 内部相加。这两种 输入签名会派发到不同的 Triton kernel。

单输入 kernel 载入一行 BF16 并在寄存器里平方。residual kernel 在 FP32 里把两个输入相加， 把和舍入到 BF16 并作为 residual 输出存下来；然后再存储并重载 FP32 平方。单输入 kernel 计算 1 / sqrt，residual kernel 则用 rsqrt。二者在数学上等价，但可能舍入成不同的 FP32 值。

residual kernel 还会为下一层存储 BF16 residual 行。这次存储 并不进入 reduction，但它的存在会把 Triton 赋给 reduction 操作数的 layout 从 sizePerThread = [4] 改成 [8]。sizePerThread 是每个线程拥有的连续段，不是总数。32 线程一个 warp、四个 warp，128 个线程覆盖 1,024 个值，因此两种 layout 下每个线程都拥有 8 个值。 无论哪种，每个线程仍然拥有 8 个值。变的是哪 8 个：[4] 下线程取两段长度为 4、相距 512 的段，[8] 下则取一段连续的 8 个。 下图把这一效应单独拿出来：同一行 tl.sum 源码，只加上必需的 BF16 store，就会改变加法顺序，8,192 个输出里有 2,854 个发生变化。

Triton 发出了什么

两个 kernel 都用 triton.compile 对着固定的 sm90 目标、Triton 3.7.1、四个 warp、关闭 autotuning 来编译。两份 TTIR 模块都包含同一个覆盖 1,024 个 FP32 值的 tt.reduce 运算。layout 分配之后，reduction 操作数在单输入 kernel 里是 sizePerThread = [4]，在带 store 的 kernel 里是 [8]。 PTX 每个线程发出的 add.f32 条数相同，两种 layout 都是 7 条，只是操作数不同。

矩阵乘：沿 K 做同一次 reduction

A GEMM 沿 K 把乘积加起来得到每个输出。训练会乘上数千行 packed token， 而 decode 常常只乘一行。像 cuBLAS 这样的库会为每种形状选不同的 kernel，这些 kernel 可能按 不同顺序加同一组 K 乘积。Split-K matmul 是清楚的例子：若干 thread block 分别累加 K 的片段，再合并部分和。当 M 变化时，库可能选出不同的 split 数，从而改变 reduction 顺序并造成不匹配。

方法 3：让 reduction 对 batch 不变

稠密注意力：一次流式 reduction

稠密注意力是一种 token 混合算子：它返回我们称为 value 的低维投影的线性组合，线性组合的权重是我们称为 key 与 query 的低维投影点积的 softmax。 存在大值时直接算 softmax 可能数值不稳，但 softmax 对平移不变，因此可以从输入里减去最大值来稳定它。朴素取最大值需要对整个向量扫一遍。FlashAttention 改做 流式 softmax：它从每一块输入 tile 抽出最大值 m、指数和 l，以及加权 value 和 u。在归约两块 tile 级摘要之前，先把它们缩放到同一个最大值。把许多 tile 级摘要归约起来，就得到注意力输出 u / l。

m = max(m₁, m₂); l = exp(m₁ − m)l₁ + exp(m₂ − m)l₂; u = exp(m₁ − m)u₁ + exp(m₂ − m)u₂; Attention = u / l

推理引擎可以通过 多种 attention backend 来做这件事，例如 FlashAttention 或 FlashInfer；训练端则可能用 FlashAttention、FlexAttention，甚至 SDPA。每个 backend 分块与合并摘要的方式都不同。

训练处理许多 packed query，decode 则常常用一条 query 对着很长的 key/value cache。推理 backend 可能把 cache 切开，让若干 block 同时处理这条 query，再在第二次 reduction 里合并它们的 (m, l, u) 摘要。改变 split 数 就会改变哪些值先被加在一起。不同版本的 FlashAttention 也可能把第一次 reduction 分块得不一样。

对稠密注意力，我们在两个引擎里都用带 num_splits=1 的 FlashAttention 4，因此两边都不再做第二次合并。

语言模型头：对词表做一次 reduction

语言模型头接收最终隐状态，为词表里的每个 token 算出一个 logit。 对选中的 token y，它的 logprob 是选中 logit 减去整个词表上的 log-sum-exp：

log p(y | h) = zᵧ − log Σⱼ exp(zⱼ)

这个头把固定 K 的矩阵乘与流式 log-sum-exp 合在一起。输出取决于 矩阵乘的累加顺序、词表分组边界，以及用来 合并各组摘要的树。

两个引擎都用上固定 K 的矩阵乘之后，它们的 logits 就对齐了，包括选中 token 的 logit zy。剩下的不匹配可能来自词表上的 log-sum-exp。 每个词表组产出一个最大值与一个指数和 (m, l)，头再合并这些摘要。训练端可以一次分 256 个 logit，而 decode 分 128 个。分组不同意味着局部最大值不同，缩放后的和就会按不同顺序相加。

我们让两个引擎都使用 256 个 logit 一组，并在组内以及合并各组摘要时使用同一棵显式 reduction 树。

方法 4：写两个做同一套算术的 kernel

SGLang 需要整行 FP32 logits 来采样 token，而 XoRL 只需要被采样 token 的 logprob。于是我们让 XoRL 直接从 GEMM tile 的 FP32 累加器算出选中 logit 以及每一份流式 softmax 摘要，不必物化完整的 [M, V] logits tensor，从而节省大量显存与计算。这就是一例：为了效率可以允许两个引擎用不同 kernel，只要它们做同一套算术，保证逐字节相同的输出。

什么必须钉死，什么可以自由调

要让两个引擎一致，不必冻结每一个启动参数。必须在两边钉死的，是那些决定 reduction 形状（因而决定顺序）的参数。只影响调度的参数可以自由调。例如在 LM head 里，我们钉死沿词表维的 tile 宽度以及 K slab 的宽度，因为它们决定哪些 tile 会被收进一份摘要、以及我们如何沿 K 归约。但每个引擎仍可按工作负载自行选择行块大小、group size、pipeline stage 与 warp 数。

Qwen3.5/3.6：Gated DeltaNet 与 mixture-of-experts 层

Qwen3.5/3.6 系列带来新挑战：循环层。Gated DeltaNet 是循环层。它把一份 FP32 状态从一个 token 带到下一个，这份状态上的任何差异都会沿序列传播。对 Qwen3-8B 我们只需对齐 XoRL 与 SGLang，现在还要对齐 SGLang prefill 与 SGLang decode。这也是我们遇到的第一个 MoE，因此会讨论对齐 MoE 的特殊难点。

Gated DeltaNet：对齐循环状态

Gated DeltaNetYang, Kautz, and Hatamizadeh, “Gated Delta Networks” (2024)。引入本架构使用的循环线性注意力层。 维护一份运行中的 FP32 矩阵 H，概括当前 token 之前的全部信息，并每个 token 更新一次。对一个头、一个 token，其循环形式是：

H̄ₜ = exp(gₜ)Hₜ₋₁, δₜ = βₜ(vₜ − H̄ₜᵀk̂ₜ), Hₜ = H̄ₜ + k̂ₜδₜᵀ, oₜ = Hₜᵀq̂ₜ/√dₖ

这里 g 是衰减门，β 是更新强度，v 是当前 token 的 value，q̂ 与 k̂ 是 L2 归一化后的 query 与 key。更新 Ht = (I − βtk̂tk̂tᵀ)H̄t + βtk̂tvtᵀ 就是 delta rule。

训练与 decode 对循环的分组不同

训练、prefill 与 decode 对循环的分组不同。XoRL 一次算 64 个 token。 SGLang 在 prefill 时也用 64-token 的 chunk，但 decode 一次更新一个 token 的 H。 64-token 计算与逐 token 计算 对 FP32 乘法与加法的分组不同，因此可能在 chunk 边界产出不同状态。下一个 token 读这份状态，差异会沿序列继续传播。

64 行的块在内部也不一样。SGLang 自己的 kernel 把运行状态存成 [V, K]，并用匹配的转置乘法顺序，再用单独的小块 pass 加上一次 merge 来求逆 64 行三角因子。XoRL 把状态存成 [K, V]，并用一次融合 merge。两边算的是同一组和，只是 FP32 分组不同，因此长上下文下会有一小截元素对不上。

在 decode 时回放 64 行计算

两个引擎用相同的 reduction 顺序做 q/k 的 L2 归一化，把 g 与 β 保持在 FP32，并在对衰减做指数之前 mask 掉未来位置。Serving 也跑 XoRL 的 [K, V] 状态 kernel 及其融合三角 merge，因此两边 在构造 chunk 边界的那些阶段执行同一套 kernel 体。对 XoRL 的前向， 我们调用 SGLang 的因果卷积 kernel 并实现其反向。

XoRL 训练与 SGLang prefill 使用一次 64 行状态更新，prefill 在每个完整 chunk 之后存储 FP32 状态。要 decode token p，我们从该边界出发，按训练顺序重算第 0 到 p 行。到达下一个 chunk 边界之前，最多重算 64 行。

不匹配 XoRL 训练一次算 64 行，而 SGLang decode 一次更新一个 token 的 H。SGLang prefill 共享 64 行分组，但按 serving 方向携带状态。

GLM-5.2：稀疏注意力与 FP8 expert

GLM-5.2 带来新的复杂之处，包括稀疏注意力机制以及这些 expert 权值使用的 FP8 原生权重。要正确训练 GLM-5.2，我们需要组合多种并行：Context Parallel、Expert Parallel、Tensor Parallel、Fully Sharded Data Parallel 与 Pipeline Parallel。XoRL 支持对 GLM-5.2 做全参数、LoRA 与 QLoRA 训练。

稀疏注意力

一些 GLM block 会选出更早的位置来做注意力，后续 block 复用这些选择。若 selector 选出不同位置，不匹配会沿序列级联。我们先对齐 selector，再对齐注意力。

选出稀疏注意力位置

Selector 返回后续稀疏注意力 block 将读取的位置。XoRL 与 SGLang 构造其输入的方式不同。XoRL 分开投影 key 与 head gate，并对 BF16 的 query、key 打分。SGLang 把 key 与 head gate 一起投影，再把 RoPE 之后的 query、key 转成 FP8，各自带自己的 scale。这些差异可以改变被选中的位置。

我们让 XoRL 跟随推理端的 selector 计算。我们在 BF16 里一起投影 key 与 head gate，并在 RoPE 之后做 BF16 舍入。然后把 query 与 key 分别按各自的 scale cast 成 FP8。两个引擎都对完整历史打分，分数打平时选更小的位置，并按升序返回位置给后续稀疏注意力 block。

Prefill kernel 写入 prompt 的 key，decode 再追加每个生成的 key。Prefill 与 decode 可能把归一化、RoPE 与 BF16 舍入放在不同位置。为在 XoRL 里复现 serving cache，我们标出 prefill 边界，并用对应的 SGLang prefill 或 decode 计算重建每一行。

两个引擎可以用不同方式存储历史，只要每个逻辑位置上的值相同。XoRL 把历史存在连续 tensor 里，SGLang 存在 64-token 的 page 里。

Mixture-of-experts 层

在 GLM 里，router 会加校正 bias，expert 从 FP8 权值运行，并且许多 rank（我们最少用 EP=16） 对每个 MoE 输出有贡献。适配器训练与全权值训练共用一份 FP8 expert 前向。 两种模式只在反向之后如何更新 expert 权值上不同。

选出 GLM 的八个 expert

GLM 只在选 expert 时加校正 bias。它们的权重仍来自加 bias 之前的 sigmoid 分数。训练端可能把这份 bias 载成 BF16，而推理保持 FP32，从而改变被选 expert。训练端也可能在调用 expert 之前把归一化后的 routing 权重舍入到 BF16，而推理把它们留在 FP32，并在 expert kernel 里乘上因子 2.5。

四路残差混合

融合会改变残差计算

压缩稀疏注意力

每一层都使用 128-token 的滑动窗口注意力。C0 层只看这个窗口。 C4 层还会看重叠的摘要。这些摘要覆盖八个 token，每四个 token 建一次。C128 层对每个不重叠的 128-token tile 有一份摘要。每个 query 在一次 softmax 里同时看自己的摘要与滑动窗口。

压缩前缀

要构造一行压缩结果，模型在 BF16 里投影隐状态，用 FP32 权重做 pooling， 再归一化，施加 RoPE 并存成 FP8。投影用与稠密层相同的 batch-invariant matmul 和同一份 RoPE kernel。 训练端看到完整序列，而推理在 prefill 时构造这份状态、在 decode 时更新它。因此两边可能在不同的 token 边界上创建压缩行。我们只在对应的 token 组完成时才创建 C4 与 C128 行，以便对齐 serving 边界，确保后续 query 读到正确的压缩行。

在 XoRL 里，我们使用 SGLang 的摘要计算与 FP8 cast。SGLang 的稀疏 prefill kernel 不是字节稳定的，因此我们按每个因果 query 行循环 decode kernel 来回放 prompt。然后用同一个 kernel 一次推进一个 token 的 paged cache。在 token 之间，我们携带最近 token 的 cache、FP32 compressor 状态以及 C4/C128 行，并在与 serving 相同的边界上加入一行压缩结果。

Importance sampling、PPO 截断与 CISPO

当每个 token 都有 ρt = 1 时， PPO 不会截断，CISPO 也不会封顶，更新就退化成上面的 on-policy 梯度。

我们在 XoRL 里的 IS 比 Tinker 里的 IS 训得更好，但仍落后于逐字节对齐的运行。 我们使用与 Tinker 相同的形式。 训练后期，IS 每回合比逐字节对齐运行多生成 44% 的 token。 这些 token 大多不是正经推理，只是模型在猜之前反复检查格式、词数和是否准备好。 如上文所说，大比值带来大梯度时，它会留在优化器状态里，并影响之后许多步。 我们发现绝大部分质量来自 IS 比值大于 1 的 token（也就是训练端给出的似然高于采样端）。

我们的 PPO 运行差得多。我们使用与 Tinker 相同的截断阈值。 它丢掉了太多重要 token 的梯度，几乎学不到东西。 测得的不匹配虽比 IS 低得多，多半是因为策略只在产出退化的 rollout。

CISPO 本应是修好这些问题的目标函数。它不允许无上界的 IS 比值，但也不丢掉梯度，只是限制它们的贡献。我们使用默认值。我们发现 CISPO 能有效缓解不匹配。我们在 XoRL 里的 CISPO 运行落到 72.5% held-out 解题率，明显高于不截断 IS 的 63.9%，但仍低于逐字节对齐运行的 77.4%。CISPO 对 Tinker 的效果也很显著，把表现提升 25%，几乎追上 0-mismatch 运行。若比较报告的 K3，Tinker 上的 CISPO 比 Tinker 上的 IS 基线低得多。

我们试过的目标函数没有一个能完全追上 0-mismatch 运行的表现，尽管 CISPO 相当接近；但这并不排除：仔细调过的目标函数仍有可能近乎完全校正不匹配。

我们大多数实验做在 MoE 上，因为训练-推理不匹配对 MoE 可能比稠密模型更具灾难性。 对网络的大部分，不匹配多少是平滑累积的：这里差几比特，那里差几比特。 但 MoE 层做的是离散选择。一旦 router 的 top-k 在训练端与采样端选出不同 expert，不匹配就会大得多。 我们猜想，这可能就是毁掉 Tinker 那些运行的失败模式。

One idea proposed in prior work is Router Replay: 在推理时记录被选 expert 下标，并把它们传给训练引擎。Group Sequence Policy Optimization 描述了 Qwen 更早的 Routing Replay 策略，Stabilizing MoE Reinforcement Learning by Aligning Training and Inference Routers 提出 Rollout Routing Replay。 这一做法出现在 GSPO 与 R3 里。我们没有看到只回放 router 下标的收益（对比上面两次 River 运行）。 Router Replay 确实略微降低不匹配，但设想一下：若我们指望它挽救一条不匹配极高的 rollout，会发生什么。假设推理引擎给 expert 0 打了高分，训练端给 expert 0 打了低分，我们却仍然回放 expert 0。这时会出现严重不匹配：expert 下标一致，routing 权重却不一致，因为训练端仍用自己的 logits 重算该权重。只回放下标：在不匹配很小时什么也不做，在极端不匹配时甚至可能有害，只在「中等」不匹配区间才可能有帮助；我们预期总体效果几乎会抵消。

Cursor 在训练 Composer 2 时修改了 Router Replay。他们滤掉那些在训练端自己的 router 下 gating 分数低得不合理的回放 expert，并用训练端 top-k 里的候选替换。他们报告这能降低基础回放留下的 p99 数值不匹配。这是合理策略；我们再看第三种选项。

我们把 Router Replay 扩展为同时记录并传输 routing 权重。R3 作者特意只传输下标，好让 router 保持可训练，这是值得尊敬的目标。 SGLang 每个请求返回两份 payload：被选 expert id（整数），以及归一化后的 FP32 routing 权重，按每个 token、每个 MoE 层、每个被选 expert 一份。XoRL 直接使用传来的权重，而不再重算。这份 payload 随 token × MoE 层 × 被选 expert 增长，因此我们用 handle 经 Mooncake 或文件系统搬运，而不是内嵌进 rollout 记录。

我们扩展后的 Router Replay，称为 Total Router Recall，效果很好。它的 held-out 准确率几乎与逐字节对齐运行相同，并且全程 K3 停在 3e-4，而不是像基线那样往上漂。

但 Total Router Recall 也有代价。我们无法再正常训练 router。 技术上仍可用 stop-gradient 技巧拿到梯度。 若前向传 w − sg[w] + w*，前向值仍是采样端权重 w*，反向则是 ∂w/∂θ。但后续层跑在 w* 上，因此 ∂L/∂w 在回放的 router expert 上求值，而 ∂w/∂θ 在训练端 logits 上求值。两个因子来自不同的 router 选择，于是我们优化的是采样端权重附近的损失线性化，梯度误差项对两个 router 的差距是一阶的。 训练端现在也耦合到采样端的内部：它需要采样端的 expert id 及其归一化权重，按采样端的 layout，覆盖每个 token 的每一 MoE 层。 每个请求都要从采样端传给训练端的数据量很大；Mooncake 让它多少可管理，但捕获这些元数据并跨设备发送仍是不可忽视的开销。

我们通过一套与 Tinker 兼容的接口在 XoRL 里跑实验：先启动训练与 采样服务器，再从 轻量客户端 向它们发送采样与训练请求。 我们当然不想每个请求都把巨大的 router 元数据从采样端经客户端再送回训练端。 但这意味着：若我们要在客户端改动 token / logprobs，例如截掉第一个答案之后的 token，就必须以某种方式在 routing payload 上镜像同样的改动。

看到这里你可能觉得这一切有点凑合，确实如此。Tinker 连基础的 Router Replay 都不支持。 尽管如此，Total Router Recall 仍是我们目前能想出的、相对逐字节对齐系统最好的替代。 若你想要一种容易插入、用来缓解不匹配、又不在乎训练 router 的办法，这是个好选项。 任何 0-k3 的替代都有吸引力，因为它可能不必付 0-mismatch 方案必须付的代价。

即便用 CISPO 跑 0-mismatch 栈——这是我们找到的缓解不匹配的最佳目标函数——异步仍会把表现打崩。来自过期权值与过期 cache 的不匹配迅速冲高，模型很早平台化。但加入 Total Router Recall 能收回很大一块表现，同时吃到 Async RL 的加速。我们的 TRR + CISPO + Async 运行里，报告的 K3 仍会在早期冲高，但之后一路往下走。

Streaming / async RL 的目标是让全部训练 GPU 与推理 GPU 始终打满。一种不会引入任何不匹配、又能部分重叠训练与推理的办法，是 Streaming RL。

我们让 SGLang 每完成一条轨迹就立刻返回，客户端拼好完成的组再交给 XoRL。XoRL 对一个完成的组做一次前向-反向——因为我们只需在组内归一化优势——并只在最后做一次优化器步进。因此梯度更新与把全部数据一次性打进一个大 batch 完全相同。因为等待分布是几何的，我们能在训练端与采样端之间得到相当好的重叠，而不需要任何异步。

Async RL 用过期策略的新请求填上异构序列长度留下的气泡，以此换不匹配。但我们也可以用不同策略的请求来填这些气泡，办法是做 multi-LoRA 训练。若我们想同时跑多个任务，当一个任务只剩最后几条掉队轨迹时，另一个任务可以用新鲜 batch 填满采样队列。每个请求对自己的 adapter 仍是 on-policy，因此这种重叠不会引入不匹配。只有这些任务共享同一基座模型时才做得到。当然，这不会加快单个任务的训练；但若我们想拉起一套 XoRL 训练服务与一套 SGLang 采样服务、同时跑多个实验，multi-LoRA 能有效打满 GPU。

结语

我们相信，以 0 mismatch 训练开源权重 MoE，对任何 RL 栈都是非常可达成的目标，而且收益很实在。这些技术今天都用在 XoRL 里，但同样容易移植到其他栈。尽管 XoRL 今天用 SGLang 做推理，我们看不出同一套方法不能用在其他推理引擎上。
