TL;DR

  1. Weight 是最自然的 LUT-B target，但 scale contract 必须分清。CUDA 13.4 reference LUT payload 是 K64 3.125 bits/weight，native SFB path 是 K64 3.25 bits/weight。实测的 3.375-bit two-K32 rows 是 non-native quality oracle。根据 data path，我对 native K64 的估计是 dense FP8 的 40–70%，中心为 55%；32.33× H100 byte ceiling 需要约 79%。
  2. 当前 LUT-B MMA 不支持 A3 作为 matrix A。公开 PTX 只有 B operand 的 lookup decompression；W3 已占用该 operand，因此 W3A3 无法编码。本文支持的 pairing 是 E4M3 A + UE8M0 K32 scale 与 3-bit LUT-B operand。
  3. KV 能用同一条指令，但 layout 更难。QK group 是 8 tokens × 64 head channels； PV group 是 64 tokens × 8 value channels。Offline LM 与可选 OSCAR 把 Qwen K3V3 保持在 PPL 约 10.4，而 per-tile uniform K3V3 的 PPL 是 1504。
  4. Context capacity 是共享 HBM budget，不是模型支持声明。在本文 TP8 memory assumptions 下，single-request arithmetic 是 runtime retile 的 10.0M，或 two direct layouts 的 6.21M；该 pool 会被并发 requests 平分，而且 checkpoint 自身 positional limit 不变。

1Intro：Vera Rubin 最近到底变了什么？

1.1 从“faster GPU”变成 agentic inference platform

NVIDIA 对 Rubin 的官方叙事是 agentic AI：更长 context、更多 reasoning steps、更高 decode interactivity， 以及 rack-scale orchestration。单张 Rubin GPU 的公开规格包括 224 SM、896 Tensor Cores、288 GB HBM4 和 22 TB/s HBM bandwidth；Vera Rubin NVL72 则把 72 张 GPU 连接成一个 NVLink 6 scale-up domain。

1.2 为什么 Weight 和 KV 都值得关心？

Community 常用一句话概括 inference：prefill is compute-bound, decode is bandwidth-bound。 Medium 的 disaggregated inference 文章用这个框架解释了为什么 HBM traffic 和 prefill/decode separation 会变得越来越重要。

Decode 会反复读取两类大数据：每个 linear layer 的 model weights，以及 attention 的历史 K/V。 Weight traffic 每个生成 token 大致固定，在 low batch 时尤其重要；KV traffic 则随 context 增长，并在 long-context serving 中逐渐占主导。LUT-B 的意义在于，同一个 3-bit B-operand format 可以同时减少 static weight 与动态写入 KV cache 的 bytes。

1.3 用 CUDA 13.4 探测 Rubin ISA

SemiAnalysis / InferenceX 报道了第一版公开 SM107 software stack：CUDA 13.4、PyTorch、vLLM 和 OpenAI Triton 开始加入 Rubin 支持， 同时披露了 3-bit programmable LUT Tensor Core。

我们实际安装了 CUDA 13.4.46 Developer Preview，并使用：

  • PTX ISA 9.4
  • sm_107f family target for documented LUT-B/K64 forms
  • ptxas
  • cuobjdump
  • nvdisasm

这让我们至少可以做 compile-time legality check。需要注意，vLLM 的 SM107 tracking issue 仍然是 open，Triton 也只是 initial Rubin support； software bring-up 还没有结束。

2最相关的新特性：3-bit programmable LUT-B

2.1 LUT-B 在做什么？

普通 FP8 B matrix 每个值需要 8 bit。Rubin LUT-B 改为：

  1. 每个位置只存一个 3-bit index；
  2. index 从 8-entry E4M3 LUT 中选择 reconstruction value；
  3. Tensor Core 在 tcgen05.mma 内部完成 lookup；
  4. kernel 不需要先 materialize 一个 decompressed B matrix。

SemiAnalysis 描述的 granule 是 K=64 × N=8 = 512 values：

512 × 3-bit index = 192 bytes
8 × E4M3 LUT      =   8 bytes
--------------------------------
total             = 200 bytes
effective         = 3.125 bit/value

LUT 不要求 uniform spacing，因此可以放 Lloyd-Max 这种 non-uniform centroids。这也是 3-bit 仍可能保住 质量的关键。

2.3 3-bit Weight 是最自然的 LUT-B Case；KV 使用同一个 Primitive

TargetMXFP8 A3-bit LUT-B解决的瓶颈仍然困难的部分
Weight W3A8activation Xoffline-packed Wᵀmodel-weight capacity 与 decode weight bandwidthquantization quality 与 small-batch M occupancy
KV K3V3Q，再到 Pdynamic Kᵀ，再到 Vlong-context KV capacity 与重复 HBM readruntime packing、paged layout、orientation 与 row packing

Weight 的 mapping 更简单：Y = X × Wᵀ 天然把 static、可离线 transpose 的 weight matrix 放在 B，因此每个 64 × 8 granule 都能提前打包成 512 个 indices 和一个 8-value E4M3 LUT。这是 3-bit storage + E4M3 reconstruction，不是普通 INT3 arithmetic。

同一条 instruction 并不限于 static weight。Dynamic Kᵀ 与 V 也能成为 B operand，因此 Rubin 可以用同一个 in-MMA lookup 减少 long-context decode 反复读取的 KV bytes。 KV 更难实现，但它与 weight 使用的是同一个硬件 primitive。

3Weight Quantization：最自然的 W3A8 LUT-B Case

Linear layer 存储 W[N,K]，计算 Y=A×Wᵀ；物理 B operand 天然就是 Wᵀ[K,N]。它是 static、可 offline transpose/fit/pack 的，正好位于 Rubin 提供 LUT decompression 的位置。Qwen3-4B 与 Gemma4-12B 量化所有 text linear weights；MiniMax-M3 只量化 routed-expert 的 w13（fused gate/up）与 w2（down）weights。“Expert-input A8” 指 dispatched hidden 在进入 w13 前做 QDQ；gate/up 后进入 w2 的 intermediate 仍是 BF16。Router、shared experts、attention、norms、embeddings 与 lm_head 保持 native。

5KV Cache Quantization — Accuracy、Speed 与 Capacity Bounds

5.1 Kernel Mapping：把 LUT-B 映射到 Attention

Rubin LUT-B 有一条最重要的规则：它只在 MMA 内解压 matrix B。因此我们不把整个 attention 都压成 3-bit，而是压缩每个 decode step 都会反复读取的 cache；Q 和 P 仍作为 MXFP8 matrix A。

5.1.1 GQA KV 与 MLA latent：同一条配方，两种 cache

两种架构走的是同一条四步路径：

  1. Cache 只写一次。离线准备 codebook；token 进入低精度区域时，只保存 3-bit index 和 8 个 E4M3 lookup values。
  2. 第一次 LUT-B MMA。MXFP8 Q 作为 A，压缩 cache 作为 B，计算 attention scores。
  3. Softmax 保持 FP32。max、exp、sum 和 normalization 不降到 INT3；得到的 P 留在片上， 再转成 MXFP8。
  4. 第二次 LUT-B MMA。MXFP8 P 作为 A，同一类压缩 cache 作为 B，得到 attention output。

差别只在“压缩哪一份 cache”：

  • GQA / MHA（Qwen、Gemma）缓存独立的 Kᵀ 和 V，所以每层有 K/V 两套 codebook，也可以有独立的 R_k / R_v。sink 64、recent 256 和未满 block 保持 BF16。QK tile 是 8 tokens × 64 head channels；PV tile 是 64 tokens × 8 value channels。
  • MLA（Kimi K3）不展开 K/V，只缓存一份共享的 512-d latent c_KV，所以每层 只需一套 codebook 和一个 latent rotation。Kimi 的 69 个 KDA states 与 64-d RoPE suffix 保持原生精度； 只有 24 个 Gated-MLA layers 的 latent 进入 K3V3。同一 latent 在 QK 需要 c_KVᵀ、在 PV 需要 c_KV；因为 public PTX rejects transposed LUT-B，一份 physical copy 需要 runtime retiling。

上面提到的 BF16 sink/recent 窗口值得单独介绍，因为本文所有方案都保留它。cache 中各位置的 敏感度并不相同：最前面的 64 个 token 是 attention sink —— 会吸收不成比例注意力权重的位置； 最近的 256 个 token 则是 decode 引用最频繁的部分。这两段始终保持 BF16、不进入 3-bit 路径； 离开 recent 窗口后，只量化完整 K8 与 V64 blocks。每个 physical tile 都是 512 values，但 K/V 沿不同 轴选择这 512 个值。§5.2.2 的消融分别量化了两者的贡献；窗口与 rotation/clipping 配方沿用 OSCAR 论文。

5.1.3 Lloyd-Max：把 8 个刻度放到真正需要的位置

3-bit 只能表示 8 个值。最简单的 uniform quantization 会把 8 个刻度等距排开；如果大多数值挤在 0 附近、 只有少量 outlier 很大，很多刻度会浪费在几乎没有数据的区域，0 附近反而分得太粗。

Lloyd-Max 的做法很直接：

  1. 在 calibration data 上先放 8 个初始中心。
  2. 每个数分给离它最近的中心。
  3. 把每组中心移动到这一组数据的平均值。
  4. 重复第 2、3 步直到基本不再变化，最后只做一次 E4M3 rounding。

这个过程完全离线进行。Serving 时不再迭代，只需找到最近的一个中心并保存其 3-bit index。GQA 每层分别拟合 K/V 两套 8-value codebook；MLA 每层只拟合 latent 的一套 codebook。

5.1.4 OSCAR：先把尖峰摊平，再交给 3-bit

Lloyd-Max 解决的是“8 个刻度放在哪里”，但如果少数维度特别大，3-bit 仍然很难表示。 OSCAR 可以理解为： 先旋转坐标系，把集中在少数维度的尖峰摊到更多维度，再量化。

具体只有三步：

  1. 在 calibration data 上为每层学习一个 orthogonal rotation。
  2. 写 cache 前先 rotation，并裁掉极少数最极端的 outliers，然后用 Lloyd-Max K3V3。
  3. 在 QK/PV 的另一侧做对应变换或 inverse rotation，让原来的 attention 数学关系保持不变。

GQA 可以分别使用 R_k 和 R_v；MLA 因为 K/V 共享同一个 c_KV，只能使用 一个 latent rotation，并把对应变换吸收到 absorbed-query 和 value projection。最简单的记法是： Lloyd-Max 调整尺子的 8 个刻度，OSCAR 先把要量的东西铺平。

H100/B200 两行只是“如果 HBM 只搬这些 compressed bytes”的 normalization ceiling，不是可执行的 native K3V3 performance。它们必须先用 software unpack/dequantize，实际会增加 instructions、temporary traffic 和 latency。Rubin 的区别是 lookup 发生在 Tensor Core MMA 内，但 Rubin row 同样只是 byte ceiling， 不是 kernel prediction。

在 byte 数字之上，第一个需要补充的 roofline 细节是 operand 方向。把 decode 写成 K × Qᵀ / Vᵀ × Pᵀ 时，长 KV 位于 A 的 M 方向，短 Q/P 位于 B 的 N 方向；对非常 skinny 的 GEMV， 这个方向更容易填满不对称的 MMA tile。但是 LUT 解压只支持 B，所以 compressed KV 必须使用 Q × Kᵀ / P × V 的方向。

有读者向我们指出了最新的 decode kernel，这个观察是对的： FlashInfer SM100 CuTe GQA decode kernel 明确设置 mma_tile_m=128；GEMM1 的 A 是 K、B 是 Q，GEMM2 的 A 是 V、B 是 P。它让 sequence/head-dim 填满 A 的 M 方向，并把 GQA heads × prediction tokens 填进 B 的 N 方向。需要同时区分 其他实现：FlashInfer 旧的 prefill/Tensor Core path 与 FlashAttention-3 也存在 Q/P-as-A、KV-as-B 的排布。因此 operand 角色不是 GQA 的数学规定，而是 kernel-specific schedule；最新的 CuTe decode kernel 确实选择了 KV-as-A —— 而这恰好是 LUT-B 对 compressed KV 禁止的方向。对 LUT-B 来说 Q/P 必须放 A， 于是问题变成 single-token decode 时 A 的 M tile 有多空。

PTX 的 kind::mxf8f6f4 shape 是 M=128、N 从 8 起。Qwen3-4B 的 GQA ratio 是 4，所以一个共享 K/V tile 最多把 4 个 Q heads 打包成 4 行：

为了检查“交换 operand 本身是否总会更快”，我们还在 B300 上用普通 padded dense-E4M3 GEMM 测了相同 logical work。Q/P-as-A 与 KV-as-A 的 median latency 分别为：QK 8K 39.97 / 40.42 µs、PV 8K 43.71 / 46.70 µs、QK 32K 52.42 / 53.41 µs、PV 32K 57.95 / 57.18 µs， 差异在约 7% 以内。这个 cuBLASLt microbench 不包含 FlashInfer 的 persistent decode schedule、TMEM softmax pipeline 或 LUT-B，因此它只能说明“operand 名字本身”不会自动产生巨大 penalty，不能推翻 FlashInfer 对 M/N tile 的选择，也不能替代 Rubin measurement。上表的差距来自 MXFP8 固定 M=128 时的 logical tile utilization。

6Limitations

  1. Quality 来自 numerical simulation，不是 packed Rubin execution。H100/B200 在 multiply 前恢复 fake-quantized tensors。Index/LUT/SFB format 被显式模拟，但最终 fused Weight/KV kernels 尚未在 Rubin 上运行。
  2. Full-tile LUT-B throughput 未知。10%/25%/50%/100%-of-dense rows 只用于观察 sensitivity，不是 expected efficiency。CUDA 13.4 Developer Preview performance data 也不能用于 characterize Rubin。
  3. Layout work 取决于 architecture 与 deployment。H64/OSCAR transforms、dynamic cache packing、MLA retiling、tensor/context sharding 与 hybrid non-attention layers 都不在 isolated GEMM roofline 内，end-to-end implementation 必须计入。

7Conclusions：Accuracy 与 Performance

7.1 Accuracy

  • A8 稳定；当前所需 operand position 不支持 A3。8K–128K 的 A8-only KL₅₀ 都不超过 0.05375。当前 LUT-B 没有 LUT-A，因此 W3A3/KV3A3 无法用同一条 MMA。
  • W3 quality 更依赖算法，而不是“3-bit”这个名字。H64+GPTQ 是跨模型最稳健的 family； uniform/NF3 会崩溃。更细 two-K32 scaling 会改善部分 quality，但这些 rows 是 non-native oracle； 只有 one-K64 rows 是 Rubin kernel candidate。
  • KV3 需要 nonuniform codebook，困难场景还需要 rotation。Uniform Qwen K3V3 达到 PPL 1504/KL₅₀ 5.15；offline Lloyd-Max 把 PPL 拉回约 10.4。Latent OSCAR 把 Kimi K3 从 1.601/0.00800 改善到 1.564/0.00679，并把 GPQA 三种子从 83.16% 提到 89.73%。

7.2 Performance

  • Weight mapping 最干净，但旧 headline 只是 byte ceiling。我的 data-path guess 把 native K64 放在 H100 BF16 weight-only 的 16.32–28.57×，中心为 22.45×；32.33× ceiling 仍要求 dense FP8 的 79.2%，且尚未计入 non-weight overhead。
  • KV 随 context 增长节省更多 bytes，但 decode shape 决定 utilization。GQA4 single-token decode 只有 4/128 M-row occupancy；MLA 可让多个 local heads 复用同一 latent，不继承 相同的 underfill。
  • Qwen GQA4 engineering guess 低于 byte ceiling。1M 下 40–70% data-path band 是 354–619 attention tok/s，中心为 486；page traversal、Q/P conversion、softmax 与 output movement 会继续降低真实 fused kernel。
